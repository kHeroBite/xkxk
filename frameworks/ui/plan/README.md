# ui plan — 정본 문서 색인

> 상태: 운영 중 · 최종 갱신일: 2026-11-24
> 이 폴더는 ui 의 요구·설계·계획·결정을 담는 살아 있는 정본이다. 진입점은 `index.json` 이다.
> Pd 경로 인용 규칙: 2026-11-24 Pd 저장소에서 옮긴 문서에서 새 홈에 대상이 없는 링크는 `Pd:<Pd 저장소 상대경로>` 표기로 풀었다(예: `Pd:plan/05_아키텍처/48_Pd_연동설계_총괄_계약등록부.md`). 이 표기와 본문의 `poc/ui/…` 는 Pd 저장소(`/mnt/c/DATA/Project/Pd`) 기준 경로이며, `poc/ui/` 는 이 저장소의 `frameworks/ui/` 에 해당한다.
> `09_화면설계/02_메뉴구조.md` 재생성은 Pd 저장소에서 한다(새 홈에는 생성기 `menu_tree.py` 와 그 입력이 없어 재생성할 수 없다).

## 핵심 원칙

1. **plan 은 살아 있는 정본이다.**
   - 작업을 시작할 때 `index.json` 을 먼저 읽고, 거기서 가리키는 관련 문서를 읽는다.
   - 작업이 끝나면 확정된 결정은 ADR(`90_결정관리/02_결정기록_ADR.md`)과 `index.json` 에 남긴다.
   - 바뀐 내용은 해당 문서를 직접 고친다. 판 사본(`_v2`·`_old`·`복사본` 등)을 만들지 않는다.
   - 수치·표처럼 생성되는 내용은 손으로 고치지 않고 `_build/` 스크립트로 다시 만든다.
   - 구현이 plan 과 다른 결정을 요구하면 plan 을 먼저 고친 뒤 구현한다(문서 먼저, 코드 나중).
2. **문서 한 개는 300줄을 넘기지 않는다.**
   - 넘으면 `NN_제목_부록/a1_*.md` 로 나누고 본문에는 부록 색인표만 남긴다.
   - 문서 머리에 "상태·최종 갱신일"을 적는다.
3. **확인되지 않은 내용과 민감한 값은 구분해서 다룬다.**
   - 추정이나 미검증 내용은 문장 앞에 "추정"·"미검증"으로 표시한다.
   - 외부 정보는 출처 URL 을 함께 적는다.
   - 자격증명·서버 주소·포트·계정 같은 값은 적지 않는다. 필요하면 `INFRA.md` 의 해당 절을 참조로만 건다.

## 프로젝트 추가 원칙

> ui 에만 해당하는 원칙을 여기에 적는다. 아래 5개는 Pd 대원칙 등록부(`Pd:plan/README.md` 핵심 원칙 표, 기준 커밋 157403c)에서 UI 프레임워크에 해당하는 것만 출처 번호와 함께 인용했다. 정본 문구는 Pd 쪽이다.

- (Pd 1) 소스 파일은 짧게 — 책임 단위로 나눈다(권장 200줄·상한 300줄). 상세는 `04_기술스택/02_소스구조_분할규칙.md`.
- (Pd 3) plan 은 살아 있는 정본 — 시작 전에 `index.json` → 관련 문서를 읽고, 끝나면 결정은 ADR·`index.json` 에, 변경은 해당 문서에 반영한다. plan 과 다른 결정이 생기면 plan 을 먼저 고친다.
- (Pd 8) 옵션화가 대원칙 — 미리 정하지 않고 옵션으로 열어 두며, 문서에 적는 값은 설정 키의 기본값이다. 고정 예외는 법령·보안·데이터 무결성뿐이다.
- (Pd 11) 하드코딩된 값은 없다 — 모든 값은 설정 키와 기본값을 가진다.
- (Pd 14) 레이어 분리 — UI/UX·컨트롤·데이터 레이어를 나눈다. PoC·시험 코드에도 같이 적용한다(계층 검사 `tools/check_layers.py`, 분류표 `LAYERS.md`).

## 폴더 지도

기본 번호는 아래와 같다. 프로젝트가 번호나 폴더명을 바꿀 수 있으며, 문서는 `index.json` `documents` 의 카탈로그 키로 찾는다.

| 폴더 | 담는 것 | 카탈로그 키 |
|---|---|---|
| `00_요구사항/` | 사용자 요구 원문, 요구사항정의서 | requirements_raw, requirements |
| `01_분석/` | 현황·기존 시스템·외부 조사 | analysis |
| `02_범위_일정/` | 개발범위, WBS, 일정표 | scope, wbs, schedule |
| `03_아키텍처/` | 아키텍처 설계, 기술스택 | architecture, tech_stack |
| `04_기능/` | 기능요건 | features |
| `05_데이터/` | ERD(to-be) | erd |
| `06_화면/` | 화면목록·메뉴, 화면기획서 | screens |
| `07_인터페이스/` | API 설계 | api |
| `08_시험/` | 시험계획, 시험케이스, 시험결과서 | test_plan, test_cases, test_report |
| `09_구축_배포/` | 구축·배포 구조(값은 INFRA.md 참조) | deploy |

- 이 영역은 Pd 에서 옮긴 문서 번호 체계를 그대로 쓴다. 실제 폴더는 `00_요구사항/`(요구 원문·정의서), `01_시장조사/`(UIUX 패턴·디자인 테마 조사), `04_기술스택/`(소스 분할 규칙·UI PoC 합격 기준·판정 보고서·창 크롬 기준), `05_아키텍처/`(XKXK 저장소 구조·폼팩터 용어), `09_화면설계/`(화면 설계 전부), `90_결정관리/`(결정대기·ADR·향후과제·옮긴 ADR·D 행 부록·이전기록), `_build/`(메뉴 아이콘 생성기)다. 위 표의 기본 번호와 다르므로 문서는 `index.json` `documents` 로 찾는다.
- 변경이력은 루트 `HISTORY.md` 를 정본으로 쓰고 plan 에 중복해 두지 않는다.
- 이 저장소에서 실제로 쓰는 문서는 `index.json` 의 `active_docs` 로 선언한다. 선언하지 않은 문서는 만들 의무가 없다.
- 시험 자산과 도구의 위치는 `index.json` `assets`(`test_root`·`tools_root`)가 가리키는 README 에 있다.

## 표준 문서 목록과 템플릿

표준 문서의 전체 목록·최소 목차·갱신 주체는 ocanon 스킬의 `references/CATALOG.md` 를 참조한다.
문서별 템플릿은 같은 스킬의 `references/DOC_TEMPLATES_A.md`(분석·설계)와 `references/DOC_TEMPLATES_B.md`(계획·시험·이행)에 있다.

## 표기 규칙

- 파일명은 `NN_제목.md` 로 짓고, 부록은 `NN_제목_부록/a1_*.md` 로 둔다.
- 문서 머리 두 줄에 상태(작성 중·운영 중·보관)와 최종 갱신일을 적는다.
- ID 는 REQ-NN(요구), FN-NN(기능), SCR-NN(화면), TC-NN(시험), ADR-NNN(결정), D-NN(결정대기), TODO-NN(과제) 형식을 쓴다.
- 확인되지 않은 내용은 "추정"·"미검증"으로 표시하고, 외부 정보에는 출처 URL 을 단다.

## 재생성

- 생성 문서는 `python3 -B _build/<스크립트>.py` 로 다시 만든다.
- 재생성 스크립트를 추가하면 이 절에 한 줄로 적는다(스크립트·입력·출력).

| 스크립트 | 입력 | 출력 |
|---|---|---|
| `_build/menu_icons.py`(`--check`·`--self-test`) | `_build/menu_data.py`·`menu_icon_data.py`·`icon_glyphs.py` | 메뉴 아이콘 SVG·axaml·C# 카탈로그(`src/`·`assets/` 아래) |
| (Pd 저장소에서만) `menu_tree.py` | Pd 기능·계약 등록부 | `09_화면설계/02_메뉴구조.md` |
