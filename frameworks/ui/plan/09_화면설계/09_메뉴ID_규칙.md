# 메뉴 ID 규칙 — 불변 4자리 숫자

> 상태: 설계 정본
> 근거: 규칙(§2)은 결정 35·35-1, 배정 방식·표시·탭과 실행 중 항목 제외·클라이언트 프로그램별 번호 체계는 결정 53·55·56·58, 구간 경계 값은 D-157, pd 본체 접두는 D-156 이다. 번호를 부여한 뒤부터 R-3(불변)을 적용한다(경위는 §11).
> 결정 기록: ADR-085(`../90_결정관리/02_결정기록_부록/b12_ADR-085_087.md`), 빌드 채널 원칙 ADR-090(`../90_결정관리/02_결정기록_부록/b13_ADR-089_090.md`).
> 관련: 화면 ID 규칙은 `01_화면설계_공통원칙.md` §9(읽기만 — 이 문서는 01 을 고치지 않는다), 메뉴 트리 생성물 `02_메뉴구조.md`, 정본 데이터 `../_build/menu_data.py`, 생성기 `../_build/menu_tree.py`, ADR-052(화면·메뉴 구조).

## 1. 사용자 원문과 결정

> 각 메뉴마다 ID를 만들어서 관리하자. mars처럼 하니 그게 메뉴명을 말하는것보다 소통에도 확실한것 같았다.

결정 35-1(2026-11-05)은 다음과 같다.

- 업무 화면과 셸 메뉴 모두에 불변 4자리 숫자 ID 를 새로 둔다.
- ID 는 메뉴와 화면 제목에 표시한다.
- 삭제된 번호는 다시 쓰지 않는다.
- 매핑 정본은 `plan/_build/menu_data.py` 다(§6).
- 문서 추적용 화면 ID(`SCR-<기능 영역 코드>-NN`)는 그대로 유지하고 병행한다.
- Mars 의 번호값은 쓰지 않는다. Mars 는 '번호로 소통한다'는 관행만 참고했다.

## 2. 규칙 (결정 35·35-1)

| 번호 | 규칙 | 근거 |
|---|---|---|
| R-1 | 메뉴 ID 는 숫자 4자리다. 앞자리가 0 이어도 4자리로 쓴다(예: `0042`). | 결정 35-1 |
| R-2 | 대상은 업무 화면(탐색기 메뉴의 화면)과 셸 메뉴(파일·창·보기·시스템 항목) 둘 다다. | 결정 35-1 |
| R-3 | 한 번 붙인 ID 는 바꾸지 않는다. 화면 이름·메뉴 그룹·위치·권한·릴리스가 바뀌어도 ID 는 그대로다. | 결정 35-1 '불변' |
| R-4 | 삭제(폐기)된 ID 는 다른 메뉴에 다시 쓰지 않는다. | 결정 35-1 |
| R-5 | ID 는 메뉴 항목과 화면 제목에 함께 표시한다. | 결정 35-1 |
| R-6 | ID 와 화면·메뉴의 대응은 `plan/_build/menu_data.py` 한 곳에만 둔다. 다른 문서는 인용만 한다. | 결정 35-1 |
| R-7 | `SCR-<기능 영역 코드>-NN` 화면 ID 는 병행한다. 화면 ID 도 불변이다(D-496). 메뉴 ID 와 화면 ID 는 서로를 대체하지 않는다. | 결정 35-1 |
| R-8 | Mars 의 메뉴 번호값은 가져오지 않는다. 같은 번호가 우연히 겹쳐도 Mars 와 뜻이 같다는 의미가 아니다. | 결정 35-1 |

두 ID 의 역할은 다음과 같다.

| 구분 | 메뉴 ID | 화면 ID |
|---|---|---|
| 형식 | 숫자 4자리 | `SCR-<기능 영역 코드>-NN` |
| 쓰는 곳 | 사용자 화면(메뉴·제목), 사용자·지원·개발자 사이의 소통 | 설계 문서·기능 추적·시험, 권한 코드·설정 키·캐시 키의 열쇠 |
| 바뀔 수 있나 | 바뀌지 않는다(R-3) | 바뀌지 않는다(D-496). 화면을 다른 모듈로 옮겨도 그대로 둔다 |
| 정본 | `menu_data.py` | `menu_data.py`(형식은 01 §9) |

- 화면 ID 의 접두는 발급 당시의 기능 영역 코드이고 소유 모듈을 뜻하지 않는다. 소유 모듈은 모듈 등록부(`../05_아키텍처/48_Pd_연동설계_총괄_계약등록부.md` §3)에서 찾는다.
- 01 §9 는 화면 ID 형식만 정하고, 01 §9 의 AutomationId 는 화면 ID 를 영역 이름으로 쓴다(예: `scr-prj-01.btnSave`). 이 규칙은 AutomationId 를 바꾸지 않는다.

## 3. 대상 범위 세부

결정 35-1 은 '업무 화면·셸 메뉴 모두' 까지다. S-2·S-5 의 근거는 결정 56, S-7 의 근거는 결정 58 이고, S-1·S-8 은 후보다(§6 끝 글머리의 향후 과제로 추적한다).

| 번호 | 대상 | 후보 처리 | 이유 |
|---|---|---|---|
| S-1 | 업무 화면 1개 | ID 1개. 같은 화면을 여러 메뉴에서 열어도 같은 ID 를 쓴다(후보). | 한 화면을 두 번호로 부르면 소통이 흐려진다 |
| S-2 | 화면 안의 탭·하위 보기 | ID 를 따로 두지 않는다. 필요하면 화면 ID 와 탭 이름으로 부른다(결정 56). | 번호 수가 불어나고 탭 구성은 자주 바뀐다 |
| S-3 | 셸 메뉴의 고정 항목(예: 계단식 배열, 설정…, 도움말) | 항목마다 ID 1개(셸 구간). | 결정 R-2 |
| S-4 | 셸 메뉴의 하위 메뉴 머리(예: `독립 창 ▸`, `모니터 ▸`) | ID 1개. | 머리만 말해도 위치가 특정된다 |
| S-5 | 실행 중에 생기는 항목(열린 창 목록 1~9, 모니터 1·2 …, 최근 항목) | ID 를 두지 않는다. 묶음을 담는 하위 메뉴 머리의 ID 로 부른다(결정 56). | 항목 수와 내용이 실행마다 달라 불변 ID 를 줄 수 없다 |
| S-6 | 구분선·빈 공간·캡션 버튼(최소화·최대화·닫기) | ID 를 두지 않는다. | 메뉴 항목이 아니다 |
| S-7 | pd-admin·오케스트레이터 화면 | 클라이언트 프로그램별 별도 번호 체계다. pd-admin 은 `a0001` 형식, 오케스트레이터(pd-studio·orc 화면)는 `o0001` 형식으로 앞에 영문 한 글자를 붙인다(결정 58). | pd-admin 은 별개 프로그램이고, 접두로 프로그램을 헷갈리지 않게 한다(사용자 원문) |
| S-8 | 로그인 전 전용 창 | ID 1개(후보). | 접속 문제 문의에서 화면을 특정할 수 있다 |

## 4. 번호 배정 방식 (안 2 — 결정 53·58, 구간 경계 값 D-157)

결정 53 은 Q-ID-1 에서 권고안 안 2(셸·업무 두 구간)를 골랐고 `0000` 은 미배정 표시로 남긴다. 결정 58 은 클라이언트 프로그램(pd 본체·pd-admin·오케스트레이터 화면)별 별도 번호 체계를 정했다. 이 문서에서 번호 체계를 가르는 단위는 클라이언트 프로그램이고, 판매 단위인 제품(모듈 조립, `../05_아키텍처/22b_Pd_회사운영플랫폼_솔루션카탈로그.md` §7)과 다르다. 비교했던 안 1(전역 순번)·안 3(메뉴 그룹 구간)은 쓰지 않는다.

| 클라이언트 프로그램 | 형식 | 셸 구간 | 업무 구간 | 근거 |
|---|---|---|---|---|
| pd 본체(사용자 클라이언트) | 숫자 4자리, 접두 없음 | `0001`~`0999` | `1001`~`9999` | 결정 53·58. 접두 없음은 D-156 이다 — 결정 58 이 접두를 붙인 프로그램은 pd-admin·오케스트레이터뿐이므로 pd 본체는 접두 없는 4자리로 구분한다 |
| pd-admin | `a` + 숫자 4자리 | `a0001`~`a0999` | `a1001`~`a9999` | 결정 58 원문 "a0001 처럼 어드민은 앞에 a" |
| 오케스트레이터(pd-studio·orc 화면) | `o` + 숫자 4자리 | `o0001`~`o0999` | `o1001`~`o9999` | 결정 58 원문 "오케스트레이터는 o0001 처럼" |

- `0000`(접두 프로그램은 `a0000`·`o0000`)은 어느 프로그램에서도 배정하지 않고 '미배정' 표시로만 쓴다(결정 53).
- 구간 경계 값(셸 `0001`~`0999`, 업무 `1001`~`9999`, 경계 `1000` 은 비움)은 고정 값이다(D-157). 번호는 `MENU_ID_CONFIRMED` 가 참이 된 뒤부터 R-3(불변)을 적용한다(경위는 §11).
- 구간 경계는 어느 층에서도 바꾸지 않는다. 값의 성격은 고정 예외이고 사유는 데이터 무결성이다(ADR-089). 메뉴 ID 는 어느 회사에서나 같은 화면을 같은 번호로 부르기 위한 식별자라 회사마다 다르면 같은 번호가 다른 화면을 가리키게 된다.
- 같은 구간 안에서는 등재 순서대로 다음 번호를 붙인다. 화면이 다른 메뉴 그룹으로 옮겨가도 번호는 그대로다(R-3).
- 업무 구간 배정 결과(화면별 번호, 화면 배치·화면 ID 값의 후보 표시, 마지막 번호)의 정본은 `plan/_build/menu_data.py` 이고 `02_메뉴구조.md`(생성물)에서 본다. 화면 수와 번호 범위는 이 문서에 값으로 적지 않는다(덧붙인 경위는 §11). 셸 구간은 셸 메뉴 항목 목록 구조화 뒤에 배정한다(§6).
- 같은 내용을 다루어도 클라이언트 프로그램·메뉴 그룹·권한이 다르면 별개 메뉴다. 예를 들어 SCR-FIN-06(pd-admin, 메뉴 ID `a1011`)은 시스템관리자(root)가 공표값을 입력·배포 승인하는 운영사 경로 화면이고, 회사 관리자가 받아 보는 초안 영역 SCR-FIN-03(pd 본체, 메뉴 ID `1029`)과 다른 메뉴다.
- 오케스트레이터 화면은 아직 `menu_data.py` 에 없다. 화면이 등재될 때 `o1001` 부터 붙인다.
- 용량: 업무 구간은 프로그램마다 8,999개, 셸 구간은 999개다. 현행 업무 화면 수의 정본은 `plan/_build/menu_data.py` 이고 `02_메뉴구조.md`(생성물)에서 본다(가감 경위는 §11). 구간 표(셸 `0001`~`0999`·업무 `1001`~`9999`)는 바뀌지 않는다. 셸 고정 항목 수는 미집계이지만 현 셸 메뉴 문자열로 보아 999개를 넘지 않는다고 본다(추정).

## 5. 표시 규칙 (결정 55, 채널 정의는 ADR-090)

결정 55 원문은 "개발/STG/QA 빌드에만 [0042] 이름, 좁으면 툴팁 으로 보여주고, 운영빌드에는 이름만 보여주자." 이다. 채널 이름은 `../05_아키텍처/05_제품구성_시스템메뉴.md` §3.2 의 `dev`·`staging`·`qa`·`prod` 이고, 채널별 포함·제외 표는 ADR-090 이 정본이다(메뉴 ID 표시는 그 표의 첫 행).

| 빌드 채널 | 업무 메뉴 항목·셸 메뉴 항목 | 화면 제목(창 제목줄·제목 탭·문서 탭·독립 창 제목) | 좁은 화면 |
|---|---|---|---|
| dev·staging·qa | `[0042] 이름` (pd-admin `[a0042] 이름`, 오케스트레이터 `[o0042] 이름`) | `[0042] 이름` | 이름만 보이고 ID 는 툴팁 |
| prod(운영) | 이름만 | 이름만 | 이름만 |

- 빌드 채널별 메뉴 ID 표시 여부는 회사 층에서 바꿀 수 없다. 값 분류는 제품 상수이고 근거는 사용자 결정 55·57·90 이다(D-130, ADR-090). 제품 상수는 설정 키를 갖고 운영 시스템 층에서만 정하며 회사 재정의가 없다. 키는 `ui.menu_id.visible_channels`(메뉴 ID 를 보이는 빌드 채널 목록, 이름은 후보)이고 기본값은 위 표의 `dev`·`staging`·`qa` 다. 키 등록부(`../06_기능목록/20_Pd_상세기능설계_공통_권한_화면.md` §5.1)에 올렸다. 옵션화의 고정 예외(법령·보안·데이터 무결성)로 분류하지 않는다. 표시 여부는 빌드 채널로만 갈린다.
- 운영 빌드의 화면에는 메뉴 ID 를 표시하지 않는다. 대신 서버 전송 오류 로그(모든 채널 기본 포함, 결정 90)에는 오류가 난 화면의 메뉴 ID 를 화면 ID 와 함께 싣는다(D-129). 사용자가 오류를 신고할 때 지원 담당은 이 로그의 메뉴 ID 로 화면을 특정한다. 별도 지원 코드는 두지 않는다. 로그 항목 정의는 ADR-090 채널 표와 `../05_아키텍처/05_제품구성_시스템메뉴.md` §3.3 이 정본이다.
- '좁은 화면' 은 스마트폰 NAV 하단 탭·목록, 72 DIP 까지 줄어드는 제목 탭처럼 ID 를 붙이면 이름이 말줄임되는 자리다. 판정 폭은 01 §2-1 제목 탭 폭 규칙을 따르고, 플랫폼별 세부 위치는 폼팩터별 화면 설계 문서(03·04·06)가 정한다(§8).
- 단축키 표시와 ID 의 배치, 웹의 브라우저 탭 제목·딥링크에 ID 를 쓸지는 후보이고 `04_웹_화면설계.md` 에서 정한다(§6 끝 글머리의 향후 과제로 추적한다).
- 다국어: ID 는 언어와 무관하다. 번역된 메뉴 이름이 달라도 같은 ID 로 화면을 특정할 수 있다.
- 화면별 표시 방식의 정본은 화면 설계 문서 01·03·04·06 이고, 그 문서들이 이 규칙에서 받아 적는 내용은 §8 에 있다.

## 6. 정본·생성물 (menu_data.py·menu_tree.py)

- 업무 화면은 `menu_data.py` 의 `MENU_ID` 표가 화면 ID 와 1:1 로 짝짓는다. 프로그램 접두(`PREFIX`)·구간(`SEGMENT`)·확정 여부(`MENU_ID_CONFIRMED`)도 같은 파일에 있다. `02_메뉴구조.md`·`메뉴구조.csv` 는 생성기 `menu_tree.py` 가 이 데이터로 다시 만든 생성물이다. 기존 화면의 메뉴 ID 변경은 생성기가 직전 생성물과 대조해 막는다(R-3 검사).
- 셸 메뉴 항목은 항목 목록 구조(항목마다 이름·종류·메뉴 ID)로 `menu_data.py` 에 두고 셸 구간 번호를 붙인다. 지금 데이터는 `SHELL_MENU` 문자열 하나라서 항목별 ID 를 붙일 자리가 없고, 구조를 바꾸는 일과 번호 배정은 아래 끝 글머리의 향후 과제다.
- 폐기 번호는 지우지 않고 '폐기 목록' 으로 `menu_data.py` 에 남겨 R-4 를 생성기가 검사하게 한다(목록 형식은 후보).
- 생성기 검사는 프로그램 접두와 4자리 형식, 업무 구간 안, 중복 없음, 폐기 번호 재사용 없음, 미정의 화면 없음, 미배정 화면 없음이다. 위반이면 생성을 멈춘다. 직전 생성물 `메뉴구조.csv` 의 화면 ID↔메뉴 ID 짝과 새 값을 대조해 다르면 쓰기 전에 생성을 멈춘다(R-3, 직전 값 0000 미배정은 배정 허용).
- 다른 문서(기능 부록·화면 설계·시험)는 메뉴 ID 를 새로 만들지 않고 `02_메뉴구조.md` 에서 인용한다.
- 아직 하지 않은 일은 넷이다. 셸 구간 번호 배정(R-2 의 셸 메뉴 쪽), 폐기 목록 형식과 화면 삭제 때의 R-4 검사, §3 S-1·S-8 과 §7 의 후보 값, §5 의 단축키·웹 표시 후보다. 향후 과제 목록(`../90_결정관리/03a_향후과제_TODO_2.md`)에 등재해 추적한다.

## 7. 바꿀 때의 절차

| 상황 | 처리 |
|---|---|
| 화면·메뉴 추가 | 클라이언트 프로그램과 구간(§4)에 맞는 다음 번호를 `menu_data.py` 의 `MENU_ID` 끝에 넣고 생성물을 다시 만든다. |
| 이름·그룹·위치 변경 | ID 는 그대로 둔다(R-3). |
| 화면 둘을 하나로 합침 | 남는 화면의 ID 를 쓰고 사라지는 화면의 ID 는 폐기한다(R-4). 합친 사실을 폐기 목록에 적는 것은 후보다. |
| 화면 하나를 둘로 나눔 | 원래 ID 는 기능이 더 많이 남는 쪽에 두고 다른 쪽에 새 번호를 준다(후보). |
| 화면·메뉴 삭제 | ID 를 폐기 목록으로 옮긴다. 다시 쓰지 않는다(R-4). |
| 화면을 다른 모듈로 옮김 | 화면 ID(SCR)와 메뉴 ID 를 모두 그대로 둔다(R-3, D-496). 소유 모듈은 모듈 등록부에서만 바꾼다. |

## 8. 화면 설계 문서가 받아 적는 내용 (01·03·04·06)

아래는 화면 설계 문서가 이 규칙에서 받아 적는 내용이다. 근거는 결정 35-1·53·55·56·58 과 ADR-090 이다.

1. `01_화면설계_공통원칙.md` §9: 메뉴(업무 화면·셸 메뉴)는 불변 메뉴 ID 를 가지며 삭제 번호는 재사용하지 않는다. 형식은 pd 본체 4자리, pd-admin `a`+4자리, 오케스트레이터 `o`+4자리다. 표시는 dev·staging·qa 빌드에서 `[0042] 이름`(좁은 화면은 툴팁), prod 빌드는 이름만이다. 화면 안 탭과 실행 중 생기는 셸 항목에는 ID 를 두지 않는다. 이 문서로 가는 포인터를 둔다.
2. `03_데스크톱_화면설계.md`: 탐색기 트리·제목 탭·창 제목줄·셸 메뉴 항목의 `[0042]` 표시 위치와 툴팁 전환 폭, 창 메뉴 열린 창 목록(1~9)은 ID 를 붙이지 않는다는 점. M1 화면 목록에 pd-admin 법인 마스터 콘솔 SCR-ADM-07(D-127, ADM-10 M1)이 더해졌다.
3. `04_웹_화면설계.md`: 브라우저 탭 제목·딥링크에 ID 를 쓸지(후보). 운영 빌드의 웹에서는 쓰지 않는다(결정 55).
4. `06_모바일_화면설계.md`: 폰 하단 탭·삼선 메뉴 목록은 좁은 화면이라 이름만 두고 ID 는 길게 누르기 같은 툴팁 대체로 보이는 안(후보), 태블릿 DOCK 패널 제목은 데스크톱과 같다. 새 화면 SCR-HRS-04·SCR-PRE-04·SCR-EVA-04 의 스마트폰 노출 값(✕·△·△)은 생성기 데이터의 후보 값이다.
5. `01_화면설계_공통원칙.md` §9 에는 결정 90 의 내용도 함께 적는다. 운영 빌드에는 디버그모드가 없고, 서버 전송 오류 로그는 모든 채널에서 기본이며 화면·메뉴 ID 를 싣는다. 운영 화면에는 메뉴 ID 를 보이지 않는다. 문안은 ADR-090 부록 b13 에 있다.

## 10. 서브 ID (결정 126, D-329)

결정 126(D-327)은 계산기 같은 유틸에 메인 기능 ID 는 새로 주지 않되 서브 ID 를 발급해 구분하라고 정했다. 아래 형식·발급 규칙은 D-329(`../90_결정관리/01_결정대기_부록/d329_결정126_확인대기.md`)다.

| 항목 | 규칙 |
|---|---|
| 형식 | `<기능ID>-U<n>` — 기능 ID(예 `PLT-09`) 아래 유틸·하위 단위. `U` 는 유틸(utility)이고 n 은 1부터 센다. |
| 발급 | 기능 안에서 순번으로 준다. 폐기해도 정의 줄을 지우지 않고 같은 자리에 `(폐기 YYYY-MM-DD)` 를 붙여 남기고(사유는 `, 사유 …` 로 덧붙일 수 있다) 그 번호는 다시 쓰지 않는다(메뉴 ID R-4 와 같은 원칙, 결정 129). 그래서 한 기능의 서브 ID 정의 줄은 폐기 표기 줄을 포함해 1부터 연속이다. 예 `  - **<기능ID>-U<n> 이름**(폐기 YYYY-MM-DD, 사유 …)` — 검사기 S5~S7 이 한 파일로 연속·재사용·형식을 판정한다(`../_build/fd_rules.py`). 발급 기록 주체는 정본 관리자이며 해당 기능 부록 블록에 적는다. |
| 기능 ID 와의 관계 | 서브 ID 는 기능 ID 를 늘리지 않는다. 기능 수 집계(`../06_기능목록/21_Pd_기능요건상세_공통_색인.md` 의 합계)는 그대로다. |
| 메뉴 ID 와의 관계 | 서브 ID 는 기능 안 단위의 식별자이고 메뉴 ID 는 메뉴 항목의 식별자다. 서브 ID 가 독립 메뉴 항목(새 창 열기 등)을 가지면 그 항목은 §4 규칙대로 메뉴 ID 를 따로 받는다(1:N 가능). `menu_data.py` 에는 TODO-153(서브 ID 검사기·메뉴 열 후보) 전까지 서브 ID 를 기록하지 않는다. |
| 표기 위치 | 기능 부록 블록 안 하위 글머리, 화면 설계 문서, 시험 ID 에 쓴다. 부록의 `###` 머리줄·표 첫 칸·`- 라벨:` 형식에는 쓰지 않는다(검사기 `check_feature_detail.py`·`check_ai_usage.py` 가 기능으로 세지 않게 — 집계 불변). |
| 첫 발급 | `PLT-09-U1` 계산기(위젯·독립 새 창 두 형태, 명령 팔레트 인라인 계산은 보조 — `16_개인플래너_전환유도_화면설계.md` §1.1, a05_PLT PLT-09 블록). 다음 후보 단위 변환·타이머는 미발급이다. |
| 옵션 | 제공 유틸 목록(`ui.planner.utility.list`)은 운영 시스템 층에서 정하는 운영 값이고 기본값(후보)은 계산기 1종이다. 위젯 표시(`ui.planner.utility.widget`)·새 창 허용(`ui.planner.utility.window`)은 회사·사용자 옵션이고 기본값(후보)은 켬·허용이다. 키 이름은 후보이고 정본은 키 등록부(`../06_기능목록/20_Pd_상세기능설계_공통_권한_화면.md` §5.1)다(D-505). 형식·결번 규칙은 고정 예외이고 사유는 데이터 무결성(식별자)이다. |

## 11. 개정 이력

본문에서 옮긴 경위다. 현행 규칙은 위 절이 정본이다.

- §4 구간 경계. 결정 53 이 '반영 때 후보로 제시'하라고 한 값이었고 옛 서술은 "사용자 확인 전까지 번호 뒤에 '(후보)' 를 붙여 낸다" 였다(결정 90 반영 사이클에 개정). 번호 부여 완료(TODO-104, 2026-11-06) 때 `MENU_ID_CONFIRMED` 를 확정으로 바꾸고 `메뉴구조.csv` 를 다시 만들었다.
- §4 업무 화면 수. 결정 113 으로 86개에서 88개, 결정 115·116 의 SCR-FIN-06 으로 89개, 결정 117 로 7개를 더해 96개(2026-11-12), 결정 118 로 98개, 결정 129 의 SCR-IAM-05 로 99개, 결정 130 의 SCR-ADM-08 로 100개(2026-11-15)가 됐다.
- §2·§7 화면 ID. 옛 서술은 화면 ID 가 '모듈 재배치 때 문서 정리로 바뀔 수 있다'였다(D-496 으로 개정).
- 머리말. 작성일은 2026-11-05 다. 규칙(§2)은 결정 35·35-1, 배정 방식·표시·제외 대상·프로그램별 번호 체계는 2026-11-05 결정 53·55·56·58 로 정해졌다. 결정 90 반영 사이클(2026-11-06)에 결정 86 자율 판단으로 정한 것이 구간 경계 값(D-157)과 pd 본체 접두(D-156)다. D-156 의 옛 서술은 "접두 없는 4자리는 해석이다" 였다.
- §2. 2026-11-05 Grep 때 `plan/09_화면설계/` 문서에는 메뉴 ID 표시 규칙이 없었다.
- §4 배정 결과. 2026-11-05 에 배정하고 2026-11-06 에 불변으로 돌렸다. pd 본체는 `1001` 부터 붙였고 결정 113·117·118·129·130 으로 화면을 덧붙였다(결정 130 의 SCR-ADM-08 이 `1089`). pd-admin 은 `a1001` 부터 붙였고 결정 115·116 의 SCR-FIN-06 이 `a1011` 이다(2026-11-12).
- §5. 옛 서술은 운영 빌드에서 ID 를 숨기는 근거를 '보안 예외(ADR-090 작성자 해석, 사용자 확인 대상)'와 '사용자가 고정한 제품 정책' 두 가지로 적었다. 값 분류 제품 상수 하나로 고쳤다(README 원칙 8, D-493). D-129·D-130 은 결정 86 자율 판단으로 닫은 행이다.
- §6. 화면 ID 와 메뉴 ID 의 짝은 2026-11-05 에 반영했고 2026-11-11 에 데이터(`menu_data.py`)와 생성기(`menu_tree.py`)를 나눴다. R-3 대조 검사는 2026-11-11 에 넣었다(F-3-034). 옛 서술은 '구간 경계 확정 뒤에 넣는 후보' 였다.
- §8. 옛 제목은 '화면 설계 문서 반영 요청'이었다.
- §10. D-327 은 결정 126 에서 답이 바뀐 행이고 D-329 는 결정 127 에서 닫혔다. 옵션 행의 옛 표기는 'pd-admin 제품 옵션'이었다.
