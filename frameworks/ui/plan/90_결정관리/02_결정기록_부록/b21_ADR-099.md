## ADR-099. MDI·SDI·웹 창 배치(스냅 레이아웃) 도입

### 1. 맥락

- 사용자 요구(2026-11-11, 원문 일부): "상단으로 끌어서 최대화나 정해진 레이아웃대로 변경… 창을 끌어서 원하는 위치를 지정".
- Pd PoC 는 MDI 문서 창·SDI(독립 OS 창)·웹 관리형 창을 끌어 옮기고 탭으로 합칠 수 있다(01 §4.4 탭 합류, 자석 UI-12). 끌어서 정해진 배치로 바꾸는 기능은 없었다.
- Windows 11 은 창을 화면 위쪽으로 끌면 Snap 막대를 보인다(확인됨, https://support.microsoft.com/en-US/windows/experience/snap-your-windows). Pd 의 MDI·웹 창은 OS 창이 아니라 이 OS 기능이 닿지 않는다. SDI 는 OS 창이라 OS 기능과 겹칠 수 있다.

### 2. 결정

| 번호 | 내용 | 근거 |
|---|---|---|
| 99-1 | MDI·SDI·웹 관리형 창·태블릿 MDI 방식에 창 배치를 넣는다. 폰 NAV·태블릿 DOCK 은 해당 없음 | 사용자 원문, 기기별 UI 형 규칙(폰=모바일형만, 끌 창 없음) |
| 99-2 | 칸 종류 6종(최대화·좌우 1:1·좌우 2:1·세로 3열·왼쪽 1/2+오른쪽 위아래·2×2) | '정해진 레이아웃대로 변경' |
| 99-3 | 우선순위는 탭 합치기 > 막대 칸 > 모서리 > 위쪽 가장자리 최대화 > 좌우 가장자리 | 탭 합치기 표적은 작고 명시적이라 이긴다 |
| 99-4 | 막대 칸 밖 위쪽 가장자리 놓기 = 최대화(`SnapTopEdgeMaximize`, 기본 켬) | '상단으로 끌어서 최대화' |
| 99-5 | 막대·감지 띠 밖 놓기 = 칸 미적용 일반 이동, Esc = 시작 위치 복귀 | '창을 끌어서 원하는 위치를 지정'. 이전 판의 '막대 밖이면 취소' 는 원문이 아닌 해석이라 바로잡았다(oplan 검증 F1) |
| 99-6 | 옵션 8개(SnapEnabled·SnapLayouts·SnapEdgeDistance·SnapBarDelayMs·SnapEdgeEnabled·SnapTopEdgeMaximize·SnapKeyboard·SnapSdiMode) | 옵션화 대원칙(ADR-089) |
| 99-7 | SDI 방식 `SnapSdiMode` 자동(기본)·앱·OS·끔. 자동은 OS Snap 켜짐이면 OS 에 맡기고, 판정 불가·실기에서 OS 막대 미확인이면 '앱' | OS 막대와 앱 막대가 함께 뜨는 이중 표시를 막는다 |
| 99-8 | 칸이 창 최소 크기보다 작으면 비활성. 칸은 영역 안이라 끌 수 있는 구간 50px 이상이 늘 남는다 | MDI 끌기 한계 결정(2026-11-08) |
| 99-9 | 키보드 대안은 창 메뉴 '배치 ▸' 와 앱 단축키 후보 Ctrl+Alt+방향키(충돌 확인 뒤 등록, 충돌이면 메뉴만) | Win 키 조합은 OS 예약 |

### 3. 대안

| 안 | 내용 | 판단 |
|---|---|---|
| A(채택) | 공용 데이터(칸 정의·구역 판정) + 경로별 얇은 엿보기 처리기(MDI·관리형·SDI) + 공용 막대 뷰 | 기존 탭 합류 처리기와 같은 구조라 Dock 업데이트 영향이 작고, 웹·태블릿이 같은 코드를 쓴다 |
| B | Dock MdiDocumentWindow 를 상속·재템플릿해 이동 처리 안에서 다룬다 | Dock 내부에 묶여 업데이트 위험이 크다. 기각 |
| C | SDI 는 OS Snap 에만 맡기고 MDI·웹만 구현한다 | 'SDI 도 적용' 요구를 일부만 충족한다. 단독 채택하지 않고 장점(이중 표시 없음)은 99-7 '자동' 으로 흡수했다 |

### 4. 결과

- OS 위임(`SnapSdiMode`=OS, 또는 자동에서 OS 로 판정)이면 SDI 는 OS 모양을 쓰므로 Pd 칸 종류(6종)·옵션·탭 합치기 우선 규칙과 다르다. 같게 하려면 '앱' 을 고른다. 설정 화면의 SDI 방식 설명에도 이 내용을 쓴다.
- '끔' 이어도 OS 의 Snap 동작은 앱이 막지 못한다.
- 저장 형식(LayoutSnapshot)은 바꾸지 않는다. 스냅 전 크기는 메모리에만 두고 재시작 뒤에는 스냅된 사각형을 일반 위치로 복원한다.
- 확실하지 않음: SDI 의 OS 이동 루프(BeginMoveDrag) 끌기에서 OS 위쪽 Snap 막대가 뜨는지, OS Snap 켜짐을 읽는 문서화된 API 가 있는지는 확인하지 못했다. 실기·조사 결과와 자동의 최종 해석(OS 위임 유지 또는 '앱')은 batch 3 에서 이 절에 적는다.
- 최대화 단추 위 Snap 메뉴(HTMAXBUTTON, https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/ui/apply-snap-layout-menu)는 첫 판에서 범위 밖이었다. 아래 개정 1 로 범위가 바뀌었다.

### 4.1 개정 1 (2026-11-11, 새 ADR 번호 없음)

- 사용자 요청(2026-11-11 16:58)으로 최대화/이전 크기 단추 위 1초 호버 팝업을 넣었다. 팝업 칸을 누르면 창 메뉴 '배치' 와 같이 그 칸을 적용한다. 설계는 11 문서 §3.8 이다.
- HTMAXBUTTON 범위 변경: OS 메뉴를 쓰려고 캡션 버튼의 WM_NCHITTEST 응답을 바꾸지 않고, 앱이 팝업을 직접 그린다. 단추 클릭 동작은 그대로다.
- 적용 대상은 MDI 문서 창·웹 관리형 창·SDI 앱 단추다. 터치·폰 NAV·태블릿 DOCK·접은 폴드에는 띄우지 않고, 다른 창이 단추를 덮어도 띄우지 않는다. 데스크톱 SDI 는 `SnapSdiMode`=끔이면 띄우지 않는다.
- Windows 메인 창은 OS(Win11) 메뉴에 맡겨 앱 팝업을 띄우지 않는다. OS 메뉴가 실제로 뜨는지는 실기 확인 전이다(11 문서 §12.2).
- 99-6 의 옵션은 8개에서 10개가 됐다. `SnapFlyoutEnabled`(기본 켬)·`SnapFlyoutDelayMs`(기본 1000, 0~3000)를 더했다. `SnapEnabled` 를 끄면 팝업도 꺼진다.
- 데스크톱 SDI 의 팝업 열림·칸 배치 실기는 보류다(`../../04_기술스택/04_판정보고서_부록/a10_측정보류_목록.md` H-11).
- 위 §4 의 'SDI 끌기에서 OS 위쪽 막대가 뜨는지' 는 batch 3 시점에도 실기 보류다(a10 H-09). 그래서 자동의 해석은 '판정 불가 → 앱' 그대로다(`OsSnapProbe.OsBarConfirmed=false`).

### 4.2 개정 2 (2026-11-11, 새 ADR 번호 없음)

- 사용자 요청(2026-11-11)으로 Snap Assist(남은 칸에 놓을 창 고르기)를 넣었다. 끌기 막대 칸 배치와 최대화 단추 호버 팝업 칸 배치 두 경로 모두 해당한다. 설계는 11 문서 §3.9 이다.
- 결정: 칸 하나에 창을 놓은 뒤 남은 칸마다 후보 창 카드를 보이고, 고르면 다음 칸으로 넘어간다. Esc 는 그때까지 고른 것만 남기고 나머지를 무시한다(사용자 관찰). 가장자리 반쪽·모서리 뒤에도 띄운다(옵션 `SnapAssistOnEdge`, 기본 켬). Windows 의 가장자리 스냅 뒤 동작은 외부 해설 기준이라 **확실하지 않음**이다.
- 옵션은 10개에서 13개가 됐다. `SnapAssistEnabled`(기본 켬)·`SnapAssistOnEdge`(기본 켬)·`SnapAssistThumbnails`(기본 켬, 웹은 비트맵 실패 시 카드 폴백)를 더했다. `SnapEnabled` 를 끄면 함께 꺼진다.
- 대안 3안과 판단은 다음과 같다.

| 안 | 내용 | 판단 |
|---|---|---|
| A(채택) | Shell 상태 머신 `SnapAssistSession` + 표시 이음매 `ISnapAssistOverlay`, 배치는 기존 `WindowMenuOps.ApplyCell` 재사용, 오버레이 1종을 MDI·웹·SDI 가 공유 | 칸 사각형·최소 크기·위치 고정·최대화 해제·저장 표시·스냅 전 크기 기억을 한 곳이 이미 맞춘다 |
| B | 기존 끌기 오버레이(`ISnapOverlay`)에 후보 표시를 얹는다 | 끌기 오버레이는 입력을 통과시키고 포커스가 없는데 Snap Assist 는 입력을 받고 포커스를 가져가 성격이 반대다. 기존 끌기 경로 회귀 위험이 있어 기각 |
| C | MDI·웹·SDI 별로 따로 구현한다 | 코드가 3벌이 되고 규칙이 어긋나기 쉬워 기각 |

- 썸네일은 정지 비트맵 1회(`RenderTargetBitmap`)로 한다. 실시간 `VisualBrush` 는 매 프레임 다시 그려 성능 측정이 보류 중이라 쓰지 않는다. 웹에서 `RenderTargetBitmap` 지원은 **확실하지 않음**이라 실패하면 카드로 폴백한다.
- 같은 지시의 크롬 단추 표현 변경(호버·누름 테두리 제거, 켜짐·꺼짐 기호 구분)은 이 ADR 이 아니라 `../../09_화면설계/01_화면설계_공통원칙.md` §4.2 에 기록한다.
- Snap Assist 의 표시·썸네일 시간은 측정하지 않고 a10 보류로 올린다(H-16).
- 실측 확인(2026-11-12): 데스크톱 MDI 원격 회귀 19/19·웹 w24 14/14·Fold5 DOCK·NAV·접힘 미표시가 PASS 라 11 문서 §3.9 를 '확인됨' 으로 고쳤다. 웹 썸네일은 headless Chromium 에서 `thumb=bitmap` 으로 얻어졌다. SDI 앱 모드 호스트 표시와 데스크톱 실 Shift+Tab 은 보류다(a10 H-17).
- 수치 변경: 크롬 토글 꺼짐 불투명도를 0.55~0.75 에서 0.85 로 올렸다. 0.75 에서 다크 문서 제목줄 실측이 2.96:1 로 3:1 에 못 미쳤기 때문이다(01 §4.2).

### 5. 재검토 조건

- 실기에서 SDI 를 위로 끌 때 OS 막대가 뜨고 탭 합류와 충돌하면 자동의 기본 해석을 '앱' 으로 바꿀지 다시 본다.
- Ctrl+Alt+방향키가 OS·드라이버 단축키와 충돌하면 단축키 후보를 다시 정한다.
- 끌기 프레임 비용 측정(a10 보류)에서 회귀가 나오면 판정 방식을 다시 본다.
