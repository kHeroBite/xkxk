## 1. 평가 축

| 축 | 보는 것 | 좋음(◎) 기준 |
|---|---|---|
| 성능 | 기동 때 추가 비용, 메뉴·창 열기·명령 실행 때 호출 비용 | 지금 PoC 의 직접 호출과 같은 수준 |
| 결합도 | 솔루션이 프레임워크 내부에 얼마나 묶이는가 | 공개 계약만 안다 |
| 배포 | 프레임워크 변경이 솔루션에 닿는 경로와 자동화 정도 | 표준 도구로 자동 전달 |
| 버전 호환 | 깨지는 변경을 언제 어떻게 알아채는가 | 컴파일·pack 때 기계 검출 |
| 커스터마이징 | 메뉴·독·아이콘·글꼴·색 등을 솔루션이 바꿀 수 있는 폭 | 거의 전부 |
| 디버깅 | 솔루션 개발자가 프레임워크 안까지 따라가 볼 수 있는가 | 같은 프로세스·같은 디버거 |
| 보안 | 신뢰 경계·공격면이 늘어나는가 | 새 공격면 없음 |
| 다중 호스트 | 데스크톱·브라우저 WASM(AOT·트리밍)·Android(전체 AOT)에서 같은 방식으로 되는가 | 세 호스트 동일 |
| 학습 비용 | 솔루션 개발자가 익혀야 할 양 | 일반 .NET·Avalonia 지식으로 충분 |

## 2. 방법론별 조사

### M1 모노레포 ProjectReference
- 형태: 같은 저장소 안 앱이 `<ProjectReference Include="../frameworks/ui/src/…csproj" />` 로 소스를 직접 참조한다. 지금 호스트 3개가 이 방식이다.
- 장점: 비용 0, 디버깅 최상, 커밋 즉시 반영된다.
- 단점: 저장소 밖 솔루션은 쓸 수 없다. 버전 개념이 없어 항상 최신 소스에 묶이고 깨지는 변경을 막을 장치가 없다.
- 판정: 저장소 안 소비자(시험 앱·같은 저장소 제품)에만 채택한다.

### M2 NuGet 패키지 참조(층별)
- 형태: 층마다 패키지로 내고 솔루션이 `<PackageReference>` 로 받는다.
- 근거: NuGet 은 SemVer 2.0 을 따른다(https://learn.microsoft.com/en-us/nuget/concepts/package-versioning). 패키지 검증은 pack 뒤 이전 안정판 대비 호환성 깨짐·대상 프레임워크 누락을 검출한다(https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview , https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/baseline-version-validator).
- 장점: 표준 배포 단위다. 정적 링크라 트리밍·AOT 에 그대로 들어간다. 버전 관리가 기계적으로 된다.
- 단점: 버전을 올리고 게시하는 절차가 생긴다. 디버깅은 심볼·소스 링크 구성이 필요하다(구성 방법은 확인 필요).
- 판정: 기본 전달 수단으로 채택한다.

### M3 호스트 빌더 + 모듈 계약
- 형태: `XkxkUi.CreateBuilder(args).UseDesktopHost().AddModule<T>().Build().Run()`. 모듈은 `IUiModule.Configure(IUiModuleContext)` 에서 메뉴·명령·창·독·설정·문구를 등록한다(본문 §4.2 예시).
- 장점: 솔루션은 계약만 안다. 등록 순서·주입 순서를 빌더가 강제해 지금 `App` 정적 속성 대입 순서 문제(부록 a2 §3)를 없앤다. 모듈 단위로 기능을 켜고 끈다.
- 단점: 계약 설계 공수가 크고, 계약은 한 번 내면 바꾸기 어렵다.
- 판정: 구성 API 로 채택한다.

### M4 명령·델리게이트(함수 포인터) 등록
- 형태: `ui.Commands.Add(id, titleKey, icon, execute: ctx => …, canExecute: ctx => …, gesture)`. C# 델리게이트가 함수 포인터 역할을 한다.
- 장점: 호출 비용이 직접 메서드 호출 수준이다. 컴파일러가 형식을 검사한다. 리플렉션이 없어 트리밍·AOT 안전하다.
- 단점: 델리게이트가 잡는 객체 수명 관리(메모리 누수)를 계약에 적어야 한다.
- 판정: 동작 연결 방식으로 채택한다. 메뉴·단축키·즐겨찾기·원격 진단이 같은 명령 ID 를 쓴다.

### M5 뷰모델 계약 + 뷰 매핑(창 내용 전달)
- 형태: `ui.Windows.Register<TViewModel, TView, TArgs>(id, options)`. 창이 열릴 때 프레임워크가 뷰모델을 만들고 `OnOpenedAsync(args)` 를 부른 뒤 뷰를 붙인다.
- 대안 비교: 창마다 `Func<Control>`(뷰 팩토리)을 넘기는 방식은 단순하지만 불러오는 중 표시(REQ-114)·인자 전달·저장 복원을 솔루션이 매번 짜야 한다. 컨트롤 인스턴스를 직접 넘기는 방식은 지연 생성이 안 돼 기동이 느려진다. 이름 규칙으로 뷰를 찾는 리플렉션 ViewLocator 는 트리밍 경고 대상이다.
- 장점: 지연 생성, 강타입 인자, 불러오는 중 아이콘 스피너·취소·오류 표시를 프레임워크가 공통 처리한다. 지금 `IDocumentViewFactory` 를 일반화한 형태다.
- 판정: 창 내용 전달 방식으로 채택한다.

### M6 선언형 매니페스트 + 소스 생성기
- 형태: 솔루션이 `ui.manifest.json`(메뉴 트리·명령·아이콘 키)을 두면 증분 소스 생성기가 컴파일 때 M3·M4 등록 코드로 바꾼다.
- 근거: 소스 생성기는 컴파일 중 코드를 만들어 컴파일에 추가한다(https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/source-generators-overview). 증분 생성기(`IIncrementalGenerator`)는 단계별 결과를 캐시해 바뀐 입력만 다시 계산한다(https://github.com/dotnet/roslyn/blob/main/docs/features/incremental-generators.md). 트리밍 지침은 리플렉션 기반 처리 대신 소스 생성기를 고려하라고 한다(https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming). "기존 코드 수정 불가"는 문서가 명문화한 문장을 찾지 못했고 "추가" 개념만 확인했다.
- 장점: 선언형 편의와 컴파일 타임 성능·검사를 함께 얻는다. 지금 아이콘 생성기(`plan/_build/menu_icons.py`)와 같은 사상을 빌드에 넣는 것이다.
- 단점: 생성기 작성·유지 공수, 생성 코드 디버깅 학습이 필요하다.
- 판정: 선택 계층으로 둔다. 기본 API(M3~M5)만으로 모든 기능이 되게 한다.

### M7 DI 컨테이너 확장점
- 형태: `IServiceCollection` 에 서비스를 등록하고 `IServiceProvider` 로 꺼낸다(https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection). 솔루션이 로그·저장소·아이콘 공급자를 교체한다.
- 장점: .NET 표준 관례라 익숙하다. 서비스 교체가 쉽다.
- 단점: 생성자 선택이 리플렉션 기반이라 트리밍·AOT 영향이 있을 수 있다. 위 문서에는 트리밍·AOT 언급이 없어 확인 필요다. 기동 때 그래프 구성 비용이 있다.
- 판정: 결정 항목(본문 §11 결정 7). 권장은 빌더 안 자체 등록부(제네릭 팩토리 델리게이트)로 시작하고, AOT 경고 실측 뒤 재검토하는 것이다.

### M8 파라미터형 열기(문자열 키 + 인자 사전)
- 형태: `ui.Open("acme.project.editor", new Dictionary<string, object?> { ["id"] = 42 })` 또는 `xkxk://open/acme.project.editor?id=42`.
- 장점: 원격 진단·딥링크·즐겨찾기 저장·매니페스트처럼 문자열로만 다룰 수 있는 경로에 필요하다.
- 단점: 형식 검사가 실행 때로 밀리고 오타가 조용히 실패할 수 있다.
- 판정: 보조로만 둔다. 강타입 인자(M5 `TArgs`)를 기본으로 하고, 문자열 경로는 등록된 인자 변환기를 거쳐 강타입으로 바꾸는 어댑터로 한정한다.

### M9 선언형 매니페스트 런타임 해석
- 형태: 기동 때 JSON·YAML 을 읽어 메뉴·창을 만든다. 명령은 이름 문자열로 리플렉션 바인딩한다.
- 장점: 재빌드 없이 파일만 바꿔도 메뉴가 바뀐다.
- 단점: 기동 때 파싱 비용이 들고, 오류가 실행 때만 드러난다. 리플렉션 바인딩은 트리밍 경고 대상이다(prepare-libraries-for-trimming, 위 URL). 스키마 버전 관리가 별도로 필요하다.
- 판정: 기본 경로에서 뺀다. 단 사용자 개인화(즐겨찾기·레이아웃)처럼 원래 실행 중 데이터인 것은 지금처럼 JSON 저장을 유지한다.

### M10 테마·스타일 패키지만 공유
- 형태: 토큰·스타일·아이콘 리소스만 패키지로 나누고 셸은 각자 만든다.
- 장점: 가볍고 위험이 적다.
- 단점: 사용자가 원한 "메뉴·독·창 구성까지 프레임워크가 제공"을 채우지 못한다.
- 판정: 독립 방법으로는 기각하고, M2 의 패키지 하나(토큰·테마)로 흡수한다.

### M11 템플릿 복제(dotnet new·fork)
- 형태: 시작 템플릿으로 솔루션을 만들고 그 뒤는 각자 고친다.
- 장점: 처음 시작이 가장 빠르고 제약이 없다.
- 단점: 복제 뒤 갈라져 변경이 퍼지지 않는다. 원문 5.5(자동 배포·적용)에 정면으로 어긋난다.
- 판정: 프레임워크 전달 방법으로는 기각한다. 새 솔루션의 빈 시작점(패키지 참조가 미리 들어간 `dotnet new` 템플릿)으로만 쓴다.

### M12 플러그인 동적 로드(AssemblyLoadContext·MEF)
- 형태: 실행 중 폴더의 DLL 을 읽어 모듈을 붙인다.
- 근거: 플러그인은 `AssemblyLoadContext` 와 `AssemblyDependencyResolver` 로 읽고, 공유 계약 어셈블리가 같은 인스턴스가 아니면 같은 이름 형식도 다른 형식이 된다(https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext , https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support). 같은 튜토리얼은 신뢰할 수 없는 코드를 안전하게 읽을 수 없다고 경고한다(보안 경계 아님). Native AOT 는 `Assembly.LoadFile` 같은 동적 로드를 지원하지 않는다(https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).
- 장점: 재빌드 없이 기능 교체가 된다.
- 단점: 웹(AOT·트리밍)·Android(전체 AOT)에서 기본 경로로 쓸 수 없다. 형식 동일성·의존 충돌 관리가 어렵다.
- 판정: 기각한다.

### M13 웹뷰·마이크로프런트엔드 임베딩
- 형태: 셸 안에 웹뷰를 두고 솔루션 화면을 웹으로 띄운다.
- 장점: 솔루션이 어떤 웹 기술을 써도 된다.
- 단점: 웹뷰 기동·메모리 비용이 별별UI 의 네이티브 렌더 성능 목표(원문 5.6)와 어긋난다. 테마·글꼴·Ctrl+휠 배율·창 아이콘 같은 셸 규칙이 웹 내용까지 닿지 않는다. Avalonia 의 세 호스트 공통 웹뷰 지원은 확인 필요다.
- 판정: 기각한다.

### M14 프로세스 밖 UI 셸 + IPC
- 형태: 별별UI 를 별도 프로세스로 띄우고 솔루션이 named pipe·gRPC·JSON-RPC 로 메뉴·창을 지시한다.
- 장점: 언어 독립, 셸 단독 갱신이 가능하다.
- 단점: 모든 호출이 직렬화·프로세스 경계를 지난다. 창 내용(그리드·간트)을 원격 프로세스에서 그릴 수 없어 결국 내용 프로토콜을 새로 만들어야 한다. 브라우저 샌드박스·Android 에서는 별도 프로세스 구성이 안 된다고 본다(추정).
- 판정: 기각한다.

### M15 로컬 HTTP/REST API
- 형태: 셸이 로컬 포트에서 REST 를 열고 솔루션이 호출한다.
- 장점·단점: M14 와 같고, 포트 노출이라는 공격면이 더해진다. 지금 진단 원격 제어(`PD_DIAGNOSTICS`)가 이 형태지만 시험 전용이고 제품 빌드에서 빠진다.
- 판정: 기각한다(진단 용도는 지금처럼 유지).

## 3. 조합 결론

- 기본: M2(전달) + M3(구성) + M4(동작) + M5(창 내용). 저장소 안에서는 M2 대신 M1.
- 보조: M8 은 문자열 경로 어댑터, M10 은 M2 안의 테마 패키지, M11 은 시작 템플릿.
- 선택: M6(1.0 뒤), M7(결정 7).
- 제외: M9(실행 중 데이터 외), M12·M13·M14·M15.
- 이 조합에서 연결이 실행 때 일어나는 곳은 델리게이트 호출과 지연 생성뿐이라, 본문 §7 의 "경계 비용 0" 원칙을 지킬 수 있다(추정 — F2·F6 에서 실측으로 확인).
