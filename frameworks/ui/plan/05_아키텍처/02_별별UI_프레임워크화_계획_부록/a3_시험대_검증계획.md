## 1. 목적

- 프레임워크(`src/`)와 분리된 시험대 프로젝트를 두고, 외부 솔루션과 같은 조건(공개 API 만)으로 프레임워크를 상시 사용·검증한다(dogfooding).
- 메뉴·명령·창·독·아이콘·테마·글꼴·문구·API 등록을 사람이 직접 바꿔 보며 시험할 수 있게 한다(사용자 요청, RAW-003).
- 시험대와 검증 스크립트로 프레임워크 회귀를 자동 판정한다. 같은 스크립트를 로컬 일괄 실행기와 CI 가 함께 쓴다.

## 2. 위치

| 안 | 위치 | 판단 |
|---|---|---|
| A(채택) | 영역 안 `frameworks/ui/testbed/` | 프레임워크(`src/`)와 폴더로 나뉘고, 같은 영역이라 하네스 test_root·tools_root·빌드 스크립트·빌드 잠금을 그대로 쓴다. 이름은 폴더 기준 `xkxk.frameworks.ui.testbed.*`(UADR-0002 규칙)이다. |
| B | 저장소 루트 `apps/` | `../01_XKXK_저장소구조.md` §4 가 `apps/` 를 제품 앱 자리로 정했다. 시험대는 제품이 아니어서 기각했다. |
| C | 본문 첫 제안 `samples/xkxk.frameworks.ui.sample` | '예제'로 읽혀 시험·검증 목적이 흐려진다. 사용자 표현 '테스트용 프로젝트'에 맞춰 testbed 로 바꿨다. |

- 시험대 별도 저장소는 두지 않는다. 같은 영역이 하네스·빌드 잠금 재사용에 유리하고, 패키지 모드 빌드(§3.3)로 저장소 밖 소비 조건을 따로 재현할 수 있기 때문이다.

## 3. 구성

### 3.1 트리

```text
frameworks/ui/
├── src/                                        # 프레임워크(패키지 대상)만
│   ├── xkxk.frameworks.ui · .data · .shell · .views · .fonts
│   └── xkxk.frameworks.ui.hosting.desktop · .hosting.browser · .hosting.android   # B11 신설(호스트 공통 코드, 소스만 분리 — 패키지화는 F5)
├── testbed/                                    # 시험대(IsPackable=false, 패키지 대상 아님)
│   ├── xkxk.frameworks.ui.testbed/             # 시험대 모듈 1개(라이브러리): TestbedModule·데모 문서·차트·엑셀·설정 패널·시나리오 해석기
│   ├── xkxk.frameworks.ui.testbed.desktop/     # 실행 호스트 3개(B11 에 지금 src 호스트의 Program·csproj 이동)
│   ├── xkxk.frameworks.ui.testbed.browser/
│   ├── xkxk.frameworks.ui.testbed.android/
│   ├── xkxk.frameworks.ui.testbed.consumer/    # 최소 소비자 앱(30줄 안팎, PackageReference 만, B17)
│   ├── scenarios/                              # 시나리오 JSON(시험대 해석기 전용, B15)
│   └── Directory.Build.props                   # 참조 전환: 평소 ProjectReference, -p:XkxkUiUsePackages=true 면 피드 PackageReference
├── test/framework/                             # 프레임워크 검증 스크립트(§6, test_root 하위)
└── tools/pack_local.sh                         # 로컬 피드(artifacts/feed, git 무시)로 pack(B17)
```

- 구성 요약: 시험대 모듈 1, 실행 호스트 3(데스크톱·웹·Android), 최소 소비자 앱 1(consumer), 시나리오 폴더 1 이다.
- 시험대 모듈은 프레임워크 공개 계약(`IUiModule`)을 구현하는 보통 모듈이다. 실행 호스트는 `XkxkUi.CreateBuilder` 에 시험대 모듈을 등록하는 얇은 Program 만 가진다.
- 최소 소비자 앱은 시험대 모듈 없이 피드 패키지만 참조해 빈 셸을 띄운다. 패키징 결함(누락 리소스·전이 의존)을 잡는 용도다.

### 3.2 정체성

- 시험대 앱 정체성은 빌더 인자로 넘긴다. 프레임워크 기본값을 쓰지 않는다.
- 데이터 폴더 `%LOCALAPPDATA%\xkxk\frameworks\ui\testbed`, 단일 인스턴스 이름 `xkxk.frameworks.ui.testbed.<채널>.Instance`, Android 패키지 `xkxk.frameworks.ui.testbed`, 실행 파일 `xkxk.frameworks.ui.testbed.desktop.exe` 다. UADR-0002·0003 의 폴더 경로 규칙을 그대로 적용했다.
- Fold5 에서는 옛 `xkxk.frameworks.ui` 패키지를 B11 에서 제거하고 새 패키지를 설치한다. 옛 데이터 폴더·설정은 이전하지 않는다.
- B11 첫 단계에서 실행 파일 이름·경로를 한곳(`test/common/_paths.py`·`tools/pdctl.py` 상수)에서 읽게 바꾼 뒤 이동한다. 판정기 수십 개를 한 번에 깨지 않기 위해서다.

### 3.3 분리 강제

시험대가 외부 솔루션과 같은 조건이라는 것을 문서가 아니라 검사로 강제한다.

| 수단 | 내용 | 시작 batch |
|---|---|---|
| 공개 API 만 | 프레임워크 csproj 는 시험대에 `InternalsVisibleTo` 를 주지 않는다. 시험대는 `public` 형식·멤버만 쓴다. | B10 |
| check_layers 확장 | `tools/check_layers_rules.json` 에 `testbed` 층을 더한다. 시험대·소비자에서 `xkxk.frameworks.ui.*.Internal` 네임스페이스 참조, 리플렉션 `BindingFlags.NonPublic` 우회, 프레임워크 csproj 의 `InternalsVisibleTo` 선언을 금지 코드로 건다. | B02 규칙 골격 · B10 testbed 경로 활성 |
| 패키지 모드 빌드 | `-p:XkxkUiUsePackages=true` 로 시험대 3호스트를 ProjectReference 대신 피드 PackageReference 로 빌드한다. 저장소 안에서만 되는 참조(내부 형식·소스 상대경로·누락 리소스)를 잡는다. | B17 로컬 피드 · B18 사내 피드 |

- B02 규칙 골격의 실제 파일은 `tools/check_layers_consumer.py` 다(규칙은 `tools/check_layers_rules.json` 의 `consumer_rules`).
- 층 정의 정본 `../../04_기술스택/02_소스구조_분할규칙.md` 에 시험대 층 행을 먼저 추가한 뒤(B10) 규칙 파일을 바꾼다.
- 시험대 층은 프레임워크 모든 층을 참조할 수 있고, 프레임워크 층은 시험대를 참조할 수 없다.

## 4. 직접 설정 수단 3가지

| 수단 | 위치 | 하는 일 | 시작 batch |
|---|---|---|---|
| 앱 안 설정 패널 | 시험대 모듈 전용 창 `testbed.panel` | 메뉴·명령·창·독·아이콘·테마·글꼴·문구를 실행 중 등록 API(`Add`·`Remove`·변경 알림)로 바꾼다. 프레임워크 공개 API 만 호출하므로 패널 자체가 실행 중 변경 계약의 시험이다. | B15 |
| 시나리오 JSON | `testbed/scenarios/*.json` | `{ "menus":[…], "commands":[…], "windows":[…], "icons":[…], "theme":{…}, "fonts":{…}, "strings":{…}, "expect":[…] }` 형식으로 구성을 한 번에 적용하고 기대값을 적는다. | B15 |
| 원격 진단 명령 | 기존 `PD_DIAGNOSTICS` 원격 제어 | `scenario.apply <파일>`·`scenario.dump`·`registry.dump`(메뉴·명령·창·아이콘 등록 목록 JSON)를 더한다. 판정기가 이 명령으로 구성·대조한다. | B15(`registry.dump` 는 B06 부터, 메뉴 목록과 바꾸기 명령은 B07 부터 사용) |

`registry.dump` 와 실행 중 바꾸기 명령(B07 기준, 아래)은 B07 에 열었다. 창 목록은 이후 batch 에서 더한다.

| 명령 | 내용 |
|---|---|
| `registry.dump` | B06 의 아이콘·명령·진단에 더해 `menus` 배열(`id`·`parent`·`kind`·`command`·`automationId`·`owner`·`hidden`·`visible`·`enabled`·`section`)을 낸다. `icons.explicit` 는 내부 `UiIconStore.ExplicitKeys`(명시 등록 키)를 직접 열거한 정렬된 키 문자열 배열이다 |
| `registry.menu.add id= parent= command= [icon=] [title=]` | 실행 중 명령 항목 추가(제목이 없으면 ID). Owner 는 `app`, 응답 `{ok,id,automationId,diagnostics}`(`automationId` 는 `menu.<id>`) |
| `registry.menu.remove id=` | 실행 중 메뉴 항목 제거(앱이 추가한 항목만). 응답 `{ok,id,diagnostics}` |
| `registry.icon.add key= path=` | PathData 아이콘 추가. 응답 `{ok,key,diagnostics}` |
| `registry.icon.remove key=` | 아이콘 제거(앱이 등록한 키만). 응답 `{ok,key,diagnostics}` |

- 응답의 `diagnostics` 는 그 호출 동안 새로 쌓인 진단(`id`·`severity`·`message`·`source`)만 담는다.
- 바꾸기 명령은 시나리오 해석기(B15) 전에도 실행 중 등록·알림·다시 그리기를 확인하는 수단이며, `test/framework/measure/menu_registry_smoke.py` 가 이 명령으로 왕복을 잰다.

- 시나리오 해석기(`ScenarioLoader`)는 **시험대 모듈 안에만** 둔다. 프레임워크 기본 경로에 JSON 해석을 넣지 않는다(a1 M9 기각 결정 유지). AOT 호환을 위해 System.Text.Json 소스 생성 컨텍스트를 쓴다.
- 원격 진단 명령은 제품 빌드에서 빠지는 조건부 기능(`PD_DIAGNOSTICS`)이라 소비 제품에 노출되지 않는다(본문 §9).
- `test/framework/judge/scenario_judge.py` 가 시나리오의 `expect` 와 `registry.dump` 결과를 대조해 rc 로 판정한다.

### 6.1 성능 기준선

- 기준판은 F0 시점 PoC 커밋 `25c31b6` 빌드로 고정한다. 판정은 기준판 대비 중앙값 +5% 이내이고, 기존 절대 기준(PERF-01·05·09·11·12)도 함께 유지한다(본문 §7·§11 결정 9).
- 두 판을 교대로 3회 이상 재고 실제 ms 로 판정한다. 부하 지표로 시행을 무효 처리하지 않고 참고로만 기록한다.
- PC 포그라운드 성능 측정은 사용자가 PC 를 쓰지 않을 때만 한다. PC 사용 중이면 성능 항목만 WAIT 로 두고 다른 항목은 진행한다. Fold5 측정은 PC 비움과 무관하다.

### 6.2 모바일 시험

- Android 시험은 실기기 Fold5 로만 한다(에뮬레이터 금지). 접힌 상태 시험은 기기를 접지 않고 펼친 채 전면(커버) 화면 전환으로 한다.
- 실기기가 연결되지 않았으면 그 항목만 대기로 기록하고 다른 항목은 진행한다.

## 8. 머신 독립 원칙

- 스크립트에 경로·토큰·기기값(시리얼·IP·포트·피드 주소)을 박지 않는다. 저장소 루트(`git rev-parse --show-toplevel`)와 영역 루트를 기준으로 경로를 계산하고, 머신 고유값은 INFRA.md 에서 읽는다. CI 에서는 러너 변수가 같은 값을 준다.
- INFRA.md 에 값이 없으면 스크립트는 추측하지 않고 어느 절·어느 키가 비었는지 알리며 실패한다.
- 기존 시험 스크립트에 박힌 Pd 경로 정리(UTODO-0001)와 충돌하지 않게, `test/framework/` 는 처음부터 이 원칙으로 만든다.
- 사용자는 이전 대상 머신(Windows+WSL, 이미 있음) 정보를 INFRA.md 에 적을 예정이다.
- 이전 리허설: 새 머신에서 `verify_framework.sh` 를 1회 돌려 성능·실입력 묶음을 뺀 전 항목이 통과하는지 본다. B18 전에 하는 사용자 조치로 둔다(a4 Q1·Q2 와 같은 시점).

## 9. CI 연결 (a4 Q2 확정)

- 러너: 에이전트가 실행되는 머신의 로컬 Windows 에 GitLab Runner 를 둔다. executor 는 shell, 동시 실행은 1 이다. 데스크톱·Android 빌드에 필요한 SDK 가 그 머신에 이미 있기 때문이다.
- 빌드 잠금 공유: CI 작업도 `tools/build_lock.sh` 의 같은 잠금을 잡고 빌드한다. 에이전트 빌드와 CI 빌드가 obj 를 동시에 쓰지 않게 하기 위해서다.
- 같은 스크립트: CI 작업은 `verify_framework.sh --ci` 를 부르기만 한다. CI 전용 판정 로직을 따로 두지 않는다.
- CI 밖 항목: 성능 측정과 화면 실입력 시험은 CI 에서 돌리지 않는다. PC 비움 원칙(§6.1)에 따라 로컬에서 한다. Fold5 스모크도 실기기 연결이 필요해 로컬 묶음으로 둔다.
- 머신 이전: 저장소와 INFRA.md 를 옮긴 뒤 새 머신에 러너만 다시 등록한다. 등록 절차·토큰은 INFRA.md 에 적고(사용자 조치), 스크립트는 바꾸지 않는다.
- 정본 원격: xkxk 정본을 서버 GitLab 으로 옮기고 GitHub 는 미러로 둔다(a4 Q1 확정). CI 파이프라인(`.gitlab-ci.yml`)과 게시 작업은 그 이전 뒤 B18 에 만든다. 러너 등록·피드 주소·토큰은 확인 필요(사용자 조치)다.
