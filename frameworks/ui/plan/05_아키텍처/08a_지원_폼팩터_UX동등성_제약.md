## 7. UX 동등성 짝 (REQ-25)

> 원문(2026-10-29 16:44): "윈도우/맥버전과 웹버전의 조작(UX)방식과 아이폰/안드로이드와 모바일기기에서의 웹버전의 조작(UX)방식이 동일하게 동작하여야 한다."

### 7-1. 짝 정의 — §2 9칸 매트릭스 기준

**같은 기기**에서 앱과 웹은 **같은 조작에 같은 결과**를 내야 한다. 짝은 아래 둘이다.

| 짝 | 앱 칸(§2 #) | 웹 칸(§2 #) | 같은 기기 조건 |
|---|---|---|---|
| A. 데스크톱 짝 | #1 Windows(데스크톱), #2 macOS(데스크톱) | #7 웹(데스크톱) — 데스크톱 브라우저 | 같은 데스크톱 기기(같은 OS)에서 앱과 브라우저를 비교한다 |
| B. 모바일 짝 | #3 iOS(태블릿), #4 iOS(모바일), #5 Android(태블릿), #6 Android(모바일) | #8 웹(태블릿), #9 웹(모바일) — 같은 기기의 모바일 브라우저 | iOS(태블릿) 앱 ↔ 그 기기의 브라우저(예 iPad 의 Safari), iOS(모바일) 앱 ↔ 그 기기의 브라우저(예 iPhone 의 Safari), Android(태블릿, 펼친 폴더블 포함) 앱 ↔ 그 기기 Chrome, Android(모바일, 접힌 폴더블 포함) 앱 ↔ 그 기기 Chrome 처럼 **기기·폼팩터·UI 방식이 같은 칸끼리** 짝이다 |

- 짝 사이에 비교하는 조작은 다음과 같다. 마우스 클릭·끌기, 키보드 단축키, 우클릭 메뉴, 도킹 드래그, 패널 분할(UI-20), 크기 조절, 터치 탭·끌기·핀치·길게 누름, 툴팁, 더보기 메뉴, 방식 전환(시스템 메뉴·제목줄)이다.
- 다른 짝끼리(예: 데스크톱 앱 ↔ 모바일 웹)는 이 요구의 대상이 아니다. 폼팩터별 차이(스마트폰 NAV·대화면 3방식, ADR-051)는 §1 규칙을 따른다.
- 판정에서는 웹 축을 짝 앱과 **같은 기대 결과**로 판정한다(판정보고서 §1.3.11 등). 웹 전용 기대값을 따로 두지 않는다. 다만 §7-3 의 '불가능' 항목은 대체 조작 기준으로 판정한다.

### 7-2. 구조 근거 — 앱과 웹이 같은 공용 Shell 코드를 쓴다

- 세 헤드(데스크톱·웹·Android)는 모두 같은 공용 Shell 을 참조한다. 화면·도킹·문서·메뉴·입력 처리(Avalonia 공용 뷰와 Dock 모델)는 이 한 벌의 코드다. PoC 구현의 프로젝트·파일 이름은 `../../poc/ui/README.md` 가 갖는다.
- **분기 기준 규칙.** 화면 동작의 분기 기준은 플랫폼(OS·브라우저 여부)이 아니라 폼팩터와 UI 방식이다. 공용 코드는 플랫폼 판정으로 화면 동작을 가르지 않는다. 앱은 Android·iOS 를 터치 폼팩터로 보고, 웹은 주 포인터가 거친지(`pointer: coarse`)로 판정한다. 플랫폼 분기는 기술 제약(호스트 차이, §7-3)에만 쓴다. 새 플랫폼이나 폼팩터를 더할 때도 이 규칙을 따른다.
- 그래서 같은 입력 이벤트가 들어오면 같은 코드가 같은 결과를 낸다. 동등성이 깨지는 곳은 ① 헤드(호스트)마다 다른 부분과 ② 공용 코드 안의 플랫폼 분기, ③ 입력이 앱에 오기 전에 브라우저·OS 가 가져가는 경우(§7-3)뿐이다.
  - ① 헤드 차이: 데스크톱은 SDI 를 OS 창(HostWindow)으로, 웹·Android 는 관리형 창(앱 화면 안 창)으로 띄운다.
  - ② 공용 코드의 플랫폼 분기: 화면 동작에 닿는 플랫폼 분기(측면 패널 탭 줄 숨김, 화면 방식 메뉴·전환, 좁은 머리줄)는 위 분기 기준 규칙대로 폼팩터 판정으로 가른다. 플랫폼 판정으로 남는 분기는 기술 제약뿐이다. 분기 분류와 PoC 판정 결과는 04/04 `../04_기술스택/04_PoC_UI_판정보고서.md` 와 그 부록이 갖는다.

### 7-3. 브라우저·OS 제약 — 웹이 막을 수 없어 동등성이 불가능하거나 대체 조작이 필요한 것

형식은 '불가능(또는 부분 가능) + 대체 조작 제안'이다. 확인하지 못한 것은 **추정**으로 적었다. 타협 구현으로 덮지 않는다. 대체 조작은 짝 앱에도 똑같이 넣어 짝 사이 결과를 같게 하는 것을 원칙으로 한다.

| # | 대상 | 제약(사실·출처) | 판정 | 대체 조작 제안 |
|---|---|---|---|---|
| 1 | 브라우저 예약 단축키(Ctrl/Cmd+W·T·N, Ctrl+Tab·Ctrl+Shift+Tab, Ctrl+PgUp/PgDn) | Chrome·Safari·Edge 는 브라우저 UI 에 등록된 키의 이벤트를 페이지에 보내지 않는다. 2016년 목록에 Ctrl+N·W·T·PageDown·PageUp·Tab·Shift+Tab 이 있다(https://lists.w3.org/Archives/Public/public-webapps-github/2016Jan/0255.html). Firefox 도 같은 예약을 도입했다(https://bugzil.la/1052569). **현재 Chrome 의 정확한 예약 목록은 공식 문서로 확인하지 못했다(추정: 2016 목록과 같은 계열).** | 불가능 | 앱 단축키 표에서 이 조합을 쓰지 않는다. 문서 닫기·다음 창 같은 기능은 브라우저 비예약 키(예: Ctrl+F4·Ctrl+F6 — 웹에서 실제로 전달되는지 실측 필요)와 메뉴·더보기로 제공하고, 데스크톱 앱도 같은 키를 쓴다 |
| 2 | 전체화면·Esc(F11 포함) | 페이지가 Esc 를 잡으려면 Keyboard Lock API(전체화면 중에만, Chrome 68·Edge 79, Firefox·Safari 미지원)가 필요하다(https://developer.chrome.com/docs/capabilities/web-apis/keyboard-lock). 요소 전체화면은 사용자 활성화(transient activation)가 필요하다(https://docs.w3cub.com/dom/element/requestfullscreen — MDN 미러). iPhone Safari 는 비디오가 아닌 요소의 전체화면을 지원하지 않는다(https://bugs.webkit.org/show_bug.cgi?id=240312). F11 을 페이지가 가로챌 수 있는지는 확인하지 못했다(추정: 불가). | 부분 가능(iPhone 불가) | 앱 '전체화면' 명령(메뉴·버튼, 사용자 탭으로 실행)을 둔다. Esc 는 전체화면 해제에 양보하고, 앱 기능에 Esc 를 단독 키로 쓰지 않는다. iPhone 웹은 전체화면 없이 같은 화면으로 둔다 |
| 3 | 우클릭 메뉴(데스크톱 웹) | `contextmenu` 에서 preventDefault 하면 브라우저 메뉴가 뜨지 않는다(https://developer.mozilla.org/en-US/docs/Web/API/Element/contextmenu_event). 예외로 Firefox 는 Shift+우클릭이면 이벤트 없이 브라우저 메뉴를 띄운다(같은 문서). | 가능(Firefox Shift+우클릭만 예외) | 동등 구현 가능하다. Shift+우클릭은 앱 기능에 쓰지 않는다 |
| 4 | 길게 누름(모바일 웹) | iOS Safari 의 길게 누름 콜아웃·확대경은 `-webkit-touch-callout: none` 로도 막히지 않는다는 보고가 있다(https://developer.apple.com/forums/thread/808606 — iOS 26.1, https://bugs.webkit.org/show_bug.cgi?id=231161). 같은 버그 글은 touchstart preventDefault 가 효과가 있었다고 적는다(공식 보장 아님). `contextmenu` 는 길게 누름 경로가 아니다(MDN 위 문서). | 부분 가능(iOS 보장 없음) | 길게 누름에만 기능을 두지 않는다. 같은 기능을 더보기(…)·▾ 메뉴 버튼에도 둔다(앱도 동일). 앱 캔버스의 touchstart 처리로 콜아웃 억제를 시도하고 iOS 실기로 확인한다(현재 iOS 실기 없음, §3) |
| 5 | 브라우저 확대(핀치·Ctrl+휠) | iOS 10 이후 Safari 는 `user-scalable=no`·max-scale 을 무시해 페이지 핀치 확대를 막을 수 없다(https://webkit.org/?p=7367). Chrome 은 트랙패드 핀치를 ctrlKey=true wheel 이벤트로 보내고 preventDefault 로 페이지 확대를 막을 수 있었다는 기록이 있다(https://bugzilla.mozilla.org/show_bug.cgi?id=1052253 — 2014, **현재 동작은 확인하지 못함(추정)**). | iOS 불가, 데스크톱·Android 부분 가능(추정) | 앱 핀치 확대(UI-18)는 문서 창 안에서만 동작시키고, 브라우저 확대가 일어나도 레이아웃이 깨지지 않게 둔다. iOS 웹에서 앱 핀치와 브라우저 확대가 겹치는지는 iOS 실기로 확인한다. 확대·축소는 Ctrl+휠·핀치 외에 메뉴·버튼(+/−)으로도 제공한다(앱도 동일) |
| 6 | iOS Safari 가장자리 스와이프 뒤로가기 | 페이지 수준에서 끌 공식 방법이 없다. iOS 13.4 이후 touchstart preventDefault 로 일부 막을 수 있지만, 페이지가 스크롤 중이면 기본 동작이 이긴다(https://pqina.nl/blog/blocking-navigation-gestures-on-ios-13-4/, https://lists.w3.org/Archives/Public/public-webapps-github/2025May/0270.html). 홈 화면 웹 앱도 끌 수 없다(같은 W3C 글). 네이티브(WKWebView·UIKit)만 끌 수 있다. | 불가능 | 화면 가장자리(좌우 약 20pt — 수치는 추정)에서 시작하는 앱 끌기(도킹 드래그·패널 분할·분할선)를 두지 않는다. 가장자리 분할선은 안쪽 손잡이로 잡게 한다. 뒤로가기가 일어나도 상태를 잃지 않게 자동 저장을 유지한다 |
| 7 | 주소창 접힘·가상 키보드로 바뀌는 viewport | 모바일 브라우저는 주소창이 나타나고 접힘에 따라 보이는 높이가 바뀐다. CSS 는 svh·lvh·dvh 로 구분하고, 옛 vh 는 lvh 와 같다(https://blog.openreplay.com/understanding-dynamic-viewport-units-css/ — 2차 출처, MDN 표는 직접 확인 못 함). Chrome 108 부터 Android 가상 키보드는 기본으로 visual viewport 만 줄이고, `interactive-widget` 메타로 바꿀 수 있다(https://developer.chrome.com/blog/viewport-resize-behavior). 주소창 접힘 자체를 페이지가 막는 방법은 확인하지 못했다(추정: 불가). | 불가능(높이 변화 자체) | 앱은 높이 변화를 정상 상황으로 처리한다. 스마트폰 규칙 판정은 폭 기준이라 높이 변화로 방식이 바뀌지 않게 한다(폭 기준은 08 §1-3). 입력칸이 키보드에 가리면 보이는 영역으로 스크롤한다. 앱 쪽은 같은 기기에서 키보드 표시 때 같은 처리(가림 방지)를 기대 결과로 둔다 |
| 8 | 파일 시스템 | `showOpenFilePicker()` 는 Baseline 이 아니고 HTTPS 에서만 된다(https://developer.mozilla.org/en-US/docs/Web/API/window/showOpenFilePicker). Chrome·Edge 86 부터 지원하고 Firefox·Safari 는 미지원이다(https://web.dev/articles/files/open-one-or-multiple-files). | 부분 가능(Chromium 만) | 열기·저장은 `<input type=file>`(올리기)·내려받기로 통일한다. 로그 폴더 열기 같은 OS 폴더 동작은 웹에서 '내려받기'로 대체한다. 앱도 같은 메뉴 이름·순서를 쓰고, 결과만 플랫폼 방식(폴더 열기/내려받기)으로 다르다 |
| 9 | 여러 창(SDI·멀티 모니터) | `window.resizeTo()` 는 `window.open()` 으로 만든 창이 아니면 크기를 바꿀 수 없다(https://developer.mozilla.org/en-US/docs/Web/API/Window/resizeTo). Window Management API 는 실험 기능이고 여러 모니터를 덮는 단일 창을 주지 않는다(https://developer.mozilla.org/en-US/docs/Web/API/Window_Management_API). 판정보고서 §3.5 와 같은 근거다. | 불가능(OS 창) | SDI 는 관리형 창(앱 화면 안 창)으로 대체한다. 모니터 최대화는 브라우저 전체화면으로 대체한다(§3.5 N/A). 창 메뉴 항목의 이름·순서는 데스크톱 앱과 같게 두고 동작 차이만 문서화한다 |
| 10 | 툴팁(터치) | 브라우저 제약이 아니다. 터치 뒤 툴팁 잔류는 앱 쪽 동작으로 막는다(마지막 입력이 터치면 툴팁을 열지 않는다). | 가능 | 앱·웹 공통 코드로 같은 동작을 낸다 |
| 11 | 로컬 캐시 보존(사진·첨부·대용량 콘텐츠, ADR-050) | 웹의 Cache API·IndexedDB 는 출처 단위 할당량을 함께 쓰고, 기본은 최선 노력 모드라 저장 공간이 부족하면 LRU 로 출처 데이터 전체가 지워진다.
