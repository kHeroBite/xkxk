## 1. 축 3개 — 섞어 쓰지 않는다

플랫폼, 폼팩터, UI 방식은 서로 다른 축이다. "모바일", "태블릿" 같은 말이 축을 넘나들며 쓰여 혼선이 생겼다. 그래서 축마다 정본 용어를 따로 둔다. 화면 동작의 분기 기준은 플랫폼이 아니라 폼팩터와 UI 방식이다(규칙 본문은 `08a_지원_폼팩터_UX동등성_제약.md` §7-2).

| 축 | 질문 | 정본 값 | 정하는 것 |
|---|---|---|---|
| ① 플랫폼(OS) | 어디서 도는가 | **Windows · macOS · iOS · Android · 웹** | 빌드 대상, 배포 경로, OS 기능(트레이·창 크롬·알림) |
| ② 폼팩터 | 어떤 크기의 장치인가(제조사 구분이 아니다) | **데스크톱 · 태블릿 · 모바일** | 기본 UI 방식, 입력 방식(마우스·터치) |
| ③ UI 방식 | 화면을 어떤 방식으로 그리는가 | **MDI · DOCK · NAV** (호칭은 §8) | 대화면 3방식 전환과 스마트폰 NAV 규칙(ADR-051) |

### 1-1. ① 플랫폼(OS)
- **Windows**: Windows 데스크톱 앱이다.
- **macOS**: macOS 데스크톱 앱이다. "맥"은 구어로만 쓰고, 문서에서는 macOS 로 쓴다.
- **iOS**: iPhone·iPad 앱이다. iPadOS 를 따로 나누지 않고 iOS 에 포함한다. 폼팩터 축에서 iPad=태블릿, iPhone=모바일로 가른다.
- **Android**: Android 폰·태블릿·폴더블 앱이다.
- **웹**: 브라우저에서 도는 WebAssembly 판이다(PoC 프로젝트 `xkxk.frameworks.ui.browser`). 데스크톱·태블릿·모바일 브라우저를 모두 대상으로 한다.

### 1-2. ② 폼팩터
- **정의(사용자 지시 2026-10-31, 2026-11-08 개정):** 폼팩터는 제조사 구분이 아니라 크기 구분이다. 다만 접속 기기를 판별할 때는 크기만 쓰지 않고 기기 정보를 함께 쓴다(사용자 지시 2026-11-08 \"화면크기만으로 구분하면 안될것 같다. 좀더 기기의 정보를 상세히 확인하고 대응되어야 할 것 같다.\"). 판별 입력은 '크기+기기 정보'이고 판정표는 §1-3 이다. **스마트폰**은 바형 스마트폰을 뜻하며, '바형 스마트폰'이라고 따로 쓰지 않는다. **태블릿**은 별도 분류이고 폴드형을 포함한다. 폴드형을 펼친 상태는 태블릿이고, 접은 상태는 스마트폰(모바일)이다.
- **스마트폰과 모바일은 같은 말**이고 둘 다 쓸 수 있다. 스마트폰은 폼팩터 값 '모바일'의 정식 동의어다. 이 문서의 값 이름은 일괄 치환하지 않는다.
- **데스크톱**: 마우스·키보드를 쓰는 PC 화면이다. Windows·macOS 앱과 PC 브라우저의 웹이 여기에 든다. 웹에 한해 사용자 원문 표현 "PC"를 같은 뜻으로 인정한다(웹(PC) = 웹·데스크톱 폼팩터).
- **태블릿**: 짧은 변 폭 **600dp 이상**인 터치 장치다. iPad, Android 태블릿, **펼친 폴더블**이 여기에 든다.
- **모바일**: 짧은 변 폭 **600dp 미만**인 터치 장치다. 스마트폰과 **접힌 폴더블**이 여기에 든다.
- 폴더블은 별도 폼팩터가 아니다. 상태에 따라 **펼침=태블릿, 접힘=모바일**이다. Fold5 실측 폭은 접힘 약 401dp, 펼침 약 805dp 다(ADR-041 영향 항).
- 600dp 경계는 ADR-041 결정 1의 판정 기준과 같고, 셸의 단일 문서 전환 기준(`ui.layout.compact_width_dp`, §1-3)과도 같다. 스마트폰 규칙으로 바뀌는 폭 기준도 600dp 이고, 판단은 앱 창의 실제 폭으로 한다(ADR-051). 폼팩터 정의(짧은 변)와 전환 판단(앱 창 폭)의 차이는 §9-4 에 적었다.

### 1-3. ③ UI 방식 (ADR-051, 사용자 결정 2026-10-31)
- 기존 태블릿모드·폰모드 축을 없애고 '방식' 한 축으로 합쳤다(§9-2 결정 16). 값은 **MDI·DOCK·NAV** 이고 호칭은 §8 을 따른다.
- **대화면 규칙:** Windows·macOS·태블릿(펼친 폴드 포함)과 그 브라우저는 3방식을 모두 쓰고, 실행 중 재시작 없이 전환한다. 기본 방식은 데스크톱(Windows·macOS 앱, 웹(PC))이 MDI, 태블릿·펼친 폴드가 DOCK 이다. 전환 수단은 시스템 메뉴와 제목줄이다.
- **기기별 기본·선택(사용자 지시 2026-11-01, 2026-11-08 개정):** 접속 기기는 크기(기기 화면의 짧은 변)와 기기 정보를 함께 보고 판정한다. 기기 정보는 아래 판정표의 입력이다. 크기만으로 구분하지 않는다(사용자 지시 2026-11-08, §1-2). 기본 골격은 터치이고 짧은 변 600dp 이상이면 태블릿, 미만이면 스마트폰, 터치가 아니면 데스크톱이며, 판정표의 기기 정보가 이를 보정한다. 접은 폴드는 모바일형, 펼친 폴드와 태블릿은 태블릿형이다(사용자 지시 2026-10-31, 2026-11-08 재확인). 옵션 화면 방식은 자동·PC형·태블릿형·모바일형이다. 데스크톱은 PC형이 기본이며 '자동'은 PC형을 뜻하고 나머지 둘도 고를 수 있다. 태블릿은 태블릿형이 기본이고 PC형·모바일형을 고를 수 있다. 스마트폰은 모바일형만 되고 선택 UI 가 없다.
- **자동 전환:** 자동이면 앱 창 폭이 바뀔 때 데스크톱은 폭이 넓은 쪽 경계(`ui.layout.expanded_width_dp`) 이상 PC형, 600dp 이상 그 경계 미만 태블릿형, 600dp 미만 모바일형으로, 태블릿은 600dp 이상 태블릿형, 미만 모바일형으로 바꾼다. 경계 떨림을 막으려고 히스테리시스(`ui.layout.switch_hysteresis_dp` — 내려갈 때는 경계 미만, 올라갈 때는 경계에 이 값을 더한 폭 이상)와 디바운스(`ui.layout.switch_debounce_ms`)를 둔다. 전환은 페이드(`ui.layout.switch_fade_ms`)로 부드럽게 하고, OS 의 애니메이션 줄이기 설정이면 즉시 바꾼다. 수동으로 고른 방식은 폭과 무관하게 유지한다. 넓은 쪽 경계의 기본값은 Android 창 크기 등급(medium 600~839, expanded 840 이상, https://developer.android.com/develop/ui/views/layout/window-size-classes)에서 가져왔다. 데스크톱의 중간 단계(태블릿형)는 계획 판단이다. 재시작 뒤 방식별 레이아웃 복원(결정 2)은 이번 범위 밖이다. 600dp 는 제품 상수다(키 `ui.layout.compact_width_dp`, 근거 §9-2 결정 8·REQ-46-8). 이 항목의 키 다섯은 이름이 후보이고, 선언(값 꼴·기본값·값 분류·허용 층)은 `../10_API설계/plt_2.md` §12.1 이 갖는다.
- **스마트폰 규칙:** NAV 만 쓴다. 이 규칙으로의 전환은 자동으로만 한다. 넓은 기기에서 직접 고르는 기능(UI-19)은 없애고 대화면 NAV 로 대체한다(§9-2 결정 17).
- **NAV 2종:** 대화면 NAV 의 메뉴는 좌측과 상단에 둔다. 스마트폰 NAV 의 주 메뉴는 상·하단에 둔다(탐색기 서랍은 허용).
- **옛 이름:** 태블릿모드·폰모드·태블릿/폰 전환 스위치는 이력 문서와 현재 PoC 코드 설명에만 남긴다. 폰모드는 스마트폰 NAV 의 옛 이름이다. 'PC 모드'라는 말은 계속 쓰지 않는다(ADR-041).

#### 1-3-1. 기기 판별표 (사용자 지시 2026-11-08, 판별 입력은 '크기+기기 정보')
기기 분류(Classify)는 기기 기준이고, 자동 적용 형(Resolve)은 그 분류 위에서 앱 창 폭 규칙을 적용한 결과다. 순서는 수동 선택 유지 > 기기 분류(폰이면 모바일형 강제) > 자동이면 폭 규칙(히스테리시스 32dp)이다. '자율 판단'은 사용자 지시가 없어 원칙(기기별 기본 규칙, 옵션화 대원칙, 정보가 없으면 크기 폴백)으로 정한 항목이며 사용자가 바꾸면 고친다.

## 3. iOS·macOS 지원 근거 (외부 확인)

- **공식 지원 플랫폼:** Avalonia 문서 "What is Avalonia"는 Avalonia 12 문서이며("These docs cover Avalonia 12"), 지원 대상으로 Windows 10·11, macOS(Apple Silicon·Intel), iOS·Android, WebAssembly 를 나열한다. 출처: https://docs.avaloniaui.net/docs/overview/what-is-avalonia (2026-10-29 확인).
- **지원 등급(Supported platforms):** 출처는 https://docs.avaloniaui.net/docs/supported-platforms (2026-10-29 확인)다. 이 페이지가 Avalonia 12 전용이라고 명시하지는 않는다. 다만 12.1.0 내용과 'Avalonia 12 breaking changes' 링크가 있어 12 기준으로 본다[추정]. 등급은 메이저 릴리스마다 다시 정한다고 적혀 있다.
  - Windows: Tier 1 은 Windows 11 24H2, Tier 2 는 Windows 11 22H2·Windows 10 22H2 다.
  - macOS: Tier 1 은 macOS 26, Tier 2 는 macOS 15·14 다(ARM64·x64).
  - iOS/iPadOS: Tier 1 은 26, Tier 2 는 18.x, Tier 3 은 17.x 이하다. 최소 .NET 10.0 이다.
  - Android: Tier 1 은 Android 16(API 36), Tier 2 는 Android 12~15(API 31~35)다. 최소 .NET 10.0 이다.
  - 브라우저: 등급 없음, 최소 .NET 8.0 이다. "WebAssembly 를 지원하는 모든 브라우저"라고만 적혀 있고 브라우저별 최소 버전은 없다.
- **iOS 빌드 요건:** 공식 iOS 가이드는 "On a Mac you will need to have the latest version of macOS and Xcode installed."라고 적는다. 다른 OS 에서 빌드는 할 수 있지만 **실행·시험에는 Mac 이 필요하다.** 워크로드는 `dotnet workload install ios` 다. 출처: https://docs.avaloniaui.net/docs/platform-specific-guides/ios (2026-10-29 확인). 배포(.ipa)에는 Mac·Xcode·Apple Developer Program·프로비저닝 프로필이 필요하다. 출처: https://docs.avaloniaui.net/docs/deployment/ios (검색 결과 요약으로 확인, 본문 직접 열람은 하지 않았다).
- **macOS 빌드 요건:** macOS 앱 서명·공증에 Mac 이 필요한지는 이번에 **확인하지 못했다**. iOS 와 같은 Mac 장비 확보 과제로 함께 다룬다[추정].
- **우리 환경:** 개발 PC(WSL2·Windows)에는 워크로드 android·ios·maccatalyst 가 설치돼 있다(INFRA.md 64행). Mac 장비는 없다. 따라서 매트릭스 2·3·4번 칸(macOS·iOS)은 **Mac 장비를 확보하기 전에는 실측할 수 없다.** 장비 확보는 결정 대기 사항으로 남긴다.

## 4. 문구 규칙 (짧게)

- 플랫폼과 폼팩터를 함께 말할 때는 "플랫폼(폼팩터)" 순서로 쓴다. 예: Android(태블릿), 웹(모바일), iOS(모바일). 사용자 지시 원문의 표기 순서와 같다.
- "모바일"만 단독으로 쓰면 폼팩터를 뜻한다. 플랫폼 묶음(iOS+Android)을 말할 때는 "iOS·Android"로 쓰고, 설치형 앱 형태를 말할 때는 "모바일 앱"으로 쓴다.
- UI 방식은 "MDI/DOCK/NAV"로 쓴다(같은 뜻의 호칭은 §8). 폼팩터 "태블릿/모바일"과 섞지 않는다. 태블릿 폼팩터도 앱 창이 좁아지면 자동으로 스마트폰 NAV 를 쓴다(REQ-46-8).

## 8. UI 3방식 호칭 (사용자 지시 2026-10-31)

각 묶음의 단어는 모두 같은 뜻이다.

| # | 같은 뜻의 호칭 | 뜻 |
|---|---|---|
| 1 | **MDI = PC형 = 자유형 = 플로팅** | 창을 자유롭게 띄우고 배치하는 방식이다. 앱 창 밖 독립 창(SDI)도 포함한다(ADR-051) |
| 2 | **DOCK = 태블릿형 = 작업공간형 = 도킹 = 독형 = 독방식 = 패널형 = 서랍형** | 상·하·좌·우 패널과 가운데 문서 탭 방식이다 |
| 3 | **NAV = 모바일형 = 폰형 = 탐색형 = 메뉴형 = 사이드바** | 왼쪽 메뉴와 오른쪽 콘텐츠 방식이다. 스마트폰 NAV 는 하단 아이콘 탭과 상단 삼선 메뉴(06 모바일 §2) |
| 4 | **패널 = 독 = 서랍** (사용자 지시 2026-10-31) | 상·하·좌·우 어느 위치의 영역이든 부르는 호칭이다. 지금 왼쪽 탐색기 영역은 그 예시다. UI 방식이 아니다 |

- 4번 원문은 "왼쪽 현재 탐색기 영역에 대한 용어도 패널/독/서랍 모두 가능하게 하자"이고, 이어서 "아니.. 내가 말한 왼쪽독은 예제로 말한거다 상하좌우 모두 독이다"라고 바로잡았다.
- 2번의 독형·독방식·패널형·서랍형은 사용자 지시(2026-10-31)로 더했다. 원문은 "레이아웃 용어중 dock에 독형 독방식 패널형 서랃형 도 추가하라"이고, '서랃형'은 '서랍형'의 오타다(사용자 확인 2026-10-31).
- 2번 뜻풀이는 처음에 '좌·우·하단'이었다. 상·하·좌·우로 고쳤고, 패널·서랍도 상하좌우에 적용한다(사용자 확인 2026-10-31).
- '패널·독·서랍'은 상·하·좌·우 영역 호칭이고, '패널형·독형·독방식·서랍형'은 DOCK 방식 호칭이다. Dock 12.1.0.12 는 라이브러리 이름이다.
- 1~3번의 PC형·태블릿형·모바일형·폰형은 사용자 지시(2026-11-01)로 더했다. 원문은 \"용어정리중 mdi형에 pc형을 추가하고 dock형에 테블릿형을 추가하고 nav형에 폰형, 모바일형을 추가하자.\"이다. '형'은 방식 호칭이고 기기(폼팩터)가 아니다. 예를 들어 PC 에서 태블릿형을 고를 수 있다.
- 이 호칭은 스마트폰 메뉴 위치(REQ-46-10)나 왼쪽 겹침 서랍의 허용 여부를 정하지 않는다. 그 둘은 §9-2 결정 11 이 정한다.
- 세 방식의 호칭 모두 단일 공식 표준은 아니다.
- 도킹 안에서 패널 하나를 떼는 동작은 '분리'라고 부른다.
- 1~3번 호칭은 §1-3 UI 방식 축의 값이다(ADR-051).
- REQ-17·MDI-01~26 등 기존 'MDI'는 본문을 고치지 않고 위 1번 묶음의 MDI 로 읽는다[§9-2 결정 15·16 에서 도출].

> 2026-11-01 사용자 지시로 결정 9(PC 앱도 '자동'이면 폭에 따라 전환)와 결정 12 일부(스마트폰 NAV 는 하단 아이콘 탭 몇 개와 상단 삼선 메뉴)를 정했다. 규칙은 §1-3 이고 결정은 ADR-051 개정(2026-11-01)에 있다.

### 9-3. 기존 규정과의 관계

§1-3·§2·§4·§5·§7(현재 08a) 은 위 결정에 맞춰 고쳤다. UI-18·UI-19·D-42·ADR-041 의 화면 모드 부분은 ADR-051 로 대체했고, 핀치와 측면 패널 단일 탭은 그대로다. 원문과 기존 ADR 본문은 이력으로 보존한다. 합격 기준·판정보고서·`poc/ui` 는 아직 옛 UI 모드 기준이다.

**왼쪽 겹침 서랍:** 현행 PoC 폰모드는 ☰ 로 여는 왼쪽 겹침 서랍에 탐색기를 넣는다(구현 자리는 `poc/ui/README.md`). 결정 11 로 탐색기 서랍은 허용한다. 주 메뉴는 상·하단에 둔다.

**스마트폰 배치 후보:** `09_화면설계/05_모바일_PMS앱_비교조사.md` 의 하단 5탭 권장안(122행)은 '상·하' 조건에 맞는 후보다. 다만 Mars 와의 연속성(5탭, MAUI Shell)을 전제로 한 사용자 검증 전 제안이다(118행). 확정이 아니다. 배분은 결정 12 의 통일성 대상 앱 조사 뒤 정한다.

### 9-4. 남은 확인

**후속 절차(사용자 결정):**
- 결정 3: 재시작 뒤 스크롤 복원은 PoC 확인 뒤 결정한다.
- 결정 9: PC 앱도 '자동'이면 창 폭에 따라 전환한다(§1-3).
- 결정 12: 스마트폰 NAV 는 하단 아이콘 탭 + 상단 삼선 메뉴 구조다(§1-3). 하단 아이콘 탭의 개수·배분은 통일성 대상 앱(§9-2 결정 13) 조사 뒤 결정하며, 이 일은 향후 과제 목록(`../90_결정관리/03a_향후과제_TODO_2.md`)에 등재해 추적한다.

**결정 문면에서 도출되지 않아 따로 정한 것:**
- PC 브라우저와 태블릿 브라우저의 기본값 구분: 접속 기기가 기준이다(터치 여부와 짧은 변, §1-3). 입력 판정은 `(pointer: coarse)` 를 쓴다(§7-2 D-UX1).
- 화면 방식 선택 문구: ko 화면 방식 ▸ 자동/PC형/태블릿형/모바일형, en Auto/PC layout/Tablet layout/Mobile layout.
- 스마트폰 가로 회전(D-198): 기기 판정은 짧은 변이므로 가로로 돌려 폭이 600dp 이상이어도 짧은 변이 600dp 미만이면 스마트폰 규칙(모바일형)을 유지한다. 회사·사용자 옵션(`ui.layout.phone_landscape_keeps_mobile`)이고 이 동작(켬)이 기본값(후보)이다(ADR-089).
- 패널 분할(UI-20)의 적용 범위(D-198): DOCK 의 상·하·좌·우 패널과 MDI 의 도킹 패널에 적용하고 NAV(대화면·스마트폰)는 제외한다. 상단 패널도 같은 규칙이다. 근거는 §8 '패널 = 상·하·좌·우 영역'과 UI-20 원문의 모바일 제외다. 회사·사용자 옵션(`ui.layout.panel_split_scope`)이고 이 범위가 기본값(후보)이다(ADR-089).
- 방식 전환·창 좁힘 때 분리된 SDI 창의 처리(D-198): 대화면 방식 전환(MDI·DOCK·NAV) 때 SDI 창은 그대로 유지한다. 스마트폰 규칙(창 폭 600dp 미만)으로 바뀔 때만 메인 창 문서로 되돌리고, 다시 넓어지면 SDI 위치를 복원한다. 근거는 REQ-46-6·7(상태 유지)과 결정 15(SDI 의 소속)다. 회사·사용자 옵션(`ui.layout.sdi_on_compact`)이고 이 동작이 기본값(후보)이다(ADR-089). ADR-051 PoC 확인 항목 6 은 그대로 남는다.
- 위 세 옵션의 키 이름은 후보다. 선언(값 꼴·기본값·값 분류·허용 층)은 §1-3 의 `ui.layout.*` 키와 함께 `../10_API설계/plt_2.md` §12.1 이 갖고, 키 등록부(`../06_기능목록/20_Pd_상세기능설계_공통_권한_화면.md` §5.1)는 그 선언에서 만든다.
