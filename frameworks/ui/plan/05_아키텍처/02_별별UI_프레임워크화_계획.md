## 1. 배경·질문

사용자는 별별UI(`xkxk.frameworks.ui`)를 여러 솔루션이 호출·활용해 프런트엔드 UI 를 쉽게 만드는 프레임워크로 바꾸려 한다. 원문 질문과 이 문서의 답 위치는 아래와 같다.

| 원문 | 질문 | 답 위치 |
|---|---|---|
| 5 | 가능한가, 장단점·문제점은 무엇인가 | §2 |
| 5.1 | API 호출과 라이브러리 참조 중 가장 효율적이고 성능이 떨어지지 않는 방법은 | §3·§4·§7 |
| 5.2 | 메뉴 생성 API·창 내용 전달·함수 포인터·파라미터 전달 등 방법론을 모두 조사해 최선을 고르라 | §3, 부록 a1 |
| 5.3 | 별별UI 자신도 그 프레임워크로 구성하고 시험하라 | §8 |
| 5.4 | 메뉴·독·창 아이콘·글꼴·색 등 대부분을 솔루션이 커스터마이징한다 | §5 |
| 5.5 | 표준 방법으로 연결돼 변경이 모든 솔루션에 자동 배포·적용된다 | §6 |
| 5.6 | 로딩·UI 성능을 포기하지 않는다 | §7 |
| 5.7 | 공수가 길어도 원칙적이고 모든 경우에 대응하는 설계 | §4·§9·§10 |
| 5.8 | 계획만 세우고 구현 결정은 사용자가 한다 | §11 |

## 2. 가능 여부 판정

**판정: 가능하다.** 다만 지금 소스는 "PoC 앱 하나"를 전제로 짜여 있어 공개 API 를 새로 세우는 구조 공사가 필요하다(코드 사실은 부록 a2).

- 가능 근거(코드 확인): 층이 이미 프로젝트로 나뉘어 있다(`xkxk.frameworks.ui`·`.data`·`.shell`·`.views` + 호스트 `.desktop`·`.browser`·`.android`, 규칙 `tools/check_layers.py`). 셸이 화면 층을 모른 채 쓰는 계약 `IViewRegistry` 와 호스트 주입점(`App.LayoutStore`·`SettingsStore`·`CreateHostWindow`·`WindowHost` 등)이 있다. Avalonia 12.1.4 하나로 데스크톱·웹(WASM)·Android 를 같은 코드로 그린다.
- 막는 것(코드 확인): 정적 전역 상태(`App.MainViewModel`·`App.Shell`·`UiSettings.Current`·`ViewRegistry.Current`·`Loc.Instance` 등), 메뉴가 axaml 에 고정(`views/Menus/*.axaml`), 문서 종류가 열거형 3개(`DocumentKind` Grid·Gantt·Form)와 데모 문서(`PocDocument`)에 묶임, 다국어 사전이 셸 어셈블리에 내장, 웹 호스트가 패치판 Avalonia.Browser(`12.1.4-pd.1`, `vendor/feed`)에 의존, 화면 층이 차트 패키지 4종과 ClosedXML 을 직접 참조한다.

| 구분 | 내용 |
|---|---|
| 장점 | 화면 규칙(MDI·SDI·독·스냅·테마·움직임 효과·성능 조정)을 솔루션마다 다시 만들지 않는다. 한 곳에서 고친 결함·개선이 모든 솔루션에 퍼진다. 시험 자산(판정기·성능 측정)을 공유한다. 사용자 경험이 제품군 전체에서 같아진다. |
| 단점 | 공개 API 를 한 번 내면 바꾸기 어렵다(호환성 비용). 솔루션이 프레임워크의 서드파티 버전(Avalonia·Dock·ProDataGrid)에 끌려간다. 프레임워크 결함이 모든 솔루션에 동시에 퍼진다. 초기 공수가 크다(§10 추정 23~31주). |
| 문제점 | "자동 배포·반영"은 빌드·배포 단계까지만 자동화할 수 있고, 이미 설치된 실행 파일을 런타임에 바꾸는 방식은 AOT·WASM 제약으로 기본 경로가 될 수 없다(§6). 정적 전역 상태 제거는 회귀 위험이 크다(§9). |

## 4. 권장안

**한 줄 요약: 층별 NuGet 패키지(저장소 안은 ProjectReference)로 전달하고, 호스트 빌더·모듈 계약(`IUiModule`)에 강타입 명령·델리게이트·뷰모델-뷰 등록을 하는 것을 기본 API 로 하며, 선언형 매니페스트 + 소스 생성기는 선택 계층으로 둔다.**

근거는 다섯 가지다.
1. 성능: 연결이 전부 컴파일 때 정해진다. 실행 때 파싱·리플렉션·직렬화·프로세스 경계가 없어서 메뉴·창 열기 비용이 지금 PoC 의 직접 호출과 같은 수준이다(§7).
2. 다중 호스트: 정적 링크라 트리밍·AOT·WASM 에서 그대로 동작한다. 동적 로드 계열은 이 조건을 못 맞춘다(§3).
3. 버전 호환: NuGet 은 SemVer 2.0 을 따르고(https://learn.microsoft.com/en-us/nuget/concepts/package-versioning), 패키지 검증이 이전 버전 대비 호환성 깨짐을 pack 때 검출한다(https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview).
4. 커스터마이징: 모듈 계약은 "프레임워크가 기본값을 갖고 솔루션이 덮어쓴다"는 옵션화 원칙(plan/README.md Pd 8)과 맞는다.
5. 표준성: .NET 생태계의 표준 배포 단위(NuGet)·표준 의존 갱신 도구(Renovate 등)를 그대로 쓴다(§6).

### 4.2 공개 API 표면(B02 골격 확정, 이후 batch 는 같은 원칙으로 추가)

설계 원칙은 `/mnt/c/DATA/Project/xkxk/docs/standards/02_공개API_호환원칙.md`(UADR-0009)의 8원칙이다. 요지는 확장 자리를 미리 열고, 새 기능·파라미터는 기본값 있는 옵션 속성이나 오버로드로만 더하며, 선택 파라미터는 공개 API 에 쓰지 않는 것이다.

B02 에 실제로 생기는 형식은 셸 `src/xkxk.frameworks.ui.shell/Framework/`(네임스페이스 `xkxk.frameworks.ui.shell.Framework`)에 있다.

| 형식 | 역할 |
|---|---|
| `XkxkUi` | 진입점. `CreateBuilder()`·`(string[])`·`(XkxkUiBuilderOptions)` 3 오버로드 |
| `XkxkUiBuilderOptions` | 빌더 옵션 객체(Args·ApplicationId·HostKind·ErrorPolicy·Properties). 새 옵션은 속성 추가로만 더한다 |
| `XkxkUiBuilder`·`XkxkUiApplication` | 빌더(`AddModule`·`ConfigureServices`·`Build`)와 결과 앱. 생성자는 internal 이라 소비자가 만들지 못한다 |
| `UiModule` | 소비자가 상속하는 추상 기반. 뒤 batch 는 기본 구현 있는 virtual 멤버만 더한다 |
| `IUiModule` | 동결 인터페이스(`Id`·`Configure` 2개). 멤버 추가 금지, 소비자는 직접 구현하지 않는다 |
| `IUiModuleContext`·`IUiServiceProvider` | 프레임워크만 구현하는 계약. 소비자 구현 금지, 멤버 추가 허용 |
| `UiServiceRegistry` | 서비스 등록부(Add·Replace·Remove, 팩토리 지연 1회) |
| `UiDiagnostics`·`UiDiagnostic`·`UiDiagnosticIds`·`UiDiagnosticSeverity` | 등록 규칙 위반을 모으는 진단. 코드 XKUI0001~0003·0101 |
| `UiErrorPolicy`·`UiHostKinds`·`UiConfigurationException` | 오류 정책(Collect·Throw)·호스트 종류 문자열 상수·구성 예외 |
| `XkxkUiAppBuilderExtensions` | `UseXkxkUi` — 유일한 Avalonia 의존 파일 |

## 6. 배포와 자동 반영

"자동 반영"이 기술적으로 어디까지 되는지 단계별로 정직하게 적는다.

| 단계 | 방식 | 자동인 것 | 자동이 아닌 것 |
|---|---|---|---|
| L0 저장소 안 앱 | M1 ProjectReference | 커밋 즉시 다음 빌드에 반영 | 각 앱 재빌드·재배포 |
| L1 저장소 밖 솔루션(권장) | 사내 NuGet 피드 + SemVer + 중앙 버전 관리(`Directory.Packages.props`) + lock file + 갱신 봇 | 새 버전 게시 → 솔루션마다 갱신 MR 자동 생성 → CI 시험 통과 시 자동 병합(선택) | 주 버전(깨짐) 병합, 솔루션 배포, 설치된 실행 파일 교체 |
| L2 부동 버전(`1.*`) | restore 때 범위 안 최신 안정판 선택 | 다음 restore 의 버전 상승 | 재현성. lock file 이 있으면 강제 재평가 전에는 올라가지 않는다 |
| L3 실행 중 교체 | 플러그인 동적 로드 | — | AOT·WASM 에서 불가(§3) — 채택하지 않는다 |

- 근거: 중앙 버전 관리는 `ManagePackageVersionsCentrally` 와 전이 고정(`CentralPackageTransitivePinningEnabled`)을 제공한다(https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management). lock file 의 locked mode 는 목록과 다르면 restore 를 실패시키고, 부동 버전은 `--force-evaluate` 없이 올라가지 않는다(https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files). NuGet 은 버전·범위를 항상 지정하라고 권한다(https://learn.microsoft.com/en-us/nuget/concepts/package-versioning).
- 갱신 봇: Renovate 는 NuGet(`.csproj`·`Directory.Packages.props`·`global.json`)과 GitLab 을 지원하고 `automerge` 옵션이 있다(https://docs.renovatebot.com/modules/manager/nuget/ , https://docs.renovatebot.com/modules/platform/gitlab/ , https://docs.renovatebot.com/configuration-options/#automerge). Dependabot 은 GitLab 지원을 문서에서 찾지 못했다. 2026-11-26 기준 xkxk 저장소 원격은 GitHub(origin) 하나이고, 패키지 피드는 서버 GitLab 패키지 레지스트리로 정했다(결정 4). GitLab 은 게시를 프로젝트 단위 엔드포인트로만 받는다(https://docs.gitlab.com/user/packages/nuget_repository/). 그래서 xkxk 정본 원격을 서버 GitLab 으로 옮기고 GitHub 는 미러로 두기로 확정했다(a4 Q1, Pd 와 같은 구성). 이전은 B18 전에 사용자 조치와 함께 하고, 피드 주소·토큰은 사용자가 INFRA.md 에 적는다. 이전 뒤 갱신 봇은 Renovate 를 후보로 둔다. 사설 NuGet 피드 연결 방법은 확인 필요다.
- CI 실행 위치(a4 Q2 확정): 에이전트가 실행되는 머신의 로컬 Windows 에 GitLab Runner(executor shell, 동시 실행 1)를 설치해 돌린다. CI 는 에이전트와 같은 빌드 잠금을 쓰고, CI 와 로컬 일괄 실행기는 같은 스크립트를 쓴다. 경로·토큰·기기값은 INFRA.md 와 러너 변수에서 읽는다. 성능 측정과 화면 실입력 시험은 CI 밖에서 PC 비움 원칙으로 한다. 프로젝트를 다른 머신으로 옮기면 그 머신에 러너만 다시 등록한다(절차는 INFRA.md, 사용자 조치).
- 버전 정책: 패키지는 SemVer 2.0, `AssemblyVersion` 은 주 버전만 올린다(https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning). 깨지는 변경은 주 버전에만 넣고, 그 전 부 버전에서 `[Obsolete]` 경고를 한 번 거친다. 소스·바이너리·동작 깨짐 정의는 https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/breaking-changes 를 따른다.
- 호환 검사(CI 게이트, UADR-0009): ① 공개 API 목록 고정 — PublicApiAnalyzers 5.6.0(`PublicAPI.Shipped.txt`·`Unshipped.txt`)(https://github.com/dotnet/roslyn-analyzers/blob/main/src/PublicApiAnalyzers/PublicApiAnalyzers.Help.md). **시작은 B02** 이고 셸 `Framework/` 에만 건다. RS0016·RS0026·RS0027 은 소스 위치에 보고되므로 `.editorconfig` 경로 한정 error 로, RS0017·RS0037 은 txt 위치에 보고되므로 셸 csproj `WarningsAsErrors` 로 error 를 건다. 전 라이브러리 확대는 B16 이다. 이 저장소가 2026-11-12 보관 처리됐다는 안내가 있어 후속 배포 위치는 확인 필요다. ② 표면 검사 `test/framework/judge/api_surface_check.py`(B02) — txt 의 Shipped·Unshipped 줄이 base(기본 HEAD)에서 삭제·변경되면 FAIL 이고 허용은 명시 플래그뿐이다. 한계는 B02~B20 의 계약이 모두 Unshipped 라 삭제·변경이 txt 수정과 플래그로 드러나는 수준이고, base=HEAD 비교는 커밋 전 변경만 잡는다는 점이다. ③ `EnablePackageValidation` + `PackageValidationBaselineVersion` 은 비교할 이전 게시판 nupkg 가 있어야 하므로 **baseline 은 첫 pack 인 B17 부터**다. 의도한 깨짐은 `CompatibilitySuppressions.xml` 로 리뷰한다.
- 서드파티 전이: 솔루션은 프레임워크가 정한 Avalonia·Dock·ProDataGrid 버전을 따라야 한다. 웹 호스트의 패치판 Avalonia.Browser(`12.1.4-pd.1`)는 같은 사내 피드로 함께 배포해야 한다(§11 결정 12).

## 7. 성능

원칙: 프레임워크 경계가 비용을 더하지 않는다. 연결은 컴파일 때, 생성은 처음 쓸 때(지연), 실행 중 리플렉션·파싱·직렬화는 기본 경로에서 쓰지 않는다.

| 데스크톱 첫 화면 | PERF-01 ≤ 2000ms, 실측 대부분 1.00~1.57초(`../04_기술스택/04_판정보고서_부록/a9_성능_웹_모바일_4_5_6.x.md`) | ≤ 2000ms 그리고 지금 PoC 대비 중앙값 +5% 이내(후보) | 기존 기동 perf.json, 두 판 교대 3회 이상 |

- 판정은 실제 ms 로 하고, 성능 측정은 사용자가 PC 를 쓰지 않을 때 한다(기존 측정 원칙). 목표의 "후보"는 F0 에서 사용자가 확정한다.

## 8. 시험대와 검증

상세 설계는 부록 a3(`02_별별UI_프레임워크화_계획_부록/a3_시험대_검증계획.md`)가 정본이다. 여기에는 요지만 둔다.

- 직접 설정: 앱 안 설정 패널, 시나리오 JSON, 원격 진단 명령 세 가지로 메뉴·명령·창·독·아이콘·테마·글꼴·문구를 바꿔 시험한다(REQ-121).
- 외부 소비 모사: 최소 소비자 앱이 로컬 피드(B17)·사내 피드(B18)에서 `restore` 해 빌드한다.
- 검증: 계약 시험·레이어 검사·기존 판정기·시나리오 판정·공개 API 고정·패키지 검증·AOT 경고 0·3호스트 스모크·성능 회귀(+5%)를 `test/framework/` 스크립트로 묶는다. 항목별 시작 batch 는 a3 검증 표에 있다.

|---|---|---|
| 정적 전역 상태 제거(부록 a2 §3) | 넓은 회귀 | 앱 컨텍스트 한 개로 모으고 정적 접근자는 한 부 버전 동안 위임으로 남긴 뒤 제거. 단계마다 기존 판정기 전수 |
| 문서 종류 개방(`DocumentKind` → 문자열 ID) | 레이아웃 저장본 호환 깨짐 | 저장 형식 버전 올림 + 옛 값 읽기 변환 |
| 공개 API 조기 확정 | 나중 변경 비용 | 1.0 전까지 `0.x` 로 내고, 시험 앱·첫 솔루션 두 소비자로 검증한 뒤 1.0 |
| 서드파티 버전 전이 | 솔루션이 Avalonia 등 버전 선택권을 잃음 | 지원 범위 표를 패키지와 함께 배포, 주 버전 때만 올림 |
| 패치판 Avalonia.Browser | 사내 피드 없으면 웹 소비자 빌드 불가 | 피드 동봉 또는 원본 복귀(결정 12) |
| 자동 반영의 한계(§6) | "모든 솔루션 즉시 반영" 기대와 차이 | 갱신 MR·자동 병합까지로 정의하고 배포는 솔루션 몫으로 명시 |
| 소스 생성기 유지 비용 | 생성기 결함이 빌드 실패로 퍼짐 | 선택 계층으로만 두고 기본 API 만으로 모든 기능 가능하게 |
| 진단 원격 제어 노출 | 보안 | 제품 빌드 제외(`PD_DIAGNOSTICS`) 유지, 패키지 분리 |
| 공수 장기화 | 다른 개발 지연 | 단계마다 동작하는 상태로 끝내고(§10), 중간 중단해도 이득이 남게 순서 배치 |

## 10. 단계별 로드맵

공수는 1인 기준 주 단위 추정이다(근거: 지금 소스 규모 약 89,500줄·셸 361 파일, 부록 a2 §1). 각 단계 끝에 기존 판정기·성능 측정을 다시 돌린다.

| 단계 | 내용 | 공수(추정) | 끝 조건 |
|---|---|---|---|
| F0 | 결정(§11)·공개 API 초안 리뷰·성능 기준 확정 | 1주 | 사용자 승인 |
| F1 | 정적 전역 상태 → 앱 컨텍스트, 호스트 빌더 골격 | 3~4주 | 기존 판정기 회귀 0 |
| F2 | 명령·메뉴·아이콘 레지스트리, 셸 4메뉴를 레지스트리로 이관 | 3주 | 메뉴 회귀 0, 메뉴 열기 측정 |
| F3 | 창·문서 종류 개방, 데모 문서를 시험 앱 모듈로 이동, 저장 형식 이전 | 4~5주 | 저장본 이전 시험 |
| F4 | 테마·글꼴·문구·설정·독 확장점 | 2~3주 | 커스터마이징 시험 |
| F5 | 패키지 분리·버전 정책·CI 게이트(API 고정·패키지 검증·AOT 경고 0) | 2~3주 | 로컬 피드 소비자 빌드 |
| F6 | 자체 시험 앱 3호스트 완성·성능 예산 판정 | 3~4주 | §7 예산 통과 |
| F7 | (선택) 선언형 매니페스트 + 소스 생성기 | 3~4주 | 생성 코드 = 손 코드 동등 |
| F8 | 첫 외부 솔루션 시범 적용 | 2주 | 소비자 피드백 반영 |

- 합계 추정 23~31주(F7 포함, 제외 시 20~27주). 확인되지 않은 공수이며 F1 실측 뒤 다시 잡는다.
- 실행 순서는 F0→F1→…→F6→F8→F7(1.0 뒤)이고, 23개 batch(B01~B23)로 나눴다(부록 a4). F5 패키지 분리는 F4 뒤라는 원래 순서를 지킨다.
- 시험대 작업 배치: 시험대 모듈 신설과 데모 문서·차트·엑셀 이동은 B10, 호스트 공통 코드를 `src/xkxk.frameworks.ui.hosting.*` 로 소스만 분리하고 실행 호스트를 `testbed/` 로 옮기는 일은 B11(a4 Q3 확정, 패키지화는 F5)이다. 설정 패널·시나리오 JSON·원격 명령은 B15, 최소 소비자 앱은 B17, 3호스트 완성과 검증 일괄 실행기는 B19 다.
- ohoops 알림: F5 에서 첫 사전판(0.x)을 사내 피드에 게시하고 피드 소비 시험이 통과한 시점, 곧 B18 끝에 사용자에게 "ohoops UI 개발 가능"을 알린다(UTODO-0025).
