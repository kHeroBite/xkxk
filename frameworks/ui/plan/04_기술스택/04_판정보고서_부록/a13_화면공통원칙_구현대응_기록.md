### 4.1 옛 §2-1 제목 줄 규칙 (33~44행)

##### (옛) 2-1. 제목 줄 규칙 (사용자 지시 2026-11-02)
- **크기(사용자 지시 2026-11-07 — 이전 설계값의 2/3 로 축소)**: 제목 줄 높이 19 DIP, 제목 탭 높이 16 DIP, 제목 탭 글자 12(줄 높이 14 고정, 세로 가운데). 값은 고치기 전 빌드의 실측 높이 × 2/3 를 반올림한 것이고 설계값(28·24) 기준으로 19·16 이다. 닫기 ×·SDI 아이콘(16)은 제목 줄 19 안에 들어가야 한다. 메뉴 줄 32 DIP 는 바꾸지 않는다(OS 캡션 기준, 05_창크롬 문서).
- **제목 줄 높이 설정(사용자 지시 2026-11-11 "탭 줄 높이가 너무 낮다, 2배 정도로", 위 19·16 을 대체):** 제목 줄 높이는 설정 ▸ 모양의 '탭 줄 높이'(`UiSettings.ShellTabStripHeight`, 저장 키 같은 이름)로 정한다. 기본 38 DIP(19 의 2배), 범위 19~48 이다. 제목 탭 높이는 줄 높이 × 16/19 를 반올림한 값이라 기본 32 다. 탭 글자는 시스템 글자 토큰 `PdFontCaption`(기본 12)을 따른다(§5.2 시스템 글자). 데스크톱·웹 같다.
- **제목 탭 폭**: 자연 폭을 72~240 DIP 로 자른다. 합계가 가용 폭(오른쪽 SDI 아이콘 칸 제외)을 넘으면 모든 탭에 같은 상한 `max(72, 가용폭/탭 수)` 를 적용한다(짧은 제목은 자연 폭 유지). 72 에서도 넘치면 2px 얇은 스크롤(U4)이다. 잘린 제목은 말줄임(…)으로 표시하고 툴팁에 전체 제목을 보인다. 활성 탭만 넓히지 않는다(탭 위치가 흔들림). 순수 계산은 UI 와 분리한다(`TitleTabWidth`).
- **조사 근거**: Chrome 표준 탭 폭 232 DIP·비활성 최소 16 DIP([tab_style.cc](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/tabs/tab_style.cc)), Windows Terminal `tabWidthMode` 기본 균등([Microsoft Learn](https://learn.microsoft.com/el-gr/windows/terminal/customize-settings/appearance)), VS Code `workbench.editor.tabSizing` fit·shrink·fixed([PR 181729](https://github.com/microsoft/vscode/pull/181729)), Firefox `browser.tabs.tabMinWidth` 기본 76px(공식 문서 미확인, [ghacks](https://www.ghacks.net/?p=39522)). 공통점은 ① 상한을 둔다 ② 부족하면 같은 비율로 줄인다 ③ 하한에서 스크롤한다 ④ 말줄임+툴팁이다. 72·240 은 이 값을 반올림한 Pd 판단값이며 토큰(`PdTitleTabMinWidth`·`PdTitleTabMaxWidth`)으로 둔다. Visual Studio·JetBrains 는 공식 근거를 찾지 못해 쓰지 않았다.
- **툴팁**: 모든 제목 탭은 전체 제목(프로젝트가 있으면 "제목 — 프로젝트")을 툴팁으로 보인다.
- **독립 창(SDI) 아이콘**: 떠 있는 독립 창은 제목 탭에 두지 않고 제목 줄 오른쪽 끝의 작은 아이콘(16 DIP)으로 보인다. 활성은 강조 바탕, 비활성은 투명, 최소화는 흐린 글리프다. 툴팁은 창 이름(문서 2개 이상이면 "활성 제목 외 N"), 클릭하면 그 창을 활성화하고 최소화 상태면 복원한다. 아이콘 수는 독립 창 수와 같다.
- **구현 상태(conv_179371711303):** 위 규격(제목 줄 19·제목 탭 16·폭 72~240·SDI 아이콘 16·DOCK 숨김)은 설계 정본이고 이번 사이클 Batch 2 에서 구현 중이다. 폭 계산 `TitleTabWidth`·`TitleTabPanel` 은 Pd.Ui/Controls 층에 둔다(Shell 참조 불가, 층 검사 `check_layers`). 시험 값(높이·폭·말줄임·아이콘 수·활성 색)은 측정 대기다. 문서 영역에 제목 탭과 같은 이름의 탭을 중복해 보이지 않는다(태블릿형, E4).
- **제목 탭 닫기 × 표시 옵션(사용자 지시 2026-11-12)**: 설정 `TitleTabCloseMode`(열거 `Always`·`Hover`·`ActiveAndHover`·`Auto`, 기본 `Auto`). `Always` 는 모든 탭에 ×, `Hover` 는 마우스를 올린 탭에만, `ActiveAndHover` 는 활성 탭과 마우스를 올린 탭에만 보인다. `Auto` 는 마우스 기기면 `Hover`, 터치 기기면 `Always` 로 동작한다. × 는 제목 끝 위에 겹쳐 그리고 그 아래 제목 글자를 흐리게 한다(× 가 나타나거나 사라져도 글자는 밀리지 않는다). × 가 숨겨진 탭은 그 자리를 제목에 돌려줘 제목이 더 길게 보인다(말줄임 위치만 달라지고 탭 폭은 그대로다). 키보드 포커스가 탭에 있으면 모드와 상관없이 그 탭의 × 를 보인다. 가운데(휠) 클릭은 × 가 숨겨져 있어도 그 탭을 닫는다. 숨김 시 접근성 이름의 닫기 동작은 유지한다.
- **DOCK(태블릿형)**: 가운데 문서 탭이 목록을 맡으므로 제목 줄의 제목 탭을 숨긴다. 독립 창이 있으면 제목 줄은 아이콘만 남고, 없으면 줄 자체를 숨긴다. NAV 는 기존대로 제목 줄이 없다.
- **타이틀바 오른쪽 배치(사용자 지시 2026-11-07)**: 메뉴 줄 오른쪽은 `[자동][PC형][태블릿형][모바일형] [테마 아이콘] [_][□][X]` 순서다. 테마 아이콘은 최소화 버튼 바로 왼쪽에 두고, 그 바로 왼쪽에 UI 방식 아이콘 4칸이 온다. 캡션 버튼이 없는 웹·Android 는 테마 아이콘이 오른쪽 끝이다. 5개 모두 직접 그린 벡터 아이콘(U10)이고 이름은 툴팁과 접근성 이름으로 보인다. 테마 아이콘은 지금 어두우면 해, 밝으면 달 그림이며 누르면 라이트·다크가 바뀐다. 메뉴 줄 아래 별도 도구모음 줄(라이트/다크 스위치·설정 버튼)은 두지 않는다. 설정은 시스템(Y) ▸ 설정으로 연다. 오른쪽 도구 폭이 늘어난 만큼 셸 메뉴는 더보기로 일찍 접힌다.
- **UI 방식 스위치**: 메뉴 줄 스위치는 [자동]·PC형·태블릿형·모바일형 4칸(아이콘)이다. [자동]을 켜면 자동 판정 칸이 옅은 강조(강조색 1px 테두리+옅은 바탕)로 표시된다. 창 폭 840/600 DIP 규칙(08 용어 §1-3, 히스테리시스·디바운스 포함)으로 PC형·태블릿형·모바일형이 자동 전환된다. 자동 상태에서도 PC형·태블릿형·모바일형 칸은 눌리며, 누르면 한 번에 자동이 풀리고 그 방식으로 전환된다(사용자 지시 2026-11-04). 칸이 비활성이 되는 경우는 기기가 허용하지 않을 때뿐이다(폰은 모바일형만 허용, 스위치 숨김). 자동 상태에서 [자동]을 다시 누르면 자동을 끄고 현재 판정 형을 수동 선택으로 저장해 화면이 바뀌지 않는다.

### 4.2 옛 §4.1 출처 줄·§4.2 창 크롬 (68행, 70~100행)

- 출처 확인(Microsoft Learn 창 관리·MDI 단축키, Apple HIG)은 `05_창크롬_OS디자인_기준.md` 에 기록한다(odev-ux 담당, 이번 사이클 시험 중).

##### (옛) 4.2 창 크롬
- 창 스타일은 3종이다. **Windows 11**(기본)·**macOS**·**클래식**. '클래식'은 옛 'Mars 클래식'의 표시 이름이다(U2). 수치(모서리·외곽선·그림자·제목줄 높이)는 `05_창크롬_OS디자인_기준.md` 를 따른다.
- 캡션 버튼은 글자 글리프가 아니라 직접 만든 벡터 아이콘이다(U10, 외부 저작권 아이콘 복사 금지). 호버·누름·켜짐 표현은 아래 크롬 버튼 상태 표를 따른다(사용자 지시 2026-11-05, 이전 U6 의 아이콘 색 표현을 대체). 최소화 아이콘은 아래쪽 기준선에 둔다.
- 캡션 버튼 간격은 스타일과 상관없이 좁게 맞춘다(U11). Windows 11 스타일만 넓던 간격을 없앴다.
- 앱 로고는 독립 창(SDI)과 메인 창에만 표시하고 MDI 문서 창에는 두지 않는다(U12, 근거 조사는 05 문서 U12 절).
- 하단 모서리는 바깥 둥근 반경과 내용 영역 반경을 맞춰 창틀 두께를 일정하게 한다. 맞출 수 없는 렌더 경로는 하단 모서리를 각지게 한다(U8).
- 메인 창 제목 줄은 창이 비활성이면 제목 줄 요소 전체를 반투명으로 흐리게 한다(근거 `05_창크롬_OS디자인_기준.md` 22행, Windows 공식 문구는 투명도 수치를 주지 않는다). 구현은 `poc/ui/src/Pd.Ui.Views/MainTitleBar.axaml` 이며 비활성이면 요소에 `PdChromeInactiveOpacity` 를 적용하고 바탕은 `PdBrushMainTitleBarInactive` 로 둔다. 웹과 Android 는 OS 창 활성 개념이 달라 흐리지 않고 활성 바탕을 유지한다.
- 메인 창 타이틀바는 바로 아래 제목 줄과 바탕색으로 구분한다(사용자 지시 2026-11-05, 모든 테마). 전용 토큰 `PdBrushMainTitleBar`(활성)·`PdBrushMainTitleBarInactive`(비활성)·`PdBrushMainTitleText`(글자)를 쓴다. 창 스타일에 따라 표면색이 되는 문서 창 별칭(`PdChrome*`)은 쓰지 않으므로 macOS·클래식 스타일에서도 구분된다. 값은 MDI 제목줄 색을 출발점으로 조정한 PD 설계값이다. 판정 기준은 활성 바탕 대 제목 줄 3.0 이상, 활성 글자 대 바탕 4.5 이상, 비활성 글자(투명도 반영) 대 바탕 3.0 이상, 비활성 바탕 대 제목 줄 1.2 이상이다. 이 수치는 OS 기준 문서에 값이 없어 [WCAG 2.1 SC 1.4.11](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html)·[SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) 을 준용한 임시 기준이고, 비활성 2개는 PD 판단값이다. 판정 도구는 `poc/ui/test/desktop/judge/main_titlebar_contrast.py` 다.
- 문서 창(MDI·SDI) 기능 버튼 7개는 인접 그림 사이 빈 공간을 9px 로 둔다(사용자 지시 2026-11-05, 이전 18px, 버튼 폭 19, 클래식 13). 터치 기기는 인접 버튼을 겹치지 않고는 눌림 영역을 지킬 수 없어 이전 폭(28×32)을 유지한다. 이 폭도 `06_모바일_화면설계.md` 의 잠정 터치 기준(48dp·44pt)보다 작으며, 이 차이는 이번에 고치지 않았다.
- 크롬 버튼 상태 표현은 다음과 같다(사용자 지시 2026-11-11, 2026-11-05 표현을 대체). 호버·누름에는 테두리를 쓰지 않고 바탕색만 바꾼다. 호버 바탕은 메뉴 막대 항목 호버와 같은 토큰이다. 켜짐·꺼짐은 바탕을 바꾸지 않고 기호 색과 불투명도로 구분한다. 대상은 문서 창 기능 단추 줄(MDI·웹 관리형·SDI), 문서 창 캡션 3단추, 메인 제목줄의 테마 단추·UI 형 스위치(A·PC·태블릿·모바일)·최소·최대·닫기다. 전환은 즉시이며 애니메이션은 없다. 값은 테마 토큰이다(별칭 `PdChromeState*`, `Docking/CaptionLayout.cs`).

- UI 형 스위치에서 자동일 때 지금 판정된 칸은 불투명도 1.0 의 쉬는 기호 색이고, 기호 아래에 점(`PdUiAutoDotSize`, 지름 3 DIP, 0 이면 숨김)을 둔다. 1.0 과 꺼짐 0.85 의 차이만으로는 약하다는 시험 지적 때문이다. 선택 칸의 강조색 채움·테두리는 쓰지 않는다.
- 켜짐 표식 점(`PdChromeCheckedDotSize`, 지름 3 DIP)은 **기본값 0 이라 보이지 않는다.** 2026-11-12 시험에서 색·불투명도·1.15배 세 가지 구분으로 충분해 불필요로 판정했다. 모자라는 테마만 토큰으로 켠다.
- 키보드 포커스 링은 제목줄 크롬 단추와 UI 형 스위치 칸에 2px 안쪽 링(제목줄 기호·글자색)으로 그리고, 키보드로 옮긴 포커스(:focus-visible)에서만 보인다(`Themes/FocusVisual.axaml`·`MainTitleBar.axaml`). 강조색 1px 기본 링은 강조색 제목줄에 묻히기 때문이다. 문서 창 크롬 단추는 Focusable 이며 같은 2px 링을 쓴다(2026-11-12, 이전 `Focusable=False` 는 해소). 캡션·스위치 기호의 세로 중심은 맞췄다(차이 0px).
- 판정 기준(초기 제시값)은 켜짐 기호 색 대 제목줄 바탕 3:1 이상, 꺼짐 기호(불투명도 합성 뒤) 대 바탕 3:1 이상이다. 꺼짐 0.75 는 계산 3.37:1 이었지만 다크 문서 제목줄 실측이 2.96:1 로 미달했다(12px 기호 앤티앨리어싱으로 실측 ≈ 계산×0.88). 그래서 0.85(계산 최저 ember 문서 제목줄 3.55:1)로 올렸다. 웹 실측(2026-11-12)은 켜짐 핀 8.4·6.54:1, 꺼짐 잠금 8.02·5.77:1(라이트·다크), UI 형 스위치 선택 칸 노랑 5.49·3.48:1 이다(옛 값 #FFE066 기준 실측 — 2026-11-12 값 변경 후 freeze_b3 실측으로 대체 예정). 2026-11-12 재판정(빌드 전 계산값, 기준 3:1)은 Mars 기호 꺼짐 3.56~3.68:1, pd-contrast 켜짐 기호 노랑 제목줄 11.32:1·항상 위 10.53:1, 호버 바탕 대 제목줄 3.15·3.13:1, 누름 바탕 대 제목줄 3.69·3.67:1(누름 위 흰 기호 5.28·5.65:1), 합류 대상 표시(DockJoinTarget) 검정 글자 대 누름 바탕 3.98·3.72:1 로 모두 3:1 을 넘는다. 이월 기록의 'pd-contrast 켜짐 노랑 1.10' 은 재현되지 않았다. pd-contrast 의 '항상 위' 제목줄 색은 마젠타 #FF00FF 에서 시안 #00E5FF 로 바꿨다(같은 색 위 호버 대비 1.00 문제 해소). 비활성 회색 제목줄(#A0A0A0) 위 호버 대비는 2.72:1 로 3:1 에 못 미쳤으므로(2026-11-12 이월 해소) 비활성 창 전용 호버 바탕 토큰 `PdBrushChromeHoverInactive`(별칭 `PdChromeHoverInactive`)를 둔다. 비활성 창의 캡션 버튼·기능 버튼 호버 바탕은 이 토큰을 쓰고, 활성 창은 기존 호버 토큰을 그대로 쓴다. 내장 테마 7개 전부에 값을 두며(사용자 정의 테마에 키가 없으면 `FillMissing` 이 활성 호버 값으로 채운다), 판정 기준은 비활성 제목줄 바탕 대비 3:1 이상이다. 값 계산(odev-1, WCAG 직접 계산, **비활성 캡션 줄 Opacity 0.75 를 반영한 실효 대비** — 실효 알파 = 알파×0.75, 비활성 제목줄 `PdBrushMdiTitleBarInactive` 위 합성; 라이브 재확인 대기): 내장 테마 7개 전부 이 토큰 값을 새로 정했다. 이전은 옛 호버가 실제로 쓰이던 라이브 실측값이다. pd-light·pd-light-prev(#808080) 1.29→3.29(#D2000000), pd-dark(#4A4D52) 1.52→3.27(#A0FFFFFF), pd-contrast(#A0A0A0) 2.07→3.28(#B2000000), pd-ocean(#8E979E) 1.22→3.25(#B8000000), pd-ember(#4F4038) 1.55→3.28(#94FFFFFF), pd-forest(#969B97) 1.20→3.26(#B6000000). 밝은 제목줄은 검정, 어두운 제목줄은 흰 오버레이다. pd-contrast 는 불투명 #404040 이면 0.75 가 곱해져 2.72 로 돌아가므로 알파 검정(#B2000000)으로 바꿨다(앞서 쓴 #404040·3.965 는 0.75 를 빼고 계산한 값이라 폐기). 기본(Opacity) 방식에서는 단추 줄 흐림 0.75 를 거친 실효값을 기준으로 하며, 비활성 호버 규칙은 항상 로드되는 `ChromeButtonStyles.axaml` 에 둔다. 이전 값이 낮았던 원인은 `ChromeInactive.axaml` 이 브러시 방식일 때만 붙어서, 기본 방식에서는 활성 호버를 0.75 로 흐린 값이 쓰였기 때문이다. 활성 창 호버(`PdChromeHover`)는 그대로다. 별칭은 강조 제목줄일 때만 이 토큰을 쓰고, 표면색 제목줄은 기존 `PdBrushCaptionHover` 를 유지한다. 키는 KeyList 맨 끝(`PdBrushCacheFullOnSurface` 다음)에 둔다.
- 비활성 창은 기존 규칙대로 기호만 흐리게 한다. 꺼짐 불투명도와 곱해져 너무 흐리면 비활성 창에서는 꺼짐 불투명도를 1.0 으로 둔다(캡처로 판단).

- 새로고침 아이콘 색은 캐시 적중률을 나타낸다(0% 은색, 1~99% 연노랑에서 금색, 100% 주황 계열). 강조 띠 위 네 토큰(`PdBrushChromeGlyph`·`PdBrushCacheLow`·`PdBrushCacheHigh`·`PdBrushCacheFull`)과 표면색 제목줄(강조 끔·macOS 스타일) 위 네 토큰(`PdBrushCache*OnSurface`)은 내장 테마에서 각 활성 바탕 대비 3.0 이상으로 둔다. 진한 띠 위에서는 100% 와 높은 적중률의 색 차이가 작아 정확한 값은 툴팁으로 확인한다. 터치 기기는 툴팁을 띄우지 않아 색만 남는 한계가 있다(적중률은 보조 정보라 별도 표시를 두지 않는다).
- 기능 버튼에는 사용 불가(disabled) 상태가 없다(사용 불가는 UI 형 스위치 칸에만 있다). 동기화 버튼은 기본이 켜짐이다. macOS 신호등은 위 표의 대상이 아니다. 판정 기준은 활성·항상 위 바탕에서 상태 간 인접 색 대비 3.0 이상, 비활성 바탕에서 기본↔켜짐 2.0 이상이다. 3.0 은 [WCAG 2.1 SC 1.4.11](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html) 을 준용한 임시 기준이고, 2.0 은 PD 판단값이다(문서 창 비활성 토큰은 Mars 실측 회색이라 바꾸지 않았다). 판정 도구는 `poc/ui/test/desktop/judge/chrome_button_states.py` 다.
- 모든 창은 고도 그림자를 갖는다. 활성 창은 진하게, 비활성 창은 약하게 하고, 최대화 창은 그림자가 없다(판정보고서 §6.2 확정 사항).
- **MDI 문서 창 끌기 중 가벼운 크롬(2026-11-10, D2)** 규칙·옵션·실측은 `01a_화면설계_공통원칙_끌기경량크롬.md` 가 정본이다. 정지 상태 창 크롬 수치는 바뀌지 않는다.

### 4.3 옛 §4.3 위치 고정·자석·끌기 경계·결정 근거 (102~122행)

##### (옛) 4.3 위치 고정·항상 위·자석·Z 순서
- **위치 고정(핀)** 과 **항상 위** 는 별개 버튼·별개 기능이다. 위치 고정 중 최대화·최소화 허용 여부는 Visual Studio 관례를 따른다(사용자 지시 2026-10-28).
- **자석**: 창 이동 때는 창 전체, 크기 조절 때는 끄는 가장자리만 다른 창 가장자리·작업 영역 경계에 붙는다. 켜기/끄기와 범위(px)를 설정하고 저장한다. 위치 고정·최대화 창은 제외한다.
- **MDI 창 끌기 경계**: Windows 창처럼 캔버스 밖으로 밀 수 있고, 다시 끌 수 있는 만큼만 남긴다(`MdiDragLimit`). 잡을 곳(끌 수 있는 제목 구간)은 50 DIP 이상 보여야 하며, 기능 버튼·캡션 버튼만 남고 잡을 곳이 없는 상태는 금지한다. 창이 밀려 기능 버튼 줄이 잡을 곳을 가리면 그 줄을 접어(C안) 잡을 곳을 확보하고, 다시 펼 때는 8 DIP 여유를 둔다(접기·펴기 경계 흔들림 방지). 폭 10% 규칙은 폐지했고 '약 55% 잔존 설계 유지' 판단도 철회했다(2026-11-08). 그 뒤 2026-11-10 사용자 요청으로 잔존 비율을 다시 두며, 잡을 곳 규칙은 비율 계산의 하한으로 남는다(아래 'MDI 창 잔존 비율' 항목). 비율을 끈(0) 상태에서 왼쪽으로 밀 때 예상 잔존은 159 DIP(폭 640 기준, 2026-11-09 실측 확인)이며 막힌 쪽 여백은 실제 배치에서 잰다. 잡을 곳 규칙의 근거는 사용자 결정 2026-11-08 이다. 기능 버튼 줄을 접는 C안은 자율 판단이다. 잡을 곳 최소값은 옵션으로 둔다(옵션화 대원칙 ADR-089, 2026-11-09 자율 판단). 설정 키는 `MdiMinGrabDip`(정수, 단위 DIP, `UiSystemSettings` 소유)이고 기본값은 50, 허용 범위는 50~120 이다. 범위 밖 값은 거부하지 않고 가까운 경계로 맞추며(Clamp, 예 10→50·999→120), 키가 없으면 기본값 50 을 쓴다(옛 설정 파일 하위 호환). 하한 50 은 옵션화 대원칙의 예외다. 법령·보안·데이터 무결성 사유가 아니라 사용자 결정 'MDI 끌기 한계 50px 이상'(2026-11-08)을 지키려는 하한이므로 더 낮게 설정할 수 없다. 상한 120 은 폭 640 창에서도 캡션 버튼 108 DIP 와 함께 남는 폭이 창 폭 절반 아래에 머물도록 잡은 값이다(자율 판단). 접기·펴기 판정과 왼쪽 잔존도 이 값을 따른다(예: 70 이면 잡을 곳 70 DIP 이상). 끌기 한계 자체 시험(`placement.selftest` 의 drag 항목)은 옵션값과 무관한 구조 시험이라 50 으로 고정해 계산한다. 위쪽은 제목 줄이 사라지지 않게 0에서 멈춘다(2026-11-10 에도 유지). 아래쪽은 잔존 비율만큼(비율 0 이면 제목 줄 전체가) 보이는 데까지 밀 수 있다. 크기 조절도 같은 경계를 따르며, 오른쪽·아래쪽 가장자리는 캔버스 밖으로 늘어날 수 있다. 캔버스 밖 부분은 잘려 패널을 덮지 않고 스크롤바도 생기지 않는다. 측면 패널 쪽으로 민 부분도 문서 칸 경계에서 잘리므로, 화면에서는 불투명한 패널 아래로 들어간 것과 같다.
- **MDI 창 잔존 비율(2026-11-10, 사용자 요청, 문서 먼저):** 창을 캔버스 밖이나 측면 패널 쪽으로 밀 때 창 크기의 일정 비율은 남기고 나머지는 가려지게 한다. 설정 키는 `MdiMinVisiblePercent`(정수 %, `UiSystemSettings` 소유, DTO `int? MdiMinVisiblePercent`)이고 기본값은 25, 허용 범위는 0~90 이다. 범위 밖 값은 거부하지 않고 가까운 경계로 맞추며(Clamp, 예 −5→0·95→90), 키가 없으면 기본값 25 를 쓴다(옛 설정 파일 하위 호환). 0 은 비율을 끄는 값이며 이때는 2026-11-08 잡을 곳 규칙만 적용된다.
  - 남기는 양은 축마다 비율과 잡을 곳 규칙 중 큰 값이다. 가로 잔존은 `min(W, max(ceil(W × p), 막힌 폭 + 잡을 곳))`, 아래 잔존은 `min(H, max(ceil(H × p), 제목 줄 아래 끝))` 이다. 왼쪽으로 밀면 오른쪽 끝부터, 오른쪽으로 밀면 왼쪽 끝부터 보인다. 위쪽은 비율과 무관하게 0 에서 멈춘다.
  - 크기 조절(`ClampResize`)도 같은 잔존 계산을 쓴다. 기능 버튼 줄 접기(`ShouldFoldStrip`)는 그대로 두며, 잔존이 이미 '막힌 폭 + 잡을 곳' 보다 크면 접기 조건이 생기지 않는다.
  - 복구 판정(`IsGrabbable`·`PlacementRecovery`)은 바꾸지 않는다. 비율은 끌기 한계이고 복구는 잡을 수 없을 때만 한다. 캔버스가 줄어 비율보다 적게 보이게 된 창도 잡을 곳이 있으면 그대로 둔다.
  - 데스크톱·웹은 같은 Shell 코드라 동작이 같다. 독립 창(SDI)은 OS 창이라 해당하지 않는다.
  - 예상값(계산, 측정 시 확인): 기본 창 640×420, 기본 25% 에서 가로 잔존은 160 DIP 로 지금(159)과 거의 같고, 아래 잔존은 105 DIP 로 지금(제목 줄 33 DIP)보다 늘어난다.
- **결정 근거(§4.3 MDI 끌기 경계·잔존 비율, 2026-11-10, ADR 대신 이 절에 둔다):**
  - 사용자 원문 요지(2026-11-10 19:33): PC형(MDI)에서 MDI 창이 패널 아래나 메인 캔버스 밖으로 나가지 못한다, 예전에 요청했던 것이 회귀했는가, 일정 비율까지는 남기고 나가서 가려질 수 있게 해 달라는 요청이다.
  - 최신 코드 확인 결과 회귀는 아니다. 가로는 2026-11-08 결정(비율 폐지·잡을 곳 50 DIP)대로 이미 크게 나가고, 아래는 제목 줄만 남으며, 위는 0 에서 멈춘다. 사용자가 본 앱이 옛 빌드였을 가능성은 추정이며 확인하지 못했다.
  - 이 요청은 2026-11-08 결정 중 '비율 폐지' 부분만 갱신한다. '잡을 곳 50 DIP 이상, 버튼만 남거나 잡을 곳이 없는 상태 금지' 는 그대로 유지하며 비율 계산의 하한으로 쓴다.
  - 위쪽은 제목 줄을 유지한다(잡을 곳 없는 상태 금지 유지, team-lead 확정 2026-11-10). 위로 밀면 유일한 잡을 곳인 제목 줄이 먼저 사라져 위 금지 조건과 충돌하고, Windows 도 제목 줄을 작업 영역 위로 보내지 않는다. 위쪽 이탈이 필요하면 창 본문을 잡는 다른 잡을 곳이 있어야 하므로 별도 요구로 받는다.
  - 기본 25% 의 근거는 2026-11-09 실측 잔존 159/640 = 24.8% 다. 기본 창의 가로 결과가 지금과 거의 같고, 아래쪽은 '거의 다 사라짐' 이 없어진다. 상한 90 은 창을 최소 10% 는 밀 수 있게 한 값이다(자율 판단). 값은 옵션화 대원칙(ADR-089)에 따라 설정으로 바꾼다.
  - 끌기 경계를 메인 캔버스 전체로 넓혀 창을 패널 위에 그리는 안은 택하지 않았다. Dock 템플릿의 z 순서를 Pd 가 통제하지 못하고, 그림자가 패널 위에 그려질 위험과 웹 다시 그리기 영역이 커질 위험이 있다.
  - ADR 기록은 `plan/90_결정관리` 를 고칠 수 있게 되면 이 절을 출처로 쓴다(HISTORY 이월 후보).
- 프로그램을 닫았다가 다시 열어도 맨 위에 있던 창이 맨 위에 보인다(Z 순서 유지).
- **항상 메인 창 위**(설정, 기본 켬)와 창별 **항상 위**(OS 최상위)는 별개다. 독립 창(SDI)은 OS 소유 관계(owner) 없이 독립 창으로 뜨므로 메인을 최소화해도 그대로 남는다. 설정을 켜면 메인 창을 활성화해도 독립 창과 그 그림자 아래로 들어가 독립 창이 메인 위에 남고, 끄면 클릭한 창이 위로 오는 평범한 형제 창이 된다. 다른 앱 위로 올리는 것은 창별 항상 위뿐이다. 웹은 관리형 창이라 이 설정이 없다(04 웹 W-17).
- 활성 창을 바꿔도 이전 활성 창이 사라지거나 아래 창 내용이 위로 비쳐 그려지면 안 된다(U3, GPU 켬 기준 시험).

### 4.4 옛 §4.4 창 탭 합류·패널 기능·확장 버튼 터치·결정 근거 (130~140행, 147행, 153행, 155~161행)

- **창 탭 합류(2026-11-10, 사용자 요청, 문서 먼저):** 독립 창(SDI)끼리, MDI 창끼리 두 개 이상을 탭으로 묶는다. 끌다 보면 창이 자주 겹치므로 실수로 묶이지 않게 표적 위에 놓을 때만 합친다. 창 배치(스냅)와의 우선순위는 `11_창배치_스냅레이아웃.md` §5 를 따른다.
  1. 끌던 창이 다른 창과 겹치기만 해서는 합쳐지지 않는다.
  2. 합류 표적은 두 가지다. ① 대상 창의 창 아이콘 칸이다. SDI 는 제목 줄 왼쪽 로고이고, MDI 는 로고가 없으므로(U12) 끌기 중에만 대상 창 제목 줄 왼쪽에 나타나는 20×20 '탭으로 합치기' 아이콘(제목 글자를 밀지 않는 겹침 표시)이다. ② 대상 창에 이미 탭 줄이 있으면 그 탭 줄이다(SDI 문서 2개 이상, MDI 탭 묶음 창).
  3. 포인터가 같은 표적 위에 250ms 이상 머문 뒤 놓으면 합친다(패널 합류 `PanelJoinDrag.DwellMs` 250 과 같은 값). 누른 곳에서 8 DIP 이상 움직여야 끌기로 본다(`PanelJoinDrag.MinDragDistance` 와 같은 값).
  4. 끄는 동안 머무는 표적을 강조한다(패널 합류 강조와 같은 계열의 테마 클래스 `pdTabJoinTarget`). 놓기 전까지 창은 지금처럼 움직인다.
     - **아이콘 바꿔 보이기(사용자 지시 2026-11-11):** 합치기 아이콘이 보이는 동안 그 창의 원래 아이콘(MDI 문서 기호·SDI 앱 로고)은 숨긴다. 합치기 아이콘은 원래 아이콘 칸(로고 칸)의 가운데에 놓아 두 아이콘의 중심이 정확히 같다(이전에는 아이콘 자리를 왼쪽 4 DIP·폭 24 로 따로 두어 Windows 스타일 로고 칸(폭 48) 중심과 8 DIP 어긋났다). 로고 칸이 없는 스타일(macOS)은 제목 줄 왼쪽 24 DIP 칸 가운데다. 데스크톱 SDI 제목줄도 로고 칸 안에 같은 20×20 합치기 아이콘을 보인다(이전에는 로고 칸 바탕만 칠했다). 숨김은 불투명도로 하므로 표적 사각형(로고 칸)은 그대로다. 합치기 아이콘 바탕은 활성 제목줄 불투명색(`PdChromeTitleActive`)이며, 끄는 동안 비활성 창 제목줄에 합성되지 않는다(SDI·MDI 공통).
  5. 합치면 끌던 창의 문서(묶음이면 전부)가 대상 창 탭 줄 끝에 붙고 끌던 문서가 활성 탭이 된다. 끌던 창은 닫히고 대상 창의 위치·크기는 그대로다.
  6. 범위는 MDI→MDI(같은 문서 칸)와 SDI→SDI 다. MDI↔SDI 교차 합류는 이번 범위 밖이며 기존 Dock 탭 끌기 안내 표적의 가운데 놓기로 계속 할 수 있다. 탭형(DOCK) 문서 영역과 모바일형은 이미 탭이라 해당하지 않는다.
  7. 탭을 묶음 밖으로 끌어내면 MDI 떠 있는 창이 된다. MDI 묶음에 문서가 1개만 남으면 묶음을 풀어 같은 위치·크기의 보통 MDI 창으로 되돌린다. **분리한 창은 활성 창이 되어 Z 순서 맨 위에 온다(사용자 지시 2026-11-11).** 묶음을 푸는 정리가 남은 문서를 활성화하더라도 그 뒤에 분리한 창을 다시 활성화한다. 항상 위 창 그룹 규칙(§4.2 Z 순서)은 그대로라 항상 위 창보다 위로는 가지 않는다.
  8. 기존 Dock 탭 끌기 안내 표적(가운데 놓기)은 바꾸지 않는다. 명시 표적이라 '겹침만으로 합류' 가 아니다.
  - 데스크톱·웹 동작은 같다(웹 차이는 `04_웹` W-23). 묶음은 레이아웃 저장 형식 Version 5 의 묶음 기록(`Groups`)으로 저장·복원하고, Version 4 이하 저장본은 묶음 없이 읽는다. MDI 탭 묶음 창의 제목·캡션·탭 줄은 `03_데스크톱` §3.1, SDI 합류 화면은 §3.2 에 있다.

- **패널 기능 설정(사용자 지시 2026-11-07):** 설정 ▸ 창 페이지에서 패널 기능을 자동·켬·끔으로 고른다(기본 자동). 자동은 지금 적용된 UI 형이 PC형이면 켬, 태블릿형·모바일형이면 끔이다(형이 자동 전환되면 다시 계산). 끔이면 ① 패널 고정(📌)을 할 수 없고 버튼도 숨기며 ② 창을 끌 때 가운데 분할을 정하는 안내 박스(도킹 표적)를 보이지 않는다. 같은 패널 탭 영역 안의 순서 바꾸기는 막지 않는다. 끔이 숨기는 것은 핀 고정과 화면 분할 안내 UI 뿐이고, 패널 안의 문서를 원하는 위치(문서 영역·창·다른 패널의 탭 영역 가운데 놓기)로 끌어 빼는 것은 끔에서도 된다(방향 분할은 끔에서 하지 않는다. 다른 패널 탭 영역 가운데 놓기 허용은 자율 판단, 근거는 사용자 지시 "off라도 밖으로 뺄수는 있어야 한다"). 앱(데스크톱·Android)과 웹, PC형·태블릿형 모두 같다. 사용자가 직접 고른 켬·끔이 자동보다 우선하고, UI 형이 바뀌면 자동 값을 다시 판정한다. 끔으로 바뀌는 순간 이미 고정된 패널은 고정을 풀고 원래 비율로 돌아가며, 켬으로 돌아와도 자동으로 다시 고정하지 않는다. 저장된 레이아웃에 고정 패널이 있어도 끔이 우선한다. 규칙은 UI 와 분리한 순수 규칙(`PanelFeatureRules`)이 맡는다.

  - 터치 기기(`InputFormFactor.IsTouchDevice`: Android·iOS, 웹은 `(pointer: coarse)`)는 호버가 없어 항상 표시한다. Windows 터치 노트북처럼 터치 기기로 판별되지 않는 환경에서 터치만 쓰면 버튼이 보이지 않고 키보드로만 닿는다.

- **결정 근거(§4.4 창 탭 합류, 2026-11-10, ADR 대신 이 절에 둔다):**
  - 사용자 원문 요지(2026-11-10 19:33): SDI·MDI 모두 창 2개 이상을 겹쳐 탭으로 만들 수 있게 하되, 끌기만으로 겹치면 합쳐지는 방식은 너무 잦아 위험하니 마우스가 특정 영역(창 아이콘)이나 이미 있는 탭 줄 위에 올라갈 때만 탭을 더해 달라는 요청이다.
  - 표적을 창 아이콘 칸과 탭 줄로 한정한 것은 사용자 원문 그대로다. MDI 창은 로고가 없어(U12) 끌기 중에만 보이는 아이콘 칸을 둔다.
  - 머무는 시간 250ms 와 끌기 시작 8 DIP 는 패널 합류 규칙과 같은 값을 써서 합류 조작의 느낌을 하나로 맞춘다(자율 판단).
  - MDI↔SDI 교차 합류를 범위 밖으로 둔 것은 'SDI/MDI 모두' 를 '각 방식 안에서' 로 좁혀 읽은 보수적 해석이다(자율 판단).
  - MDI 탭 묶음 구조는 B안으로 확정했다(선행 검증 S0, 2026-11-10). `MdiTabGroupDock` 은 `DocumentDock` 이면서 `IMdiDocument` 인 형식이고(LayoutMode Tabbed), 탭형 문서 dock 을 MDI 창 하나로 띄워 Dock 기본 탭 줄·탭 끌어내기를 재사용한다. S0 판정 4조건(묶음 창 안 탭 줄 표시, 탭 클릭으로 활성 문서 전환, 탭을 밖으로 끌면 보통 MDI 창, 원격 진단 `placement.state` 정상 응답)이 모두 통과했다(근거 세션 결과 파일(저장소 밖)). A안(묶음 전용 문서가 자식 문서 목록과 자체 탭 줄을 가짐)은 쓰지 않는다. 묶음에 문서가 1개만 남으면 묶음을 풀어 보통 MDI 창으로 되돌리고, 묶음 창 제목 줄은 활성 탭 문서의 제목을 보인다.
  - ADR 기록은 `plan/90_결정관리` 를 고칠 수 있게 되면 이 절을 출처로 쓴다(HISTORY 이월 후보).

### 4.5 옛 §5.2 글자·§5.3 줌·§5.4 수식키+휠·그리드 판단 (188~189행, 194~195행, 198~234행)

**그리드 공통 클래스 판단: 도입(1단계).** 근거는 다음과 같다.

- 그리드 1개를 새로 만들 때 복제할 양이 스타일 32줄, 생성자 연결 약 12줄, 보조 클래스 3개(열 배율·터치 선택·스크롤 합치기)다. 지금 업무 그리드는 1개지만 메뉴 구조의 화면 88개 중 이름만으로 목록형인 화면이 11개 이상이다(이름 키워드 집계라 실제 수는 더 많을 수 있다).
- 장점은 새 화면이 열 정의와 데이터만 쓰면 되고, 휠·줄무늬·터치 결함 수정이 한 곳으로 모이는 것이다. 단점은 상속으로 DataGrid 교체(내장·ProDataGrid) 때 맞출 곳이 하나 늘고 초기화 순서가 바뀌는 것인데, 공개 API 만 쓰고 StyleKeyOverride 로 테마 키를 유지해 줄였다.
- 1단계 범위는 `PdDataGrid`(Pd.Ui.Views/Documents)와 전용 스타일이고 `GridDocumentView` 만 옮겼다. 벤치 화면은 내장·Pro 대조용이라 DataGrid 를 유지하고 휠 조작만 붙였다.
- 하지 않은 것은 두 가지다. 열 정의 공통화는 컴파일 바인딩(`x:DataType`)이 화면별 행 형식에 묶여 있어 미뤘으나, 그리드 10열을 템플릿 열에서 바인딩 없는 경량 텍스트 열(`PdTextColumn`·`GridRowTextColumn`, 미리 계산한 문자열을 직접 대입, 읽기 전용)로 바꾸는 G1 을 구현해 공통화할 길이 열렸다(빌드 3축 rc=0, 근거 세션 결과 파일(저장소 밖)). 효과는 실측했고 미미했다(웜 measure1 p50 90→77ms, 콜드 266→283ms, 열기 elapsed 웜 150→146ms). 열기 시간 30~50% 감소 예상은 틀렸고 원인 가설 X1(셀 실현 비용)은 거의 틀린 것으로 보며, 재분석은 이월한다(근거 세션 결과 파일(저장소 밖)). ListBox 하위 클래스는 부착 속성 `input:DenseList.Enable` 한 줄로 충분해 만들지 않았다. 셀 표시 지연 생성(A7, 2026-11-11): `PdDataGrid` 셀은 `PdCellTemplate`(Pd.Ui.Views/Documents)으로 상시 요소(테두리·뿌리 격자·내용·오른쪽 세로선)만 만들고, 평소 숨은 현재 셀·포커스·오류 표시는 그 의사 클래스가 처음 켜질 때 같은 모양·색 자원 키로 만든다(headless 첫 그리드 열기 개선 568.5→459ms, 펼침 doc 633ms 는 기준 미달이나 사용자 승인 PASS).
- 화면 밖 열 셀 지연 실현(A16, 옵션 `GridDeferOffscreenCells`, 기본 켬, 저장값, 다음에 여는 표부터 반영)은 이렇다. DataGrid 12.1.2 는 열 가상화가 없어 행마다 모든 열의 셀을 만들지만 화면 밖 셀은 숨김으로 두어 템플릿·측정을 건너뛴다(디컴파일 확인). 그래서 열 구조·열 폭·가로 스크롤 범위·선택·키보드 이동은 그대로 두고, 경량 텍스트 열(`PdTextColumn`)의 셀 내용(TextBlock)만 그 셀이 처음 화면에 들어와 셀 템플릿이 적용될 때 만든다. 첫 행은 DataGrid 가 늘 모든 셀을 보이므로 처음부터 만든다. 끄면 예전처럼 모든 셀 내용을 생성 때 만든다. 셀 템플릿이 `PdCellTemplate` 이 아닌 표(진단 대조 등)에는 걸지 않는다.
- 단일 요소 셀(A16, 옵션 `GridCompactCells`, 기본 켬, 저장값, 다음에 여는 표부터 반영)은 세로선 없는 표만 해당한다. 셀 템플릿을 `PdCellChrome` 하나(바탕·테두리를 직접 그리고 셀 내용은 시각 자식으로만 품음)로 만들어 셀당 요소를 4개(Border·Panel·ContentPresenter·내용)에서 2개로 줄인다. 현재 셀·포커스·오류 표시는 지연 생성을 유지하고 모양은 같다(headless 화소 비교 — 열기·현재 셀·포커스·세로·가로 스크롤 차이 0). 근거는 진단 계측(첫 Measure 의 대부분이 보이는 셀 요소의 부착·스타일·측정)과 같은 빌드 대조(첫 Measure 중앙값 296→149ms, headless 참고값·판정 아님)다. 세로선 표는 기존 템플릿을 쓴다. 진단 대조 스위치는 `grid-open=fullcell` 이다. 그리는 셀 글자(K15, 2026-11-17, 옵션 `GridDrawnCellText`, 기본 켬, 저장값, 다음에 여는 표부터 반영, 기본값 정본 `UiSystemSettings.DefaultGridDrawnCellText`)는 단일 요소 셀이 켜진 표의 경량 텍스트 열에만 해당한다. 셀마다 TextBlock 을 만들지 않고 `PdCellChrome` 이 TextLayout 으로 글자를 직접 측정·그려 셀당 요소를 2개에서 1개로 줄인다. 글꼴·크기·굵기·색은 셀 상속값, 여백·말줄임·세로 정렬은 `PdDataGridStyles.axaml` 의 `TextBlock.cell` 스타일 값을 그대로 읽어 쓰고(스타일을 못 읽으면 TextBlock 판으로 돈다), 행 재활용 때 글자를 다시 얻는다. 셀 글자는 셀 자동화 이름(UIA 셀 이름)으로 나가고 진단 트리에는 같은 모양의 TextBlock 노드(drawn=true)로 나온다. 툴팁 열은 반응 영역이 글자 줄에서 칸 전체로 넓어진다. 표 복사(Ctrl+C)는 이 옵션과 무관하게 지금도 빈 값이다(열에 복사용 바인딩이 없음, 별도 과제). 근거는 같은 빌드 대조 화소 비교(데스크톱 13장 — 열기·선택·셀 클릭·세로·가로 스크롤·1만 행 재활용·다크·글자 크기·요소 디자인 gridCell 패딩·굵기·크기·글꼴·되돌리기 — 차이 0, 웹 5장 표 영역 차이 0)다. 진단 대조 스위치는 `grid-open=tbcell`(TextBlock 판)·`grid-open=notext`(글자 없음, 비용 상한 측정)다.
- 문서 뷰 예열과 준비된 표 뷰(A16)는 이렇다. 예열(옵션 `PrewarmViews`, 기본 켬)은 앱 시작 뒤 유휴 1초가 이어지면 표·양식·간트 뷰를 1개씩 화면 밖 호스트(메인 화면 안 높이 0·잘라냄·입력 제외 칸)에 실제 문서 영역 크기로 붙여 측정·배치하고, 화면 밖 비트맵에 한 번 그린 뒤 뗀다. 화면에 붙지 않은 뷰는 테마·스타일이 적용되지 않아 예전 예열(떼어 둔 채 측정)은 첫 표 열기 비용을 줄이지 못했다. 준비된 표 뷰(옵션 `GridViewPool`, 기본 끔 — headless 대조에서 옮겨 붙일 때의 스타일 재적용·렌더 비용이 생성 절감보다 커 켬이 더 느렸다, 2026-11-14 결정)는 예열한 표 뷰를 버리지 않고 1개 보관했다가 다음 표 문서 열기에 그대로 쓰고, 유휴 시간에 다음 1개를 다시 채운다. 보관 뷰는 새로 만든 뷰와 같은 상태(필터 없음·정렬 없음·맨 위·선택 없음)이고, 문서 영역 크기가 다르면 붙일 때 다시 측정한다. 다시 채우기 전의 연속 열기는 일반 경로로 만든다. 다시 채우기는 바쁨 없음·입력 없음 2초·유휴 1초가 이어질 때만 한다. 보관 중에는 뷰 안 자동화 id 앞에 `pool:` 을 붙여 시험 도구가 숨은 뷰를 실제 문서로 잡지 않게 하고, 넘길 때 되돌린다. 옮겨 붙일 때 Avalonia 가 스타일 매칭과 측정을 다시 하므로(템플릿·요소 생성은 재사용) 절감은 생성 비용의 일부다.
- 재검토 조건은 업무 그리드가 3개를 넘어 열 정의 복제가 실제로 늘 때, 또는 그리드 구현을 교체할 때 다시 본다.

### 4.6 옛 §6 권한·요금제 게이팅 (236~239행)

##### (옛) 6. 권한·요금제 게이팅
- 권한은 user < admin(업체관리자) < root(시스템관리자)다(ADR-026). root 전용 화면은 Pd 메뉴에 두지 않고 pd-admin 으로 보낸다(ADR-040).
- 메뉴 R/W 권한(IAM-08)이 없는 화면은 메뉴에서 숨긴다. 요금제가 모자란 화면은 숨기지 않고 **잠금 아이콘**으로 보이며, 누르면 필요한 요금제와 업그레이드 안내(업셀)를 보인다. 요금제·기능 배치는 데이터라 화면 코드에 등급을 쓰지 않는다(ADR-027).
- 개인용 테넌트에는 기업 전용 화면(`메뉴구조.csv` 개인용 열 '—')을 아예 보이지 않는다.

### 4.7 옛 §8 화면 방식 전환·§8-1 투어·§8-2 차트 뷰 (246~269행)

##### (옛) 8. 화면 방식 전환과 상태 유지
- 전환 수단은 시스템 메뉴와 제목줄(보기 ▸ 화면 방식)이다. 선택지는 자동·PC형(MDI)·태블릿형(DOCK)·모바일형(NAV)이고, 기기별 기본·선택 집합은 08 용어 §1-3 을 따른다(PC=PC형 기본, 태블릿=태블릿형 기본, 스마트폰=모바일형만이며 선택 UI 없음). 전환해도 열린 문서·보던 문서·입력 중인 내용·선택·포커스·스크롤(첫 행 기준 1행 이내)을 유지한다(REQ-46-7).
- **자동 전환:** '자동'이면 창 폭에 따라 PC 는 840dp 이상 PC형·600~839dp 태블릿형·미만 모바일형, 태블릿은 600dp 이상 태블릿형·미만 모바일형이다. 히스테리시스 32dp(복귀는 632·872dp 이상)와 디바운스 200ms 로 경계 떨림을 막는다. 수동 선택은 폭과 무관하게 유지한다. 기기 판정은 짧은 변 기준이다.
- **자동 판별 입력(사용자 지시 2026-11-08):** 자동 UI 형은 화면 크기만으로 정하지 않고 기기 정보(터치·정밀 포인터·기기 종류·창 모드)를 더해 정한다. 판정표 정본은 `05_아키텍처/08_지원_폼팩터_용어.md` 이고 여기에는 요약만 둔다. 접은 폴드는 모바일형, 펼친 폴드·태블릿은 태블릿형이다. 새 옵션 `compactWindowKeepsTablet`(좁은 창에서도 태블릿형 유지)은 기본 끔이며, 켜면 창 폭이 600dp 미만이어도 태블릿형을 유지한다(기기 분류는 그대로). **자율 판단:** 분할 화면·창 모드로 창 폭이 600dp 미만이면 모바일형이다(옵션이 끔일 때). **자율 판단:** 정밀 포인터(마우스·터치패드)가 있는 터치 노트북은 PC형이다. **자율 판단:** 웹에서 접힘 상태를 알 수 없으면 창 폭으로 폴백한다.
- **애니메이션:** 급작스럽지 않게 약 300ms(불투명도 1→0.15 약 120ms, 교체, 복귀 약 180ms, 6dp 미끄럼)로 전환한다. OS 애니메이션 줄이기 설정이면 즉시 교체한다. 전환 요청이 겹치면 마지막 1건만 처리하고, 끌기·모달·IME 조합 중이면 끝난 뒤로 미룬다(입력 손실 0).
- 독립 창(SDI)은 MDI 방식에 속한다. 모바일형으로 바꿔도 독립 창을 닫거나 합치지 않고 그대로 두며(데스크톱에만 있고 스마트폰에는 없다), 열린 문서 목록에 '독립 창'으로 표시한다. 방식별 레이아웃의 재시작 뒤 복원은 이번 범위 밖이고 실행 중 왕복 복귀만 한다.
- **서버 재연결 중 화면(결정(P87) 4-③):** 웹·앱 모두 서버 연결이 끊기면 업무 화면을 가리고 `서버 재연결 중` 화면과 자동 재시도만 보인다. 캐시 내용을 대신 보여 주지 않는다(오프라인 모드 없음). 재연결되면 가렸던 화면을 그대로 되돌린다. 재시도 간격·횟수는 설정값이다.
- **'업데이트 확인' 메뉴(결정(P87) 37):** 시스템(Y) 메뉴의 `업데이트 확인`(`05_아키텍처/05_제품구성_시스템메뉴.md` §2 S9)으로 사용자가 수동으로 새 버전을 확인·설치한다.
- **강제 업데이트 로그인 전 화면(결정(P87) 37):** 관리자가 지정한 강제(필수) 업데이트 버전이 현재 클라이언트보다 높으면 실행 시 로그인 화면 전에 업데이트 진행 화면을 보이고 자동으로 업데이트한다. 그 밖에는 강제하지 않는다(Mars 방식). 웹은 새로고침 배너로 대신한다. 화면 공통 규칙 정본은 `../06_기능목록/20_Pd_상세기능설계_공통_권한_화면.md`(연결 끊김 화면·업데이트 확인 메뉴 (P87) 행), 판정은 `../10_API설계/00_공통규약.md` §2 다.

##### (옛) 8-1. 도움말 투어 내용 관리 (요건 6)

투어 단계·단축키·기능 설명은 코드와 분리한 카탈로그(`poc/ui/src/Pd.Poc.Shell/Tour/tour_catalog.json`)와 사전으로 관리한다. 대상은 AutomationId 로 찾고, 없거나 숨었거나 권한·폼팩터가 안 맞는 단계는 건너뛰며 번호를 다시 매긴다. 메인 화면 키 바인딩과 단축키 표는 같은 등록을 쓰고, 기능 레이어의 메뉴 줄은 메뉴 카탈로그에서 만든다. 새 메뉴·버튼이 설명 없이 들어오면 `check_tour_catalog.py` 가 빌드 전에 실패시킨다. 작성 방법은 `poc/ui/README.md` 의 도움말 카탈로그 절을 본다.

##### (옛) 8-2. 차트 뷰 공통 규칙 (U-CV-1~18 확정, REQ-58)

정본은 `08_차트뷰_설계.md`(`Pd:plan/09_화면설계/08_차트뷰_설계.md`)(뷰 카드는 08a·08c)이고 이 절은 요약이다. U-CV-1~18 은 2026-11-05 사용자 답으로 확정됐다(08 §7, D-67~D-84). 아래에 '후보'로 적은 값(코드·배치·수치)만 아직 후보다.

- **뷰 전환 컨트롤:** 같은 데이터를 보는 뷰(간트·타임라인·캘린더·칸반 등)는 한 문서 창 안에서 뷰 종류를 바꿔 본다. 뷰 종류의 저장은 SCH-07 의 `sch.view_config` 확장(`kind` 추가는 후보)이고, 분석 차트는 DSH-01 위젯 설정 스키마를 쓴다(08 §3.2).
- **ViewContext:** 컨트롤 레이어에 프로젝트·조직·기간·기준선·권한 범위를 담은 `ViewContext` 하나를 두고 모든 뷰가 구독한다. 문서 창(MDI) 단위가 기본이고 창 사이 공유는 사용자 옵션 후보다(08 §3.3). 뷰를 바꾸거나 드릴다운해도 `ViewContext` 는 유지한다(08 §3.4).
- **차트 공통 규칙:** 그리기와 입력은 UI 레이어, 뷰 상태·명령·선택 동기화는 컨트롤 레이어, API·읽기 모델·캐시는 데이터 레이어가 맡는다. 차트 라이브러리는 `IChartAdapter` 만 거친다(ADR-047). 시간축 뷰는 같은 시간축 렌더러를 공유한다(ADR-077 확정, 2026-11-06 자율 판단). 분석 차트는 \"n분 전 기준\"(`asOf`)을 표시한다(08 §3.1·3.5).
- **공통 차트·보드 컴포넌트(결정 54·52, ADR-091):** 차트 대부분은 공통 차트 컴포넌트 하나가 `ChartSpec`(설정 JSON)으로 종류·축·시리즈·색·범례·드릴다운·내보내기를 받아 그린다. 뷰마다 새 컴포넌트를 만들지 않고 설정과 파라미터(기간·집계 단위·임계선·색 규칙 등, 개인 > 회사 > 제품 초기값)로 바꾼다. 칸반은 CV-05·CV-28·ISS-09 가 보드 컴포넌트 하나를 같이 쓰고 열 정의·카드 필드·전이 판정만 모듈별 플러그인으로 둔다. 전이 규칙은 서버가 판정한다. 공통이 기본이고 예외는 근거를 적는다(08 §3.11).
- **폼팩터:** 스마트폰은 NAV 고정이고 뷰별 노출은 08 §3.10 표를 따른다(모바일 반영은 06 문서).
- 성능 목표는 전부 추정이며 PoC·M1 실측 뒤 확정한다. 측정은 사용자가 PC 를 쓰지 않을 때만 한다(08 §4).

### 4.8 옛 §9 화면 ID·§10 다국어 (271~278행)

##### (옛) 9. 화면 ID·메뉴 구조
- 화면 ID 는 `SCR-<모듈코드>-NN` 이다. 모듈코드는 기능목록과 같다(`06_기능목록`). 업무 메뉴 그룹은 홈·프로젝트·일정·이슈·공수·근태·재무·영업·수주 전·결재·공유·협업·보고·AI·PMO·조직·인사·개인 설정·설정(업체관리) 순이다(개인 설정은 결정 129, 위치는 초기 제시값).
- 한 화면은 여러 기능을 묶는다. 현행 기능 238건 확정(후보 0) 중 237건은 화면 100개(후보 표시 28개 — DOC 5·화면 ID 후보 5·배치 후보 9·신규 후보 9)에 빠짐없이 한 번씩 배치되고, 화면 없는 기능 AIN-10(홈페이지 위젯)만 `menu_data.py` NO_SCREEN 예외다(`menu_tree.py` 가 누락·중복·예외 모순을 검사한다, 수치 정본은 `02_메뉴구조.md`). 차트뷰 화면 SCR-SCH-04·SCR-DSH-04 와 "분석" 메뉴 그룹은 D-67(U-CV-1)로 도입이 확정됐고 정본은 `08_차트뷰_설계.md` 다.
- 스마트폰 노출은 ○(전체)·△(조회·간단 처리)·✕(대화면 안내) 셋이다. 기준은 ① 현장·이동 중에 쓰는가 ② 넓은 표·간트·설정처럼 대화면이 필요한가 ③ admin·root 관리 화면인가다.

##### (옛) 10. 다국어 (UI-16, ADR-039)
- 화면 문구는 키 기반 내장 사전에서만 가져온다. ko·en 을 함께 만들고 언어를 바꾸면 모든 화면이 즉시 바뀐다. 키 집합은 두 언어가 같아야 한다(`check_i18n.py`).
- 이후 zh·ja 를 더할 수 있게 문구 폭에 여유를 둔다(영어 기준 1.3배 폭을 가정하고 잘림 시험).
