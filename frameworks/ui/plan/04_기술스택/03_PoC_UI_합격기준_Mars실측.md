# PoC UI 합격 기준 — Mars 창 관리 실측 기반

> 상태 설계 정본(ADR-007) · 작성일 2026-10-28 · 판정 결과는 기록 문서 `04_PoC_UI_판정보고서.md` 와 그 부록에 있다 · 관련 ADR-007, ADR-037
> 이 문서는 Pd 데스크톱·웹 창 관리가 Mars 수준 이상인지 판정할 기준을 Mars 소스 실측으로 정한다. 시험 판정 값·판정 지표·측정 규칙·PoC 시험 기준 값의 현행 정본도 이 문서다(§6). 창 동작 규칙의 정본은 화면 설계이고(§2.3), 창 크롬 수치의 정본은 `05_창크롬_OS디자인_기준.md` 다.

## 1. 조사 방법과 범위

- 대상 소스(읽기 전용)는 Mars 데스크톱의 `Mars/0000_메인.cs`(11,426줄), `Mars/1000_MDI공통.cs`(6,339줄), `Mars/util.Form.cs`(1,250줄)이다. `class.Form.cs`·`util.Win32.cs` 에는 `Fn`·`Tp` 메서드가 없음을 확인했다.
- 추출 규칙은 접근 한정자로 시작하는 `Fn*`·`Tp*` 메서드 정의와 `Is*Maximized*` 속성·메서드다(식 본문 위임 오버로드 제외). 결과는 **메서드명 기준 고유 심볼 164개(오버로드 포함 정의 193개)** 이고, 속성 `IsEffectivelyMaximized` 1개를 더해 **165개**다.
- 이 중 창 관리 심볼은 **130개**이며 전부 아래 2장 MDI 항목에 매핑했다. 창 관리와 무관한 35개는 3장에 "제외(사유)"로 적었다. **미매핑 0건**이다(4장 대조 방법).
- 심볼 설명은 소스 주석·본문을 직접 읽어 확인한 내용이다. 확인하지 못한 동작은 "추정"으로 표기했다.

### 1.2 Mars 창 관리의 실측 한계 (Pd 가 넘어야 할 지점)

- **SDI(독립 창)는 창마다 별도 UI 스레드**로 띄운다(`Fn새창열기` 본문의 `new Thread(...)`·`Application.ThreadException` 스레드별 등록 주석). 스레드 간 Invoke 가 필요하고 예외 처리도 스레드마다 따로 해야 한다.
- **의사 최대화**를 쓴다. `IsEffectivelyMaximized` 는 `WindowState==Maximized` 또는 `_isPseudoMaximized` 또는 "MDI 클라이언트를 덮는 크기"면 최대화로 본다. WinForms MDI 최대화의 제약을 우회한 흔적이다.
- 드래그·크기 조절은 타이틀바 마우스 이벤트를 직접 처리한다(`Fn타이틀마우스다운`·`Fn마우스창이동`·`Fn리사이즈페인트`). GDI 다시 그리기로 드래그 지연이 있다는 점은 `05_아키텍처/02_성능_최적화.md` §1 에 적혀 있다(체감 수치는 미검증).
- 핀 고정은 Win32 메시지 가로채기(`Fn핀고정보다아래로유지(ref Message m)`)와 Z-Order 재적용으로 구현했다. 플랫폼 독립이 아니다.
- 화면 캡처 방지는 Win32 `SetWindowDisplayAffinity` 를 쓴다. Windows 전용이다.

## 2. 합격 기준 표 (Mars 심볼 → Pd 항목)

- 등급 must 는 하나라도 FAIL 이면 "조건부" 이하, should 는 FAIL 이어도 대안이 있으면 "합격"을 막지 않는다.
- 검증 방법 표기 중 L0 는 AutomationBridge 인자(`--open`·`--layout`·`--sdi`·`--move-all`·`--save-layout`·`--load-layout`·`--screenshot`·`--perf-out`)와 브라우저 URL 쿼리다. SS 는 스크린샷, PJ 는 perf JSON, 사람은 사람 확인 필요 항목이다.
- 웹 열은 지원 매트릭스(`../05_아키텍처/08_지원_폼팩터_용어.md` §2) #7 칸(웹·데스크톱)에서 같은 기준을 적용하는지다. SDI 는 관리형 창(Dock `DockSettings.UseManagedWindows` 등) 대체를 인정한다. 다른 지원 칸의 판정은 열을 늘리지 않고 §2.4 에 행으로 더한다.
- '판정 대상' 칸은 PoC 판정 때 무엇을 볼지의 요약이다. 창 동작 규칙의 정본은 화면 설계이고 ID 별 정본 절은 §2.3 이다. 요약과 화면 설계가 다르면 화면 설계를 따른다. 값을 바꿀 수 있는 항목의 설정 키도 §2.3 에 적는다.

- **그림자 없음(캡처 범위 안).** 창 밖 여백 4~6px 가 모두 배경색 단일값이다. 다만 캡처 여백이 4~6px 뿐이라 그보다 먼 그림자는 이 캡처로 판정할 수 없다.
- **비활성 창은 측정 불가.** 캡처에 비활성 창이 없다. 소스 기준(`1000_MDI공통.cs` OnPaint)으로 비활성 외곽선은 Gray 를 30% 어둡게 한 색, 여백 띠·제목줄은 Gray 다.
- 앞서 §(판정보고서 3.3)에 적은 "1px ±30% 음영" 측정은 **맞다**. 활성 외곽선 픽셀값이 소스 계산값과 일치한다.

Mars 소스에서 그리는 방식은 다음과 같다.
- `1000_MDI공통.Designer.cs`: `FormBorderStyle = None`, `BackColor = (64,86,141)`, `Padding = (3,4,2,2)` 다. OS 테두리가 없고, 여백 띠는 폼 배경색이 Padding 만큼 드러난 것이다.
- `1000_MDI공통.cs` OnPaint: `DrawRectangle(new Pen(borderColor,1), 0,0,W-1,H-1)` 로 1px 단일색 사각형만 그린다. 활성은 제목줄 색 +30%, 비활성은 Gray −30% 다.
- `CreateParams`: `CS_DROPSHADOW` 를 켠다. 그러나 Microsoft 문서는 이 스타일을 쓰는 창이 "must be top-level windows; they may not be child windows"라고 적는다(https://learn.microsoft.com/en-us/windows/win32/winmsg/window-class-styles). MDI 자식은 자식 창이므로 **MDI 모드에서는 OS 그림자가 나오지 않는다**. 캡처의 그림자 0px 와도 맞는다. SDI(독립 최상위 창)일 때만 OS 그림자가 적용될 수 있다(시스템 설정 SPI_SETDROPSHADOW 에 따름, Mars SDI 캡처로는 미검증).
- Mars 전체에서 `WM_NCPAINT`·`OnNcPaint`·`ControlPaint.DrawBorder3D`·`LinearGradientBrush` 를 MDI 창 테두리에 쓰는 코드는 없다. `LinearGradientBrush` 그림자는 조직도 이름 카드(`class.DraggablePanel.cs`, 우·하 3px, 알파 0→60)에만 있다.

Pd 시사점은 다음과 같다.
- 사용자 요구(그라데이션·음영 테두리, 창 아래 반투명 그림자)는 **Mars MDI 창의 실제 모습보다 강한 표현**이다. Mars 를 그대로 재현하면 요구를 충족하지 못한다. 따라서 Pd 는 Mars 수치를 출발점으로 하되, 아래를 Mars 보다 강화한다.
  - 외곽선: 1px 단일색 대신 바깥→안 2~3px 그라데이션(밝은 하이라이트 → 제목줄 색) 또는 위·좌 밝음 / 아래·우 어두움 베벨이다.
  - 그림자: Mars MDI 에는 없으므로 Pd 가 새로 정한다(창 크롬 수치의 정본은 `05_창크롬_OS디자인_기준.md`).
- 이 강화값은 Mars 실측이 아니라 Pd 설계값이다.

## 6. 시험 판정 규칙

UI 시험의 판정 값·측정 규칙·판정 지표·추가 시험 기준의 현행 정본이다. 판정 결과는 기록 문서(04 판정보고서와 부록 a1~a11)에 적는다. 기록 문서는 고치지 않으므로, 그 안의 옛 판정 낱말·기준 이름·규칙 문장은 이 절로 읽는다.

### 6.1 판정 값

- 판정 값은 `../05_아키텍처/53_Pd_용어_상태어휘_문서규칙.md` §3 축 ⑧ 의 합격·불합격·측정 보류와, 그 칸에 적용할 기준이 없을 때의 '해당 없음'이다(값 집합은 후보).
- 측정 보류에는 사유(측정값 없음·도구 판정 불가·선행 조건 미충족·실입력 필요 등)를 같은 칸에 적는다.
- 사용자가 기준 미달이나 측정값 없음을 받아들인 경우 판정 값은 그대로 두고 '(사용자 수용, 날짜)' 표시를 덧붙인다. 합격 수를 세는 쪽(제품 승격 조건·계약 gate)은 이 표시가 붙은 불합격·측정 보류를 합격으로 세지 않는다.
- ADR-007 의 기술 선택 판정 값(합격·조건부·탈락)은 기술 선택의 결론이라 이 판정 값과 다르다.
- 기록 문서의 옛 낱말은 다음처럼 읽는다.

| 옛 낱말 | 이 절의 값 |
|---|---|
| PASS, 해소, 해소(PASS) | 합격 |
| 조건부 PASS, PASS(조건부) | 합격(남은 조건은 같은 칸 비고) |
| FAIL | 불합격 |
| 사용자 승인 PASS(기준 미달) | 불합격(사용자 수용) |
| 사용자 승인 PASS(측정값 없음) | 측정 보류(사용자 수용) |
| PENDING, UNDET, HOLD, 판정 불가, 측정불가, 미측정, 미실행, 미점검, 부분 확인, 보류, 이월 | 측정 보류(사유) |
| N/A | 해당 없음 |

### 6.2 측정 규칙

1. 성능 판정은 측정된 실제 시간(ms)으로 한다. load1·CPU 부하는 참고로만 기록하고 시행을 무효로 하는 근거로 쓰지 않는다(2026-11-08 사용자 결정).
2. PC 화면을 쓰는 포그라운드 성능 측정과 실입력 시험은 사용자가 PC 를 쓰지 않을 때(PC 비움)만 한다. 창 비활성으로 판정할 수 있는 항목은 사용 중에도 한다. 모바일 실기기 측정은 PC 비움과 무관하다.
3. 사용자 지시로 2번을 벗어나 잰 회차는 결과 기록에 지시 시각과 범위를 적고 판정 값에 '(예외 측정)' 표시를 붙인다.
4. 대체 판정은 이 절에 적힌 것만 쓴다. 지금 있는 대체 판정은 하나다. 모바일 펼침 첫 프레임에서 첫 표본이 늦어 도구가 판정할 수 없으면 OS Displayed 보조 값으로 판정하고, 보조 값도 없으면 측정 보류로 둔다. 보조 판정을 썼다는 사실을 결과에 함께 적는다. 보조 판정은 첫 프레임 실측을 대신하지 않는다.
5. 회귀 도구는 비격리 기본 모드로 돌리지 않는다. 사용자 Pd·다른 시험 Pd 와 복원이 경합하기 때문이다.
6. 공식 재측정은 설정을 저장하지 않은 새 프로필로 하고 측정 전에 적용값을 확인한다. 지금 PoC 는 설정을 저장할 때 기본값까지 함께 저장해, 바뀐 제품 기본값이 이미 저장된 프로필에 닿지 않는다(TODO-617). 제품의 저장 규칙은 희소 저장이다(`../05_아키텍처/30_Pd_회사별_항목정책_옵션화_설계.md` §5.1).
7. 무효 회차(측정 시행 0, 측정 중 사용자 복귀, 프로세스 강제 종료, 절차 확인 실패)는 판정에 쓰지 않고 다시 잰다. 무효 사유는 결과 기록에 적는다.
8. 렌더 누락은 시각 트리 속성(effectivelyVisible·zIndex)만으로 판정하지 않고, 해당 영역을 잘라낸 화소 검사를 함께 한다. 빈칸 기준은 고유색 수 ≤ 4 또는 표준편차 < 6 이다(시험 도구 설정값, 후보).
9. 데스크톱 화면 밖 시험은 `--offscreen-guard on` 으로 기동해 시험 창·팝업이 사용자 화면에 나오지 않게 한다.
10. 헤드리스 고DPR 웹 시험은 장치 배율을 force 인자로 고정하고, 실제 장치(실기기 브라우저) 결과와 함께 판정한다.
11. 웹 관리형 창의 위치 복원은 공식 위치 (xf, yf) 를 창 레이어(W×H) 안으로 당긴 x = min(xf, W−w), y = min(yf, H−h)(최소 0)로 판정한다.
12. 유휴 정지(유휴 렌더) 판정은 외부 캡처로 하고, 마지막 입력 뒤 4초 안에 같은 값으로 고정되면 합격이다. 측정 구간 안에서는 측정 대상 원격 명령을 보내지 않는다(명령이 렌더를 깨운다). 기동 지연 재측정은 조용한 창에서 두 판을 교대로 3회 띄운 중앙값이 ±10% 를 넘을 때만 지연으로 본다. 진단 표본 수집 방식이 바뀐 판의 값은 예전 판 기준값과 직접 비교하지 않는다(Q4 공식 측정 원칙).

### 6.3 판정 지표

- **커밋 프레임 p95**(PERF-02 판정선). 그릴 것이 있어 실제로 커밋된 프레임 간격만 모아 nearest-rank 로 p95 를 구한다. 커밋 없는 간격(유휴 틱)은 집계에서 빼되 개수와 p50 을 함께 보고한다. 기준은 ≤ 25ms 이고 표본 하한은 30 이며, 모자라면 측정 보류다. 판정기는 `poc/ui/test/desktop/judge/b2_commit_frames.py` 다.
- **누락 공백**. 입력(실제 이동) 시각 뒤 첫 커밋까지의 공백이 25ms 를 넘으면 누락 1건이고 허용은 0건이다. 측정 끝까지 커밋이 없고 경과가 25ms 이하이면 누락이 아니라 미결로 따로 센다. 커밋 지표가 무거운 렌더를 빼먹는 약점을 막는 장치다.
- **계측 의존**. 커밋은 진단 빌드에서 Avalonia 12.1.4 Compositor 의 internal `AfterCommit` 을 리플렉션으로 구독해 잰다. 찾지 못하면 `commit_source=unavailable:<사유>` 를 남기고 측정 보류다. `AfterCommit` 은 화면 표시 시점이 아니라 배치를 렌더 스레드로 넘긴 시점이다. Avalonia 판을 올리면 이 계측이 그대로 되는지 먼저 확인한다.
- **웹 끌기 판정값**(A15·H-02 → PERF-02 지원 칸 #7, 무변화 간격 제외, 2026-11-14 사용자 결정, 측정 전에 정함, 근거 결정 번호는 D-568). 끌기 구간(누름 ~ 놓음 + 50ms)의 `Display::DrawAndSwap` 간격에서 무변화 간격을 뺀 간격을 문서마다 12회 합쳐 nearest-rank p95 를 구한다. 기준은 ≤ 25ms 다. 원래 p95(모든 간격 포함)와 뺀 간격 수를 함께 기록한다(결과 필드 `p95_ms`=판정값, `p95_all_ms`=원래값, `excluded_static_gaps`=뺀 수). 측정 도구는 `poc/ui/test/web/measure/drag_static_gaps.py`(판별)·`w10_web.py`(기록)다.
  - 무변화 간격 판별. 연속한 두 `DrawAndSwap` 사이 간격 g 가 25ms 를 넘고 다음 셋을 모두 만족하면 무변화 간격이다. ① 놓기(`EventLatency` MOUSE_RELEASED 시작 시각)가 그 간격 안에 없다. ② 간격 양끝에서 2ms 안쪽에 있는 VizCompositorThread `ExternalBeginFrameSource::OnBeginFrame` 중 하나 이상이 무작업이다. 무작업은 그 BeginFrame 시각부터 8ms 안에 시작한 CrRendererMain `FireAnimationFrame` 이 없거나 그중 가장 긴 것이 2ms 미만인 경우다(실측 0.1~0.6ms). ③ 간격 안 CrRendererMain `ThreadControllerImpl::RunTask` 와 겹친 시간 합이 g 의 60% 미만이다. 앱이 그릴 것이 없어 프레임이 나오지 않은 유휴 간격(자석 유지 정지·시작 빈 프레임)만 뺀다.
  - 판정에 남는 것. 놓기 간격(①, 놓기 1틱 지연 포함)과 느린 렌더(② 또는 ③ 불만족)는 실제 지연이라 빼지 않는다. 25ms 이하 간격도 모두 남는다. 결과를 본 뒤 이 정의를 바꾸지 않는다.
- 지표를 바꾼 사유와 기각한 대안은 기록 부록 a11 의 반복 3 에 있다.
