# 소스 구조·파일 분할 규칙 (ADR-003)

> 상태 설계 정본(ADR-003) · 작성일 2026-10-28 · 줄 수 수치는 후보이고 구현 착수 전 PoC 로 정한다
> 사용자 지시: "소스는 항상 짧게 여러 개 파일로 분할해야 한다. 클로드코드가 한 번에 읽기 쉬워야 한다. 단순 split 이 아니라 목적과 역할과 기능에 맞게 최대한 잘 분리시켜라."

## 1. 왜 필요한가

| 이유 | 설명 |
|---|---|
| AI 개발 효율 | AI 에이전트(Claude Code)는 파일을 선택적으로 읽는다. 파일 하나가 한 가지 일만 하면 필요한 파일만 통째로 읽어 맥락 손실 없이 수정할 수 있다. |
| 사람 가독성 | 파일 이름과 폴더만 보고 위치를 찾을 수 있다. |
| 병렬 작업 | 파일이 작고 책임이 분리되면 여러 에이전트·개발자가 충돌 없이 동시에 작업한다. |
| 반면교사(Mars) | `1002_프로젝트정보.cs` 15.5K줄, `1003_티켓.cs` 15.1K줄, `0000_메인.cs` 11.4K줄, 간트 partial 9.4K줄. 한 번에 읽을 수 없어 수정 범위 파악과 회귀 방지가 어려웠다. |

## 2. 크기 기준

> 서버 `pd-server` 는 Rust 다(ADR-016). 표의 `.cs`·`.axaml`·`.axaml.cs`·EF 행은 클라이언트·`pd-admin`(C#) 기준이다. Rust 행의 수치는 후보이고 구현 착수 전 PoC 로 정한다. 서버 소스 구조는 §9 를 따른다.

| 대상 | 권장 | 상한(CI 차단) |
|---|---|---|
| C# 파일(.cs) | 200줄 이하 | 300줄 |
| Rust 파일(.rs, 서버) | 200줄 이하(후보) | 300줄(후보) |
| 화면 마크업(.axaml — Avalonia, ADR-007) | 120줄 이하 | 200줄 |
| 화면 코드 비하인드(.axaml.cs)·ViewModel | 150줄 이하 | 250줄 |
| 메서드 | 30줄 이하 | 60줄 |
| SQL 파일·EF 설정 파일 | 150줄 이하 | 250줄 |
| 테스트 파일 | 250줄 이하 | 400줄 |

- 예외는 자동 생성 코드(EF Migrations, gRPC/OpenAPI 생성물)뿐이며 `*.g.cs`, `Migrations/` 로 위치를 고정해 검사에서 제외한다.
- 상한 초과가 정말 불가피하면 파일 첫 줄 헤더 주석에 사유를 적고 `size-exception.json` 에 등록한다(리뷰 승인 필수).

## 3. 분할 기준 — "줄 수"가 아니라 "책임"

### 3.1 금지하는 기계적 분할

- 같은 클래스를 `partial` 로 쪼개 파일만 나누는 것(책임은 그대로라 단순 split 이다).
- `Foo1.cs`, `Foo2.cs`, `FooPart.cs`, `FooHelper2.cs` 처럼 번호·의미 없는 이름.
- 거대 `Utils`/`Common`/`Helpers` 잡동사니 파일.

> `partial` 은 소스 생성기 연동처럼 기술적으로 필요한 경우만 허용한다.

### 3.2 허용하는 분할 축(우선순위 순)

1. **기능 슬라이스(Vertical Slice)** — 유스케이스 하나가 폴더 하나다.
2. **역할(계층)** — 같은 기능 안에서 요청 모델·검증·처리·API 엔드포인트·화면을 나눈다.
3. **도메인 개념** — 엔터티·값 객체·도메인 규칙은 개념 하나에 파일 하나다.
4. **화면 구성요소** — 화면은 영역(헤더·필터·그리드·상세 패널)별 하위 컴포넌트로 나눈다.

### 3.3 한 파일의 원칙

- 공개(public) 타입 하나 = 파일 하나, 파일명 = 타입명.
- 첫 줄은 한국어 한 줄 역할 주석이다(CLAUDE.md 신규 파일 헤더 규칙과 동일).
- 파일이 "그리고"로 설명되면(예: "프로젝트를 저장**하고** 메일을 보낸다") 나눈다.

## 4. 폴더 구조 예시 (프로젝트 생성 유스케이스)

> 아래 예시의 폴더·crate·프로젝트 이름은 후보다. 서버는 §9 의 Cargo workspace 구조(crate 구성 정본은 `../05_아키텍처/32_Pd_모듈화_조립구조_설계.md` §6), 클라이언트는 §11 의 층 구조를 따른다(배치·설치 구성은 `../05_아키텍처/20a_Pd_시스템아키텍처_데이터흐름_배치.md`·`../05_아키텍처/20e_Pd_시스템아키텍처_배치_운영_부록.md`).

```
crates/prj/src/projects/
├─ create_project/
│  ├─ command.rs                     # 프로젝트 생성 요청 모델
│  ├─ validator.rs                   # 생성 요청 입력 검증 규칙
│  ├─ handler.rs                     # 생성 처리(권한·요금제 확인 후 저장)
│  └─ event.rs                       # 생성 완료 도메인 이벤트
├─ update_schedule/ ...
└─ README.md                         # 이 기능 묶음의 유스케이스 목록(AI 진입점)

crates/prj/src/api/projects/
├─ create_project.rs                 # POST /projects 라우트 매핑
└─ ...

client/Pd.Prj.Views/Projects/        # prj 화면 모듈(§11)
├─ ProjectListViewModel.cs           # 목록 화면 상태·명령(UI 기술 중립)
├─ ProjectFilterState.cs             # 검색·필터 조건 상태 모델
├─ ProjectListView.axaml             # 프로젝트 목록 화면 골격(MDI 문서로 열림)
├─ ProjectListView.axaml.cs          # 화면 초기화(로직 없음)
└─ Parts/
   ├─ ProjectFilterBar.axaml         # 검색·필터 영역
   ├─ ProjectGrid.axaml              # 목록 그리드
   └─ ProjectSummaryPanel.axaml      # 선택 프로젝트 요약 패널
```

간트처럼 복잡한 화면도 같은 방식으로 나눈다. 렌더링(타임라인·막대·의존선), 상호작용(드래그·줌), 계산(CPM·날짜 축), 데이터 어댑터를 각각 독립 파일·클래스로 둔다.

## 5. AI 탐색 보조 규칙

- 기능 폴더마다 `README.md`(10~30줄)에 유스케이스 목록과 진입 파일을 적는다.
- 저장소 루트에 `docs/code-map.md` 를 두고 모듈 → 폴더 → 대표 파일을 한 표로 유지한다(자동 생성 스크립트 권장).
- 파일 경로만으로 역할을 알 수 있어야 한다. 경로 = 모듈/기능/역할.

## 7. PROJECT.md 파일 인벤토리 기록 규칙 (ADR-004)

> 사용자 지시: "잘게 쪼개진 파일이 많을 것이므로 개발/수정 시마다 odone 단계에서 PROJECT.md 에 정확히 잘 기록해야 한다."

### 7.1 언제

- 모든 개발·수정 사이클의 **odone 단계**(테스트 통과 후 마무리)에서 갱신한다. 커밋 전에 끝낸다.
- 대상 이벤트는 파일 추가·삭제·이동·이름변경과 역할(헤더 주석) 변경이다.

### 7.2 무엇을, 어떤 형식으로

PROJECT.md 의 "파일 인벤토리" 절에 모듈 → 기능 폴더 → 파일 순서로 한 파일 한 줄씩 적는다. 묶음 단위는 모듈 등록부(`../05_아키텍처/48_Pd_연동설계_총괄_계약등록부.md` §3.1)의 모듈 이름이다. 기능 영역 코드(PRJ·ISS 등)는 소유 모듈을 뜻하지 않으므로(D-496) 묶음 단위로 쓰지 않고 표의 기능ID 열로만 둔다.

```markdown
### prj — crates/prj/src/projects/
| 파일 | 역할 | 기능ID |
|---|---|---|
| create_project/handler.rs | 생성 처리(권한·요금제 확인 후 저장) | PRJ-01 |
| create_project/validator.rs | 생성 요청 입력 검증 규칙 | PRJ-01 |
```

- **역할 = 파일 첫 줄 한국어 헤더 주석과 같은 문장**이다. 두 곳이 어긋나지 않도록 헤더 주석을 정본으로 삼는다.
- 기능ID 는 `plan/06_기능목록` 의 ID 이다. 코드 → 요구사항 추적이 가능해진다.

### 7.3 정확성 확보 — 손 기록이 아니라 생성 + 검증

| 단계 | 방법 |
|---|---|
| 생성 | `tools/gen-inventory` 스크립트가 각 파일의 첫 줄 헤더 주석과 경로를 읽어 PROJECT.md 의 `<!-- INVENTORY:BEGIN -->` ~ `<!-- INVENTORY:END -->` 블록을 다시 만든다. 블록 밖 설명은 사람이 쓴다. |
| 검증(odone) | 이번 사이클 git 변경 파일 목록과 인벤토리 블록을 대조한다. 추가·삭제·이동된 파일이 블록에 반영되지 않았거나, 헤더 주석이 없거나 비어 있으면 **실패**한다. |
| 검증(CI) | 같은 검사를 PR 단계에서도 실행해 odone 을 거치지 않은 변경도 잡는다. |

### 7.4 PROJECT.md 크기 관리

파일이 수백~수천 개가 되면 PROJECT.md 자체가 한 번에 읽기 어려워진다(§2 원칙과 충돌). 그래서 다음 구조를 쓴다.

- PROJECT.md 본문에는 모듈 지도(모듈 → 폴더 → 대표 진입 파일)와 모듈별 인벤토리 블록을 둔다.
- 모듈 절은 `### {모듈 이름}` 제목(모듈 등록부의 소문자 모듈 이름)으로 시작해 Grep 으로 해당 절만 찾아 읽을 수 있게 한다.
- 그래도 PROJECT.md 가 정해 둔 한계(예: 1,500줄, 후보)를 넘으면 모듈별 인벤토리를 `docs/inventory/{모듈 이름}.md` 로 나누고, PROJECT.md 에는 링크와 요약만 남긴다. 이때도 생성·검증 스크립트는 그대로 쓴다. 한계 수치는 착수 시 정한다.

### 7.5 하네스 연동(참고 — 이번 계획 범위 밖)

- 현재 하네스의 문서 갱신 게이트는 PROJECT.md 누락을 **경고만** 한다(CLAUDE.md 「프로젝트 문서 체계」 기준).
- Pd 저장소에서는 §7.3 의 검증 스크립트를 odone 단계의 **차단 게이트**로 연결해야 한다. odone 스킬·hook 수정은 신규 저장소 생성 시점의 별도 작업으로 남긴다.

## 8. 이 문서가 바꾸는 다른 설계

- 서버 crate(§9)와 클라이언트 화면 모듈(§11)은 내부를 기능 슬라이스 폴더로 구성한다.
- 간트·대시보드 등 Mars 에서 거대했던 화면은 상세 설계 단계에서 컴포넌트 분해도를 먼저 그린다.

## 9. 서버 Rust 소스 구조 (ADR-016)

서버 `pd-server` 는 Rust 다(ADR-016, `plan/05_아키텍처/20_Pd_시스템아키텍처_구성_연관도.md` §8). 이 절은 서버 소스의 줄 수·책임 분할 규칙만 정한다. crate 구성(모듈마다 계약 crate 와 구현 crate)의 정본은 `../05_아키텍처/32_Pd_모듈화_조립구조_설계.md` §6 이다.

- Cargo workspace 로 구성하고 모듈 등록부(`../05_아키텍처/48_Pd_연동설계_총괄_계약등록부.md` §3.1)의 모듈마다 32 §6 의 crate 를 둔다. 구현 crate 안은 도메인·응용·인프라로 나눈다(서버 레이어 구조, 아키텍처 §7).
- 응용 계층은 포트(trait)에 의존하고 어댑터(DB·캐시·검색·큐·원격 gRPC)는 인프라 계층이 구현한다.
- 계약 원본(OpenAPI·protobuf·JSON Schema)은 모듈마다 그 모듈의 계약 crate 옆에 둔다(32 §6). 저장소 한가운데 폴더 하나에 모든 모듈의 계약을 모으지 않는다. 형식·버전 규칙은 `../05_아키텍처/52_Pd_계약버전_규칙.md` 가 정본이고 버전 단위는 모듈이다(D-495). 코드는 계약 원본에서 생성하는 방향으로만 만들고, 생성 도구는 도입 때 정한다(후보).
- 줄 수 원칙(§2)과 책임 기준 분할(§3)은 Rust 에도 그대로 적용한다. 파일은 책임 하나이고 첫 줄은 한국어 역할 주석이다. 상한 수치는 §2 의 Rust 행(후보)이다.
- 다른 언어 서비스(커넥터 C#, AI 사이드카 Python, 실시간 허브 C# SignalR)는 별도 폴더·별도 솔루션으로 두고 같은 분할 원칙을 따른다.

## 10. 디자인 자산 공유 폴더

사용자 지시(2026-11-01)로 아이콘·로고·이미지·글꼴은 저장소 루트의 공유 폴더 `assets/` 에서 주고받는다. 상세 규칙은 `../../assets/README.md` 가 정본이다.

- 사용자 원본은 `assets/incoming/` 에 넣고 삭제·덮어쓰기를 금지한다. Claude 생성분은 `assets/generated/`, 다듬은 정리본은 `assets/icons/`·`logos/`·`images/`·`fonts/` 에 둔다.
- 파일명은 kebab-case 와 크기 접미(`-16`~`-256`)를 쓰고, 아이콘은 SVG 를 정본으로 둔다.
- 앱·웹 소스 트리에 자산 원본을 두지 않는다. 빌드 때 `assets/` 에서 복사(또는 링크)하며 구체 방식은 WBS-M0 에서 정한다.
- 자산을 추가하면 `assets/_LICENSES.csv` 에 행을 추가한다.

## 11. 클라이언트 3층 구조 — UI/UX 소스 분리

UI/UX 소스는 완전히 분리해 관리·개발한다. 의존은 한 방향이고 순환을 금지한다. 클라이언트 층 구조와 업무 화면 모듈 단위의 정본은 `../05_아키텍처/32_Pd_모듈화_조립구조_설계.md` §7 이고, 이 절은 프로젝트 이름과 참조 금지 규칙을 적는다. `Pd.Poc.*` 는 PoC 프로젝트 이름이다. 제품 이름은 `xkxk.frameworks.ui.shell` → `Pd.Shell`, `xkxk.frameworks.ui.desktop`·`Browser`·`Android` → `Pd.Desktop`·`Pd.Browser`·`Pd.Android` 로 대응한다(후보).

```
시험대 실행 프로젝트(testbed/ 의 desktop · browser · android)   Program·wwwroot·Android 특성 등 플랫폼 진입 자산, 호스팅 라이브러리를 호출하며 TestbedModule 을 등록(B11)
        ↓
호스팅 라이브러리(xkxk.frameworks.ui.hosting.desktop / .browser / .android)   플랫폼 공통 코드(Win32 훅·SDI 창·저장소·진입 조립), 공개 진입점 7형식만 노출(B11, UADR-0018)
        ↓
화면 모듈(업무 모듈마다 1개, 이름 후보 Pd.<모듈>.Views)   그 모듈의 화면·뷰모델·메뉴 항목을 셸 등록 경로로 등록만 한다
xkxk.frameworks.ui.views                                  셸·공통 화면 조립층: 셸 화면·Themes·견본 문서·설정 페이지의 axaml + 코드비하인드(업무 모듈 화면은 두지 않는다)
        ↓
xkxk.frameworks.ui.shell                                 컨트롤층: 명령·상태 전이·서비스·뷰모델, 도킹 모델 조작
   ↓              ↓
xkxk.frameworks.ui             xkxk.frameworks.ui.data             xkxk.frameworks.ui = 순수 UI 층(재사용 컨트롤·스타일·애니메이션) / xkxk.frameworks.ui.data = 데이터층(DTO·저장소·직렬화·로깅·카탈로그)
```

### 11.1 층별 참조 규칙

| 층 | 참조 금지 |
|---|---|
| `xkxk.frameworks.ui` | `xkxk.frameworks.ui.shell`, `xkxk.frameworks.ui.data`, `xkxk.frameworks.ui.views`, 화면 모듈, 호스트, Dock. 패키지는 Avalonia 12.1.4 만 허용 |
| 화면 모듈 | 다른 화면 모듈, `xkxk.frameworks.ui.views`, 호스트. `xkxk.frameworks.ui.shell`·`xkxk.frameworks.ui`·서버 공개 계약에서 생성한 API 클라이언트만 참조한다(32 §7 1·2번) |
| `xkxk.frameworks.ui.views` | 화면 모듈, 호스트. `xkxk.frameworks.ui.shell` 참조는 허용한다(컴파일드 바인딩 `x:DataType` 유지) |
| `xkxk.frameworks.ui.shell` | `xkxk.frameworks.ui.views`, 화면 모듈, 호스트. 화면은 `IViewRegistry` 로 열어 역참조를 없앤다 |
| `xkxk.frameworks.ui.data` | Avalonia 패키지·코드, `xkxk.frameworks.ui.shell`, `xkxk.frameworks.ui`, `xkxk.frameworks.ui.views`, 화면 모듈, 호스트 |
| `xkxk.frameworks.ui.hosting.desktop`·`.browser`·`.android`(호스팅 라이브러리, 영역 `src/`, B11) | `xkxk.frameworks.ui.testbed`·시험대 실행 프로젝트, 화면 모듈. 참조할 수 있는 것은 `xkxk.frameworks.ui.shell`·`xkxk.frameworks.ui.views`·`xkxk.frameworks.ui`·`xkxk.frameworks.ui.data` 와 플랫폼 패키지(Avalonia.Desktop·Browser·Android)다. 공개 형식은 진입점 7개뿐이고 `InternalsVisibleTo` 는 0 이다(UADR-0018) |
| 시험대 실행 프로젝트(`testbed/xkxk.frameworks.ui.testbed.desktop`·`.browser`·`.android`, B11) | 없음. 호스팅 라이브러리와 프레임워크 공개 형식을 참조한다. `wwwroot`·`[Application]`·`[Activity]` 특성·JSExport 형식·아이콘은 이 프로젝트가 가진다(UADR-0018). 이름은 B11-2 에서는 옛 값(`xkxk.frameworks.ui.desktop`·`.browser`·`.android`)을 유지하고 B11-3 에서 `xkxk.frameworks.ui.testbed.*` 로 바꾼다 |
| `xkxk.frameworks.ui.testbed`(시험대, 영역 `testbed/`, B10) | 없음. 프레임워크 모든 층(`xkxk.frameworks.ui`·`xkxk.frameworks.ui.data`·`xkxk.frameworks.ui.shell`·`xkxk.frameworks.ui.views`)을 참조할 수 있다. 단 공개 형식·멤버만 쓴다. `xkxk.frameworks.ui.*.Internal` 네임스페이스, 리플렉션 `BindingFlags.NonPublic` 우회, 프레임워크 csproj 의 `InternalsVisibleTo` 는 금지다(UADR-0008·UADR-0017) |

- 거꾸로 프레임워크 층(`src/` 의 위 4층)은 시험대를 참조하지 못한다. 호스팅 라이브러리(`src/xkxk.frameworks.ui.hosting.*`)도 시험대를 참조하지 못한다. 시험대를 참조하는 것은 시험대 실행 프로젝트이고, B11 이후 `src/` 에는 실행 프로젝트가 없다.

- UI 층을 둘로 나눈 이유: 기존 axaml 이 `x:DataType="vm:*"` 컴파일드 바인딩이라 뷰모델 타입 없이는 컴파일되지 않는다. 화면 조립은 셸을 참조하는 `xkxk.frameworks.ui.views` 에 두고, 재사용 부품은 셸을 모르는 `xkxk.frameworks.ui` 에 둔다.
- `xkxk.frameworks.ui` 는 상위 층의 값을 속성·이벤트·작은 레코드로만 받는다. 문자열은 `UiText.Provider` 훅으로 받고 셸이 `Loc.Tr` 를 연결한다.
- 파일별 층과 근거는 자동 생성 분류표 `poc/ui/LAYERS.md`(`poc/ui/tools/classify_layers.py`)에 있다. 사유가 필요한 예외는 `poc/ui/tools/classify_layers_overrides.json` 에 둔다.

### 11.2 강제 수단

`poc/ui/tools/check_layers.py`(규칙 `check_layers_rules.json`)가 프로젝트 참조·패키지·코드의 참조(using·`avares://`·xmlns, 주석 제외)를 정적으로 검사한다. 위반이 있으면 rc=1 이고, 실행 시간 상한은 3초다(마지막 줄 `elapsed_ms=<n>`). 층 파일(`xkxk.frameworks.ui`·`xkxk.frameworks.ui.views`·`xkxk.frameworks.ui.data`)은 300줄 이하, 첫 줄 한국어 헤더 주석을 함께 검사한다. 템플릿 부품 이름(`PART_*`)은 Shell 코드에 쓰지 못하고 `xkxk.frameworks.ui` 의 `TemplateParts` 상수로만 쓴다. `check_layers_parts.py` 가 계약 상수의 실재를 `xkxk.frameworks.ui.views` axaml 의 `Name` 정의나 Shell 이 참조한 판본의 Dock DLL 에서 대조하고, DLL 을 못 찾으면 위반으로 친다.

시험대 층 규칙(11.1 표의 `xkxk.frameworks.ui.testbed` 행과 프레임워크 층의 시험대 참조 금지)은 B10 에 `check_layers_rules.json` 에 넣고 활성한다. 이 표가 먼저이고 규칙 파일이 이를 따른다.

화면 모듈 층 규칙(화면 모듈 사이 참조 금지, 화면 모듈 → `xkxk.frameworks.ui.views` 참조 금지)은 `check_layers.py` 에 아직 없다. 검사 항목 후보(미구현)이고 32 §10 C5 확장과 함께 넣는다.

한계: 사람이 규칙 파일을 고치면 검사가 무력화된다. 그래서 odone 게이트에서 실행한다.

### 11.3 이동 뒤 불변 조건

- `xkxk.frameworks.ui.shell` 에는 `.axaml` 이 없다. 앱 진입점은 `xkxk.frameworks.ui.views.PdApp` 이고 셸의 `App` 은 정적 표면과 시작 절차를 가진 기반 클래스다.
- 셸은 화면을 `IViewRegistry`(`ViewRegistry.Current`)로만 만들고 연다. `InternalsVisibleTo` 는 쓰지 않는다. 화면 층이 쓰는 셸 멤버는 필요한 것만 `public` 으로 연다.
- `xkxk.frameworks.ui.data` 는 `Avalonia`·`xkxk.frameworks.ui.shell` 문자열을 코드에 두지 않는다.
- 저장 형식이어도 `UiSettingsDto`·`LayoutSerializer`·`SplitLayoutCodec` 는 셸에 남아 있다. 제어층 형식을 참조해 옮기려면 별도 리팩터링이 필요하다.
- Shell 에 남은 Avalonia 코드는 화면 조립이 아니라 서비스다(`Platform/`·`Input/`·`Docking/`·`Diagnostics/`). 셸은 "화면을 조립하지 않는 층"이지 "Avalonia 를 쓰지 않는 층"이 아니다.

### 11.4 차트뷰 프로젝트 경계 (ADR-076~081, REQ-58)

정본은 `plan/09_화면설계/08_차트뷰_설계.md` §3.1 이고 이 절은 3층 구조(11.1)에 맞춘 후보 정리다. 프로젝트 이름과 분할은 후보이고 구현 착수 때 정한다.

- **UI 층(`xkxk.frameworks.ui`):** 차트뷰 컨트롤과 시간축 렌더러(줌·가상 스크롤·구간 선택·드래그의 공유 부분)를 둔다. 막대 의미는 뷰별 플러그인으로 바꾼다(ADR-077). 그리기와 입력만 맡고 서버·저장소를 모른다.
- **컨트롤 층:** 뷰 상태·명령·선택 동기화와 `ViewContext`(프로젝트·조직·기간·기준선·권한 범위)를 Avalonia 에 의존하지 않는 C# 라이브러리로 둔다.
- **어댑터 경계:** 차트 라이브러리(LiveCharts2·ScottPlot 5, ADR-047)는 `IChartAdapter` 만 거친다. 라이브러리 타입은 어댑터 구현 프로젝트 밖으로 새지 않는다.
- **데이터 층(`xkxk.frameworks.ui.data` 규칙):** 서버 API·읽기 모델·캐시 접근만 맡고 Avalonia 를 참조하지 않는다(11.1 표).
- 위 경계도 11.2 의 `check_layers.py` 규칙에 포함할지는 구현 착수 때 정한다.
- 공통 차트(`ChartSpec`)와 공통 칸반 보드 컴포넌트(ADR-091, 결정 52·54)도 UI 층(`xkxk.frameworks.ui`)에 두고 뷰는 설정·파라미터로만 다르게 한다(`plan/09_화면설계/08_차트뷰_설계.md` §3.11·§8 인계).
